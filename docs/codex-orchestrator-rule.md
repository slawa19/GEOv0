# Codex orchestrator rule

Status: current operational rule  
Owner surface: repository-wide review and refactoring  
Companion sources: `../AGENTS.md`, `../specs/001-codebase-renovation/`

Этот файл читается вместе с корневым `AGENTS.md` каждый раз, когда Codex работает
как оркестратор. Он не заменяет продуктовые контракты и не разрешает менять код
ради соответствия документации.

## 1. Контекст, который хранит главная сессия

Оркестратор остаётся владельцем общей картины и не отдаёт агентам принятие
межсрезовых решений. В рабочем ledger постоянно удерживаются:

- цель текущей волны, non-goals и критерий остановки;
- current / intended / optimal behavior для найденных расхождений;
- защищённые доменные, API, persistence, event и UI-контракты;
- dependency graph задач и один владелец каждого изменяемого owner surface;
- подтверждённые findings с приоритетом, evidence и решением;
- точные выполненные gates и отдельно непроверенные среды;
- остаточный долг, который сознательно не входит в текущий срез.

Рутинное редактирование и широкие исследования делегируются. Интеграционные
решения, разрешение конфликтов и финальное заявление об эффекте остаются у
оркестратора.

## 2. Порядок комплексного review

Review идёт сверху вниз, но решение принимается по эффекту, а не по размеру файла:

1. Зафиксировать состояние git, активные entrypoints, runtime/tooling и baseline.
2. Построить карту продукта: пользовательские потоки, процессы, хранилища,
   внешние границы и критические инварианты.
3. Проверить архитектурное владение: зависимости, source of truth, UoW,
   lifecycle, shared mutable state и failure semantics.
4. Проверить сквозные контракты: config/security, OpenAPI/events, schema/migrations,
   frontend consumers, fixtures и observability.
5. Проследить критические пути до функций и кодовых блоков: success, rejection,
   failure, retry, cancellation, commit/rollback и cleanup.
6. Проверить тестовую ценность, CI/gates, repository artifacts и актуальность
   документации как независимые evidence surfaces.
7. Сформировать backlog из обратимых вертикальных срезов и выполнять сначала
   P1/high-leverage изменения.

Не требуется линейно читать каждую строку. Кодовый блок рассматривается вместе с
его callers, sibling paths и наблюдаемыми эффектами.

## 3. Делегирование

Агенту выдаётся крупная законченная пачка с:

- конкретным результатом и owner surface;
- разрешёнными и запрещёнными файлами;
- входными фактами, инвариантами и соседними зависимостями;
- unique task slug/DB/ports/output root;
- targeted и milestone gates;
- форматом отчёта: `path:line`, команда, exit code, риски, unverified paths.

Параллельно работают только непересекающиеся write surfaces. Общие contract-файлы
передаются последовательно одному владельцу. Если агент находит проблему за
пределами своего среза, он сообщает её оркестратору, но не расширяет diff молча.

## 4. Приём результата агента

Отчёт агента не является доказательством сам по себе. Оркестратор:

1. проверяет diff и ключевые call-sites;
2. воспроизводит несущие targeted gates через canonical repo entrypoint;
3. отличает debug run от task-isolated/canonical evidence;
4. назначает другому агенту read-only adversarial review крупного или рискованного
   среза;
5. возвращает подтверждённые P1/P2 исходному владельцу на минимальное исправление;
6. повторяет review и gates после исправления.

Reviewer ищет false-green тесты, пропущенные sibling paths, ordering/cancellation,
transaction и cache boundaries, скрытое изменение wire/API semantics и поломку
активных callers. Он не занимается стилевыми мелочами без широкого эффекта.

Для высокорисковой commit-пачки после внутреннего adversarial review применяется
внешний Claude Code review по правилам `AGENTS.md`:

1. Зафиксировать coherent exact `BASE..HEAD` и создать чистый standalone clone с
   локальным credential-free origin; основной checkout и worktree не подходят,
   если их общая `.git/config` содержит credential.
2. Запустить встроенный `/code-review high` с `--model opus --effort high`, plan
   permissions и запретом edit/write tools. Сохранить CLI version, resolved model
   из JSON, SHAs, exit code и полный результат вне репозитория.
3. Пока frozen clone проверяется, продолжать только непересекающиеся slices.
4. Вручную воспроизвести P1/P2 и передать подтверждённые findings агентам; внешний
   reviewer не меняет файлы и не принимает решения.
5. Разрешить один remediation review по fix-delta. Повторный P1 блокирует или
   пересматривает slice; P3 не создаёт новую работу автоматически.

Сбой, timeout, exit `1/130`, пустой или повреждённый JSON — отсутствие evidence,
а не чистый review. `ultrareview` не подтверждает конкретную модель и применяется
только как опциональный дополнительный pipeline в пределах его diff-limit.

## 5. Решение и пределы среза

Finding принимается, если есть воспроизводимый пользовательский, операционный,
security, integrity или существенный maintenance effect. Предпочтение отдаётся
минимальному общему правилу. Не вводятся новый framework, outbox, service layer
или generalized abstraction только для гипотетической полноты.

Набор задач выбранной волны замораживается перед реализацией. Same-slice
регрессия или P1 возвращается владельцу этого slice; несвязанный P1 требует явно
принятого follow-up, P2 сопоставляется существующей задаче или датированному
accepted debt, P3 волну не расширяет. Review не используется как генератор
неограниченного backlog.

Если надёжное исправление требует нового полномочия, production mutation,
необратимой миграции или продуктового выбора с разными последствиями, работа
останавливается и решение запрашивается у владельца.

## 6. Закрытие волны

Волна закрывается только когда:

- все принятые findings исправлены, отклонены с evidence или записаны как долг;
- targeted gates повторены оркестратором после последнего изменения;
- выполнен применимый milestone gate либо явно указана причина отсутствия;
- независимое review не оставило нерешённых P1;
- `spec.md`/`tasks.md` отражают фактический статус и непроверенные поверхности;
- документация изменена только после выбора и проверки нового target behavior;
- `git diff --check`, status и tracked-artifact/secret checks не показывают нового
  мусора или секрета.

Финальный отчёт сначала описывает достигнутый эффект, затем evidence и остатки.
Фразы «всё зелёное», «CI green» и «готово» запрещены, если не пройдены все
соответствующие published/production-like gates.
