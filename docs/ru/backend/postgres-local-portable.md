# Локальный PostgreSQL без Docker и без прав администратора

Статус: Stable
Область: backend
Последнее обновление: 2026-09-23

Как за несколько минут поднять PostgreSQL, на котором идёт тир тестов, на машине без
Docker и без прав администратора. Написано после фактического подъёма 2026-08-20; все ловушки ниже —
не гипотетические, каждая встречена в реальном прогоне.

**Когда это нужно.** Всегда, когда запускаются backend-тесты: с 2026-09-23 (017, стадия 2c) тир
тестов идёт только на PostgreSQL, SQLite-тира больше нет, и без запущенного кластера
`scripts/verify_local.ps1` отказывает до сбора тестов. См. `AGENTS.md` §5.

**И он обязателен, чтобы вообще поднять стек.** С `T1710` (программа 017) `scripts/run_local.ps1` и
`scripts/run_full_stack.ps1` работают только на PostgreSQL: файлового движка у лаунчера больше нет,
и без запущенного кластера они отказывают с указанием на §3 этого документа. Базы лаунчера — §8.

**Когда это НЕ нужно.** Если на машине есть Docker — используйте штатный путь из
[`README.md`](../../../README.md), раздел «Postgres-backed backend tests»: `docker compose up -d db`.
Этот документ — альтернатива для машин без Docker, а не замена ему.

## 0. Ловушки, из-за которых теряют время

Прочитайте до начала — каждая стоила отдельного разбирательства.

1. **Инсталлятор требует UAC.** GUI-диалог в агентской сессии не будет закрыт никем и повесит прогон
   до таймаута. Поэтому берутся **портативные бинарники**, а не installer.
2. **`pg_ctl start` держит консоль.** Запущенный напрямую, он не возвращает управление, а сервер
   становится дочерним процессом этой оболочки. Когда оболочку убивают (таймаут, teardown агента,
   конец сессии) — **сервер умирает вместе с ней**. Запускать только отвязанным процессом (§3).
3. **Версия должна совпадать с CI.** `.github/workflows/quality.yml` пинит `postgres:16`. Ставить
   «последнее» значит получить локальные гейты, не представляющие CI.
4. **Сброс схемы требует `GEO_TEST_ALLOW_DB_RESET=1`.** Это предохранитель, а не препятствие: без
   него `verify_local.ps1` откажется трогать Postgres, если URL передан вами. Для базы, которую
   раннер вывел из `-TaskSlug` сам, флаг ставит он. CI выставляет тот же флаг.
5. ~~Дефолтному unit-tier нельзя подавать `TEST_DATABASE_URL`.~~ Снято 2026-09-23 (017, стадия 2c):
   тир один и идёт только на PostgreSQL; SQLite-URL в этой переменной — отказ до сбора тестов.

## 1. Скачать бинарники

Версию берите из `quality.yml` (сейчас 16). Проверьте доступность конкретной сборки — состав
зеркала меняется:

```bash
for v in 16.9-1 16.8-1 16.6-1 16.4-1; do
  URL="https://get.enterprisedb.com/postgresql/postgresql-$v-windows-x64-binaries.zip"
  echo "$v -> $(curl -s -o /dev/null -w '%{http_code}' -L --max-time 25 -I "$URL")"
done
```

Первая, ответившая `200`, годится. Скачать и распаковать (~300 МБ, распаковка занимает минуты):

```powershell
$tools = "$env:USERPROFILE\tools"
New-Item -ItemType Directory -Force $tools | Out-Null
curl.exe -sSL -o "$tools\pg16.zip" "https://get.enterprisedb.com/postgresql/postgresql-16.9-1-windows-x64-binaries.zip"
Expand-Archive -LiteralPath "$tools\pg16.zip" -DestinationPath "$tools\pg16" -Force
& "$tools\pg16\pgsql\bin\postgres.exe" --version   # ожидается 16.x
```

Контрольную сумму зеркало не публикует рядом с файлом; если нужна проверка целостности — сверяйте
с подписями на `postgresql.org`. Для одноразовой тестовой БД риск принят осознанно.

## 2. Инициализировать кластер

Роль и база берутся **из CI**, чтобы DSN совпадал байт-в-байт: пользователь `geo`, пароль `geo`,
база `geov0_test_ci`.

```powershell
$bin  = "$env:USERPROFILE\tools\pg16\pgsql\bin"
$data = "$env:USERPROFILE\tools\pgdata"
$pw   = "$env:USERPROFILE\tools\.pgpw"
Set-Content -Path $pw -Value "geo" -NoNewline -Encoding ascii
& "$bin\initdb.exe" -D $data -U geo -A scram-sha-256 --pwfile=$pw -E UTF8 --locale=C
Remove-Item $pw -Force
```

`--locale=C` — чтобы сортировка не зависела от локали машины; `-U geo` делает суперпользователем
сразу нужную роль, так что отдельный `CREATE ROLE` не потребуется.

## 3. Запустить сервер — отвязанным процессом

**Это тот шаг, где ошибаются.** Запуск должен вернуть управление, а сервер — пережить оболочку:

```powershell
$bin  = "$env:USERPROFILE\tools\pg16\pgsql\bin"
$data = "$env:USERPROFILE\tools\pgdata"
$log  = "$env:USERPROFILE\tools\pg16.log"
Start-Process -FilePath "$bin\pg_ctl.exe" `
  -ArgumentList @('-D', $data, '-l', $log, '-o', '"-p 5432 -h 127.0.0.1"', 'start') `
  -WindowStyle Hidden
```

Проверка, что сервер жив (а не «команда не упала»):

```powershell
$env:PGPASSWORD = "geo"
& "$bin\psql.exe" -h 127.0.0.1 -p 5432 -U geo -d postgres -tAc "SELECT version();"
```

Остановка: `& "$bin\pg_ctl.exe" -D $data stop -m fast`.

Если после перезагрузки машины сервер не поднят — повторите только этот шаг, кластер сохраняется.

## 4. Создать базу и накатить схему

Схему накатывайте **каноническим entrypoint**, а не голым `alembic upgrade`: CI использует именно
его, и расхождение «локально прошло, на CI упало» рождается на этой развилке.

```bash
export PGPASSWORD=geo
BIN="$USERPROFILE/tools/pg16/pgsql/bin"
"$BIN/createdb.exe" -h 127.0.0.1 -p 5432 -U geo geov0_test_ci

cd /path/to/GEOv0
export DATABASE_URL="postgresql+asyncpg://geo:geo@127.0.0.1:5432/geov0_test_ci"
export ENV=test
python scripts/check_alembic_heads.py      # голова обязана быть единственной
bash docker/docker-entrypoint.sh true      # применяет миграции
```

## 5. Прогнать тесты

```powershell
$env:TEST_DATABASE_URL       = "postgresql+asyncpg://geo:geo@127.0.0.1:5432/geov0_test_ci"
$env:GEO_TEST_ALLOW_DB_RESET = "1"
.\scripts\verify_local.ps1 -TaskSlug <ваш_слаг> -BackendOnly
```

Без `TEST_DATABASE_URL` раннер сам выводит `geov0_test_<ваш_слаг>` на `127.0.0.1:5432` и тир
создаёт эту базу; явный URL, как выше, нужен только для базы, выбранной вами.

Гейт печатает `Test database guard passed (backend=postgresql, database='geov0_test_ci')` — это и
есть подтверждение, что прогон шёл против Postgres, а не против SQLite. **Смотрите на эту строку, а
не на «passed»:** зелёный SQLite-прогон легко принять за Postgres-evidence.

Чтобы вернуться к выведенной раннером базе задачи, переменные снимите:

```powershell
Remove-Item Env:TEST_DATABASE_URL, Env:GEO_TEST_ALLOW_DB_RESET -ErrorAction SilentlyContinue
```

## 6. Параллельные агенты

`AGENTS.md` §7 запрещает делить изменяемую БД. Каждому агенту — своя база, имя от его слага:

```bash
"$BIN/createdb.exe" -h 127.0.0.1 -p 5432 -U geo "geov0_test_$TASK_SLUG"
```

и соответствующий `TEST_DATABASE_URL`. Кластер при этом общий — это допустимо, разделены базы.
После работы: `"$BIN/dropdb.exe" -h 127.0.0.1 -p 5432 -U geo "geov0_test_$TASK_SLUG"`.

### Уборка тестовых баз

Каждый слаг оставляет на сервере базу тира `geov0_test_<слаг>` и шаблоны `geov0_test_<слаг>__…tpl`.
Прогон убирает только осиротевшие базы **своего** слага, поэтому базы слагов, которые больше не
запускаются, копятся (на одной машине 2026-10-10 насчитана 551 база в 243 семействах, около 5,5 ГБ).
Автоматической уборки нет и не будет (решение 2026-10-10, `AGENTS.md` §12): сервер общий, а
**отсутствие соединений не доказывает, что соседняя задача отпустила свою базу или шаблон** — между
двумя прогонами сессия не держит ни одного. Времени создания и последнего использования в каталоге
PostgreSQL нет, поэтому правила «не использовалась N часов» тоже нет.

Место возвращает команда `scripts/cleanup_test_databases.py`. Сначала — что она делает, затем
процедура разовой уборки, без которой команду применять нельзя.

**Чего команда не знает, и никакая её проверка этого не заменяет:** закончена ли задача и отпустила
ли она свои базы. Владелец базы — роль `geo` — одинаков у всех параллельных задач, поэтому
«владелец совпал» исключает только базы другой роли. Каждая строка `DROP` — предложение, которому
нужно подтверждение от того, кто вёл задачу. И ещё одно: **локальный хост — не значит одноразовый
сервер.** Команда отказывается работать с нелокальным адресом, но локальным может оказаться и
туннель, и настоящая база. Смотрите на адрес и на идентификатор сервера в сводке.

**1. Инвентарь (dry-run, по умолчанию).** Только чтение каталога; ничего не меняет.

```powershell
$env:TEST_DATABASE_URL = "postgresql+asyncpg://geo:geo@127.0.0.1:5432/geov0_test_any"   # берутся хост и учётка
.\.venv\Scripts\python.exe scripts\cleanup_test_databases.py `
  --manifest .local-run\db-cleanup\manifest.json --protect <живой_слаг> --protect <ещё_один>
```

Команда пишет манифест (JSON) и печатает сводку. По каждой базе в манифесте: точное имя, OID,
владелец, размер, флаг шаблона, число соединений, семейство (слаг), вид (база тира / шаблон / клон) и
предложенное решение с причиной. Шаблон узнаётся по именованию провизионирования — суффикс после
`__` оканчивается на `tpl` (`tpl`, `modebtpl`, `<стадия>tpl`): флаг `datistemplate` провизионирование
не ставит, а базу с таким флагом команда не трогает вовсе. Вид определяет только порядок удаления.
Решения:

- `DROP` — **полное** имя базы соответствует грамматике `geov0_test_<слаг>` или
  `geov0_test_<слаг>__<суффикс>` и больше ничего не содержит (ни `?`, ни кавычки, ни пробела), проходит
  ту же проверку имён, что и раннер (`scripts/validate_test_database_url.py`), база не помечена
  шаблоном в каталоге, владелец — роль, под которой идёт команда, семейство не защищено, и ни у одной
  базы семейства нет соединения;
- `VERIFY-FIRST` — в семействе есть соединение (держит всё семейство, включая отключённый шаблон);
- `KEEP` — всё остальное: имя вне грамматики, чужой владелец, защищённое семейство, база с флагом
  шаблона.

`--protect <слаг>` защищает семейство целиком. Слаг проверяется; строка, которая слагом не является,
— отказ.

**2. Просмотр манифеста.** Строку, которую удалять нельзя, исправьте на `KEEP` или уберите. Обратное
**возможно**: строка другой задачи той же роли, вписанная в манифест с верным описанием или
исправленная с `VERIFY-FIRST` на `DROP`, будет удалена, как только у семейства не станет соединений.
Команда доверяет манифесту как просмотренному; подлинность и факт просмотра она не проверяет.
Не пройдёт только то, что расходится с каталогом или с грамматикой имён.

**3. Применение — в окно обслуживания.**

```powershell
.\.venv\Scripts\python.exe scripts\cleanup_test_databases.py `
  --apply .local-run\db-cleanup\manifest.json --maintenance-window-confirmed `
  --protect <живой_слаг> --expect-drop-count <число_строк_DROP>
```

Применение требует четырёх заявлений оператора, и без любого из них отказывает до соединения:

- `--maintenance-window-confirmed` — окно согласовано: **все сессии, использующие сервер, закончили
  или приостановили работу с базой и не запускают тесты до конца уборки.** Это заявление, а не
  блокировка: команда его не проверяет. Чужие сессии не рвём — договариваемся;
- объявление защиты: `--protect <слаг>` хотя бы один раз **либо** `--protect-none` — явное «защищать
  некого» (оба сразу — отказ). Пауза задачи не освобождает её базы, поэтому молчание не принимается.
  Действует объединение списка из манифеста и списка из командной строки;
- `--expect-drop-count N` — число просмотренных строк `DROP`. Команда печатает пересчитанный список
  (вид, имя, OID, размер) и отказывает, если строк не `N`;
- манифест не старше 60 минут. Это свежесть **манифеста** — просмотра, который он фиксирует, — а не
  возраст какой-либо базы. Проверяется только поле `created_at`; от правки манифеста после просмотра
  оно не защищает — для этого хеш просмотренного манифеста сверяется непосредственно перед
  применением (шаг 6 процедуры).

Манифест читается и проверяется целиком **до** соединения с сервером. Затем, до первого удаления,
**каждая** строка `DROP` сверяется с каталогом — сервер, имя, OID, владелец, вид, защита, — и ни у
одного **незащищённого** тестового семейства на сервере не должно быть соединений, включая семейства,
которых нет среди строк. После этого базы удаляются по порядку — клоны, шаблоны, базы тира, — и
перед каждой сверка повторяется. При любом расхождении команда **останавливается**: не пропускает и
не идёт дальше.

Единственный изменяющий оператор команды — `DROP DATABASE "<имя>"`: без `WITH (FORCE)`, без
`pg_terminate_backend`, без `ALTER DATABASE`, без `drop_database()` из `tests/migrated_schema.py` (тот
сначала рвёт соединения). Имя экранируется независимо от проверки. При живом соединении с этой базой
удаление отвергает сам сервер, и это тоже остановка.

Файл результата `*.result.json` рядом с манифестом пишется, когда применение дошло до сервера:
удалённые базы, причина остановки и — если оператор ушёл на сервер, а ответа о нём не пришло — имя
базы с **неизвестным** исходом (она никогда не записывается как удалённая). «Сервер отказал»
пишется только для настоящего ответа сервера о том, что оператор не выполнен (база занята, нет прав,
базы нет); обрыв соединения, остановка сервера, отмена, таймаут — это «неизвестно», хотя драйвер и
называет часть из них ошибками PostgreSQL. **После любого прерывания сверяйте с каталогом каждый
предпринятый `DROP`, независимо от поля `uncertain`.** Если отказ случился до соединения или сервер
не удалось прочитать до первого удаления, файла результата нет. Коды выхода: `0` — всё по манифесту
удалено; `1` — отказ или остановка применения; `2` — неверные аргументы, непригодный манифест,
недоступный или нечитаемый сервер (в том числе роль без права читать `pg_control_system()`).

Чего команда не видит: закончена ли задача; сессию, которая подключилась к **другой** базе того же
семейства в промежутке между последней сверкой и удалением; отладочные данные, которые кто-то хотел
сохранить. Остаточный риск, который держит только окно обслуживания: база, удалённая и созданная
заново под тем же именем **после** последней сверки OID, — команда удалит новую.

#### Процедура разовой уборки

1. **Принадлежность и освобождение.** От каждой сессии, работавшей с сервером, — явный список всех её
   слагов, включая повторы и вспомогательных агентов. От живого соседа — его список защищаемых слагов
   и подтверждение окна. Слитая ветка подтверждает, что работа над кодом закончена, но не что база
   больше не нужна. Неизвестное и спорное — защищать.
2. **Пауза работы с базой во всех сессиях.** Соединения не рвём. Запишите договорённость, адрес и
   идентификатор сервера.
3. **Замер «до»** — тем же чекаутом, интерпретатором, селектором и **одним выделенным слагом**, который
   защищён (`--protect`), чтобы уборка не превратила второй замер в холодный старт:
   `PYTEST_ADDOPTS="--durations=0 --durations-min=0"`, затем
   `.\scripts\verify_local.ps1 -TaskSlug db_cleanup_measure -BackendOnly`. Вывод, код выхода, число
   выбранных тестов, длительности setup/call/teardown — в `.local-run\db-cleanup\…`. Переменную после
   замера верните.
4. **Свежий манифест после замера**, со всеми защищаемыми слагами. Прежние инвентари — исторический
   ввод, а не цель удаления.
5. **Просмотр каждой строки `DROP`**: подтверждение освобождения, точное имя и OID, владелец, вид,
   размер. Неизвестное — в `KEEP` или убрать. Сырой инвентарь и итоговый манифест хранятся отдельно;
   запишите хеш итогового (`Get-FileHash`). После просмотра новых строк `DROP` не добавлять.
6. **Одно применение в том же окне.** Непосредственно перед ним ещё раз снимите хеш манифеста и
   сверьте с записанным на шаге 5: команда этого не делает. Затем: итоговый манифест, подтверждение
   окна, список защиты ещё раз, число строк. При остановке защиту не ослаблять и автоматически не
   повторять: сначала сверить с каталогом каждый предпринятый `DROP` и разобрать частичный результат,
   затем делать новый манифест.
7. **Сверка до возобновления работы**: каталог после — против утверждённого набора; OID защищённых и
   не вошедших в манифест баз на месте. Запишите файл результата, код выхода, фактические удаления и
   возвращённый объём. Удалённую базу не восстановить.
8. **Замер «после»** — той же командой и при той же фоновой нагрузке. Сравнивайте общие тесты по
   фазам отдельно. Число баз изменилось — это факт; выигрыш во времени утверждается только в той мере,
   в какой его показывают замеры.

## 7. Перенос на другую машину

Переносится только процедура, не данные. На новой машине: §1 → §2 → §3 → §4, порядка десяти минут,
из них большая часть — скачивание и распаковка. Каталог `pgdata` копировать между машинами не
нужно и не рекомендуется: база одноразовая, а несовпадение версии или локали даст отказ запуска.

## 8. Базы лаунчера (`geov0_dev_*`)

Тестовые базы — `geov0_test_<слаг>`, базы лаунчера — `geov0_dev_<слаг>`. Кластер общий, разделены
базы; это два разных пространства имён, и сброс одного никогда не достаёт до другого.

Лаунчер создаёт свою базу сам, накатывает миграции каноническим входом и сеет рецептом сообщества:

```powershell
.\scripts\run_local.ps1 start                    # geov0_dev_local
.\scripts\run_local.ps1 start -DbSlug p017t1710  # своя база параллельного агента
.\scripts\run_local.ps1 check-db                 # схема, популяция, baseline
.\scripts\run_local.ps1 reset-db                 # только своя база, только после остановки процессов
```

Границу задаёт один владелец — `scripts/dev_database.py`. Имя обязано матчить
`^geov0_dev_[A-Za-z0-9_-]+$` без сдвоенного подчёркивания, хост обязан быть петлевым, иначе отказ;
флага, который это переопределяет, нет. Сам `DROP DATABASE` идёт **без** `WITH (FORCE)`, поэтому при
живом соединении его отвергает сервер, а не только скрипт.

Проверка готовности сверяет популяцию с таблицей `ref → PID`, которую пишет сид. Сид пишет её **одну
на сообщество** и перезаписывает следующим прогоном того же сообщества, поэтому каждая база сразу
после своего сида забирает собственную копию в `.local-run/dev-databases/<имя базы>/`
(`dev_database.py adopt`), и `ready` читает только её. Без этого прогон e2e админки на своей
одноразовой базе делал бы базу лаунчера «неготовой» — воспроизведено 2026-09-23.

Пароль берётся из `GEO_DEV_PG_PASSWORD` (по умолчанию `geo`), хост и порт — из `-PgHost` / `-PgPort`.
URL передаётся скриптам переменной окружения, а не аргументом, чтобы пароль не попадал в список
процессов и в лог (`AGENTS.md` §12).

Убрать свою базу после работы:

```powershell
$env:DATABASE_URL = "postgresql+asyncpg://geo:geo@127.0.0.1:5432/geov0_dev_<слаг>"
.\.venv\Scripts\python.exe scripts\dev_database.py drop
```

## 9. Где стоит сам PostgreSQL — и почему не в папке проекта

§1–§3 ставят бинарники и кластер в `%USERPROFILE%\tools`, то есть **вне папки проекта**, тогда как
правило владельца от 2026-09-21 (`AGENTS.md` §7) говорит «никаких каталогов вне папки проекта».
Расхождение названо здесь намеренно, а не сглажено.

Правило писалось про **рабочие каталоги агента** — worktree, клоны для ревью, артефакты прогонов:
всё, что относится к задаче и должно уехать вместе с ней. Переносимый PostgreSQL к этому классу не
относится: это инструмент машины, ровесник `node` и Python, общий для всех веток и всех задач, и
переживающий любую из них. Каталог остаётся там по трём причинам, каждая проверяемая:

1. **Кластер общий по построению.** §6 и §8 делят его между параллельными агентами; внутри одного
   worktree он был бы недоступен соседнему, и каждый агент поднимал бы свой — минуты на распаковку и
   ~300 МБ на задачу.
2. **Данные кластера не должны попадать в дерево.** `pgdata` — изменяемая база; `AGENTS.md` §12
   держит runtime под `.local-run/`, а гард
   `tooling-tests/portable/test_p014_t1406_no_mutable_database_in_the_working_tree.py` существует именно потому,
   что база в рабочем дереве уже однажды туда попала.
3. **Снос worktree не должен сносить кластер.** Удаление задачи — обычная операция; потеря кластера
   вместе с ней превращала бы её в переустановку.

Если владелец решит иначе, менять придётся §1–§3 и `$data`, а не лаунчер: он знает только
`host:port`, и куда установлен сервер, его не касается.

## Что этот документ не покрывает

Продовое развёртывание (см. [`05-deployment.md`](../05-deployment.md)), настройку под нагрузку,
резервное копирование, TLS и доступ по сети: кластер слушает только `127.0.0.1` и предназначен
исключительно для одноразовых тестовых баз.
