## 1. Общее описание

### 1.1. Что это такое

**Игровой интерфейс симулятора GEO** — это визуальная надстройка над существующей системой GEO (децентрализованной кредитной сети), созданная для:
- Наглядной демонстрации сетевой структуры доверия
- Визуализации механизма клиринга (автоматического взаимозачёта долгов)
- Создания эффекта погружения через метафору "космической карты"

### 1.2. Зачем это нужно

**Проблема:** Табличные интерфейсы и графы в админке не передают динамику и "живость" системы доверия.

**Решение:** Тактический экран в стиле космических стратегий (EVE Online, Stellaris), где:
- **Участники** = звёздные системы (узлы графа)
- **Линии доверия** = гравитационные связи
- **Клиринг** = энергетический разряд, "замыкающий" цепь долгов

**Целевая аудитория:**
1. **Администраторы** — мониторинг состояния сети
2. **Демонстрации** — презентации для инвесторов и партнёров
3. **Обучение** — наглядное объяснение механики системы новым пользователям

## 2. Цели и задачи

### 2.1. Основные цели

| Цель | Описание |
|------|----------|
| **Визуализация графа доверия** | Отображение 50-100+ участников и их связей в режиме реального времени |
| **Демонстрация клиринга** | Анимация процесса взаимозачёта долгов с визуальными эффектами |
| **Иммерсивность** | Создание "Wow-эффекта" через звук, свет, частицы |
| **Производительность** | Плавная работа (60 FPS) даже на средних устройствах |

### 2.2. Функциональные задачи

1. **Отображение участников**
   - Визуальное различие типов (бизнес/физлицо)
   - Цветовая индикация состояния (активный/неактивный/в сделке)
  - Размер узла задаётся готовым `viz_size` (семантика на backend/в фикстурах)

2. **Интерактивность**
   - Клик по узлу → фокус камеры + всплывающая карточка с данными
   - Ховер → подсветка связей
   - Зум и панорамирование

3. **Визуализация транзакций**
   - Бегущие частицы вдоль линий при передаче долга
   - Вспышка при успешном клиринге
   - Звуковое сопровождение

4. **Атмосфера**
   - Темный космический фон с частицами-звёздами
   - Неоновая палитра (cyan/emerald/purple)
   - Эффекты свечения (glow) и размытия (blur)

### 4.3. Принципы данных и UX (как мы делали граф в Admin UI)

Цель: визуализация должна быть **детерминированной**, **стабильной** и без тяжёлых вычислений на фронтенде.

1) **Ничего “семантического” не вычислять на фронтенде**
- Фронтенд НЕ считает: net-эффекты, биннинг/перцентили, “кто должник/кредитор”, “какой цвет/размер”.
- Фронтенд только:
  - рисует узлы/линии,
  - применяет `viz_*` поля как есть,
  - проигрывает анимации по готовому сценарию от backend.

2) **Дискретные ключи вместо формул и градиентов**
- Вместо “посчитай цвет по величине” используются дискретные ключи: `viz_color_key` (например `person|business|suspended|debt-0..8`).
- Это снижает сложность, упрощает кэширование и убирает расхождения между режимами (fixtures/real).

3) **Progressive disclosure: показывать меньше, но точнее**
- В режиме “Обзор” связи не должны превращаться в “шерсть”: линии тонкие и спокойные.
- Детали раскрываются:
  - при выборе узла (локальная окрестность),
  - при транзакции/клиринге (подсветка только участвующих рёбер).

4) **Камера и раскладка: предсказуемость важнее “эффектности”**
- UI-оверлеи (карточка, панель истории) не должны заставлять граф постоянно “прыгать”.
- Перецентровка/fit делается только:
  - по явному действию пользователя (например кнопка “Center”), либо
  - если панель перекрывает выбранный объект.

### 4.4. Производительность и защита от перегруза (обязательные требования)

**Бюджет кадра:** целимся в 60 FPS (≈16.7ms), деградируем плавно.

Ограничители:
- **Nodes:** целевой режим 50–150, допустимый пик 300 (с деградацией LOD).
- **Links:** в Overview рендерим все, но с LOD; в Focus “ярко” только окрестность.
- **Particles:** не более 200–400 одновременно (иначе быстро растёт стоимость draw).
- **Текст/лейблы:** по умолчанию только выбранный узел и соседи; глобальные подписи — отдельный тумблер.
- **Частота обновлений:** не дергать `.graphData()` чаще, чем нужно; анимации делать через accessors + `Graph.refresh()`.

Стратегии LOD:
- Малый зум: тонкие линии, низкая альфа, без подписей, без дорогих эффектов.
- Средний зум: подсветка окрестности выбранного узла.
- Большой зум: можно включать подписи и умеренный glow.

## 5. Архитектура

Цель раздела: зафиксировать границы ответственности и базовые слои так, чтобы не повторять ошибки «первой демки» (недетерминизм, смешение данных/рендера/эффектов и вычисление семантики на клиенте).

### 5.1. Принципы (обязательные)

1) **Fixture/API parity**
- UI должен одинаково работать от:
  - реального API (snapshot + события),
  - демо-фикстур (static snapshot + плейлист событий).

2) **Семантика визуализации приходит готовой**
- Клиент не вычисляет: классы должников, квантили, ранги, «кто должник/кредитор», цвет/размер/толщину/альфу.
- Клиент применяет `viz_*` как есть и проигрывает сценарии.

3) **Детерминизм**
- В runtime запрещён `Math.random()` для решений, влияющих на смысл и воспроизводимость.
- Если нужен «живой» эффект (дыхание/лёгкое мерцание) — он:
  - визуально мягкий,
  - не меняет смысл (не перекрашивает и не пересайзит семантику),
  - предпочтительно задаётся предвычисленными параметрами или seeded PRNG.

4) **Fail-fast по данным**
- При ошибке загрузки/валидации — показываем понятную ошибку, а не «тихо» генерируем случайный граф.

### 5.2. Слои визуализации (стабильный порядок)

1) **Фон** (звёздная пыль/туманность) — отдельный слой.
2) **Базовый граф** (Canvas/WebGL):
   - фоновые рёбра,
   - узлы,
   - опционально мягкое свечение (glow/bloom).
   Важно: **знак баланса кодируется цветом самого узла, не внешним свечением.**
3) **FX overlay** (второй canvas поверх графа):
   - искры транзакций,
   - клиринг по маршруту/циклу,
   - вспышки/кольца.
4) **HUD (HTML overlay)**:
   - карточка узла,
   - управляющие кнопки,
   - (опционально) debug overlay (FPS/particles).

### 5.3. Поток данных (snapshot → render → events)

1) Источник снапшота: API или fixtures (один и тот же контракт).
2) Валидация структуры снапшота/событий на входе.
3) Базовый граф обновляется редко (смена эквивалента/сцены/снапшота).
4) События `tx.*`/`clearing.*` должны работать как «оверлеи»:
   - не пересобирать весь граф на каждый шаг,
   - использовать accessors и `refresh()` для минимальных изменений отображения,
   - временные эффекты рисовать в FX overlay.

### 5.4. Границы ответственности (что где считается)

- Backend/офлайн-генератор:
  - `viz_color_key`, `viz_size`, `viz_width_key`, `viz_alpha_key` и любые классы/квантили.
  - подготовка плейлистов событий (сценарии tx/clearing).
  - политика отображения статусов (`suspended/left/deleted`): скрывать/показывать/стилизовать — решается данными, не фронтом.
- Клиент:
  - физика/раскладка (если используем force layout),
  - отрисовка, LOD, камера,
  - проигрывание событий (тайминг, эффекты),
  - но не «финансовая семантика».

### 5.5. Анти-паттерны (ошибки первой демки — не повторять)

1) Монолитный компонент, который одновременно грузит данные, крутит физику, рисует, обрабатывает ввод и эффекты.
2) Скрытый недетерминизм (рандом в рантайме, «мигания», случайная генерация графа при ошибках).
3) Семантические вычисления на фронтенде (цвет/размер/классы должников/квантили).
4) Частые полные пересборки графа на клик/шаг событий вместо `refresh()` и оверлеев.

### 6.2. Компонент №1: Граф (`force-graph`)

**Задача:** Отрисовка узлов и связей с физической симуляцией.

#### Почему не `react-force-graph-2d`?
- Основной стек проекта — **Vue.js 3**
- `react-force-graph-2d` — это React-обертка над библиотекой `force-graph`
- Использование React внутри Vue-проекта раздует бандл и создаст конфликты зависимостей
- **Решение:** Использовать нативную библиотеку `force-graph` (Vanilla JS) напрямую

#### Как это работает

```typescript
import ForceGraph from 'force-graph';

// В хуке onMounted:
const Graph = ForceGraph()
  (graphContainer.value) // Привязываем к div
  .graphData(data)       // Передаём { nodes: [], links: [] }
  .nodeCanvasObject((node, ctx, globalScale) => {
    // Важно: цвет/размер приходят готовыми с backend как viz_* поля.
    // UI только применяет эти ключи (без вычислений/градиентов на фронте).
    const colorKey = String((node as any).viz_color_key || node.type || 'person').toLowerCase();
    const size = (node as any).viz_size || { w: 12, h: 12 };
    const w = Math.max(6, Number(size.w) || 12);
    const h = Math.max(6, Number(size.h) || 12);

    const palette: Record<string, string> = {
      business: '#10b981', // emerald
      person: '#3b82f6',   // blue
      suspended: '#94a3b8',
      left: '#64748b',
      deleted: '#475569',
    };

    // Должники могут быть дискретно раскрашены (debt-0..8) — ключи задаёт backend.
    const fill = palette[colorKey] || (colorKey.startsWith('debt-') ? '#f59e0b' : '#3b82f6');
    ctx.fillStyle = fill;

    // Кастомная отрисовка
    if (node.type === 'business') {
      // 🟩 Рисуем КВАДРАТ
      ctx.fillRect(node.x - w / 2, node.y - h / 2, w, h);
    } else {
      // 🔵 Рисуем КРУГ
      ctx.beginPath();
      ctx.arc(node.x, node.y, Math.min(w, h) / 2, 0, 2 * Math.PI);
      ctx.fill();
    }
  })
  .linkWidth(link => link.selected ? 2 : 0) // Скрываем неактивные
  .linkColor(link => link.selected ? '#22d3ee' : '#64748b33')
  .onNodeClick(node => {
    store.selectNode(node); // Обновляем состояние через Pinia
  });
```

#### Доработка спецификации под производительность и “не перегружать экран”

Вместо бинарного `selected` вводим режимы визуализации + LOD (уровни детализации):

**Режимы:**
- `Overview` (по умолчанию):
  - узлы видны все;
  - связи — тонкие и спокойные (низкая альфа), чтобы читалась “структура”, но не было шума;
  - подписи выключены.
- `Focus` (выбор узла):
  - ярко рисуются только связи выбранного узла и ближайших соседей;
  - “фоновые” связи либо скрыты, либо почти прозрачные.
- `Clearing` (на время клиринга):
  - отображаются только участники и рёбра, задействованные в сценарии клиринга;
  - на фоне можно оставить еле заметный силуэт сети (опционально).

**LOD по зуму/нагрузке:**
- малый зум: тонкие линии, минимум эффектов, без текста;
- средний: подсветка окрестности + умеренный glow;
- большой: подписи (ограниченно) и дополнительные детали.

Критически важно: правила цвета/размера/толщины задаются не формулами на клиенте, а ключами `viz_*`.

#### Логика связей (Фильтрация)

```javascript
// По умолчанию все связи невидимы
links.forEach(link => link.selected = false);

// При клике на узел
function selectNode(nodeId) {
  links.forEach(link => {
    // Показываем только связи выбранного узла
    link.selected = (link.source.id === nodeId || link.target.id === nodeId);
  });
  Graph.graphData({ nodes, links }); // Перерисовываем
}
```

Доработка: вместо полной пересборки графа на каждый клик (что может быть дорого), рекомендовано:
- хранить `mode` и `selectedNodeId` в Pinia;
- менять только видимость/параметры через accessors (`linkWidth`, `linkColor`, `linkDirectionalParticles`) и вызывать `Graph.refresh()`.

### 6.4. Компонент №3: Анимация транзакций

**Задача:** Визуализировать движение денег по связям.

Обязательное уточнение (важно для протокола GEO и чтобы не «запереть» UI в тупик):
- транзакция может идти **по маршруту из нескольких рёбер** (multi-hop), поэтому визуальная метафора должна поддерживать список рёбер/узлов маршрута;
- клиринг — это **цикл долгов** (обычно 3+ узла, иногда 4–6+), поэтому эффекты должны уметь подсветить/проиграть цикл целиком, а не только один сегмент.

## 9. Принципы данных и производительности (как Admin UI)

### 8.1. Правило “визуальные поля приходят готовыми”

Чтобы избежать расхождений и просадок FPS:
- backend/офлайн-генератор вычисляет всё, что связано с:
  - балансом/долгом,
  - классами цвета,
  - масштабами размера,
  - приоритетами подсветки,
  - бинами/перцентилями.

Фронтенд применяет только:
- `viz_color_key` → палитра/паттерн,
- `viz_size` → размер примитива,
- `viz_*_key` для линий → ширина/альфа/цвет,
- события → анимация.

### 8.2. Анти-перегруз интерфейса

По умолчанию на экране одновременно:
- видны **без подписей** все узлы;
- активные связи (окрестность выделенного узла / событие) — заметные;
- остальные связи — “фоновые” (тонкие + низкая альфа), либо скрыты при сильном отдалении.

### 8.3. Деградация качества без лагов

При росте нагрузки снижать (в таком порядке):
1) число видимых рёбер (по LOD),
2) число частиц,
3) glow/blur,
4) подписи.

## 10. Контракт API для состояния, транзакций и клиринга

**Источник правды:** см. [docs/ru/simulator/frontend/docs/api.md](../../../../../simulator/frontend/docs/api.md).

Коротко:
- Snapshot возвращает узлы/рёбра и готовые `viz_*` ключи (цвет/размер/альфа/ширина).
- Поток событий (SSE) отдаёт `tx.*` и `clearing.*` как готовые к анимации сценарии.
- Клиент не пересобирает граф на каждое событие: только overlays + `refresh()`.
