# Runbook: удержание целостности эквивалента и восстановление согласованности

```text
Статус: Stable
Область: core
Последнее обновление: 2026-10-18
```

Решение владельца 2026-10-05 (В3, программа 030, `F-030-14`): «Ошибки в долгах на реальной работе проекта быть не
должно… Если сейчас ошибка — перезасеять или исправить прямо в базе для консистентности базы». Механизма «принять
расхождение как есть» нет и не будет. Этот документ — процедура; нового механизма за ним нет.

## 1. Что означает удержание

Сверка долгов идёт в цикле целостности (`app/core/maintenance_jobs.py`) при старте процесса и затем через
`INTEGRITY_CHECKPOINT_INTERVAL_SECONDS`, по умолчанию раз в сутки (программа 047); по требованию — командой
`scripts/reconcile_debts.py` (§3); ошибка контрольных точек сверку не отменяет — обе записываются
(`app/core/maintenance_jobs.py:102`, 030 `F-030-7`). Сверка одного эквивалента
(`verify_journal_equals_change`, `app/core/ledger/reconciliation.py:969`) проверяет:

- (а) текущие долги равны baseline плюс сумма журнала;
- (б) каждая записанная операция равна пересчёту своего объявленного намерения; денежный `INJECT` с 030 S3 не
  поддерживается и даёт `FAILED`;
- **соответствие «транзакция ↔ операция»** (`_correspondence`, `reconciliation.py:903`; 030 `F-030-5`): у каждой
  `COMMITTED`-транзакции `PAYMENT`/`CLEARING` есть своя операция, у каждой операции — `COMMITTED`-транзакция;
  `ABORTED`-платёж без операции допустим; любая другая форма строки `transactions` — находка
  `transaction_in_a_shape_no_writer_leaves`;
- **структурные нарушения** (`_structure`, `reconciliation.py:949`; 030 `F-030-20`): встречный долг пары
  (`debt_counter_debt`) и долг без живой линии (`debt_without_a_live_line`). Долг выше **сниженного** лимита
  нарушением не считается (решение 026 В3).

Каждое из этих оснований само по себе делает результат `FAILED`. `FAILED` ставит **удержание** на этот эквивалент
(`equivalents.integrity_hold_result_id`) в той же транзакции, что и публикует результат, без повторного прогона
(fail-closed с 2026-10-19, 047 `T4704`); сохранённый `FAILED` без удержания удерживается следующим прогоном без
проверки. Платежи, клиринг и денежные записи симулятора в эквиваленте отказываются, остальные эквиваленты работают.
Удержание возможно и на эквиваленте, исправленном уже после публикации его `FAILED`; снимается оно так же — §3.

Чем удержание **не** является: ошибка самой сверки, отсутствие результата, `UNVERIFIABLE` и устаревший результат
удержания не ставят — они видны как `warning` в `GET /api/v1/integrity/summary` и `GET /api/v1/integrity/status` с
причиной в `alerts` (`_reconciliation_view`, `app/api/v1/integrity.py:110`; 030 `F-030-8`): нет результата; результат
старше порога свежести (`result_freshness_threshold`, 2 × интервал + 5 мин, по умолчанию 48 ч 5 мин); контрольная точка эквивалента новее его
результата больше чем на допуск прогона (последняя сверка не опубликовала результат). Известное окно: другой воркер
или перезапущенный процесс может отвечать `healthy` до порога свежести ([`specs/BACKLOG.md`](../../specs/BACKLOG.md), раздел «Принято программой 031»,
пункт 9). Деньги предупреждения не останавливают.

**Прогон, который не может закончиться** (047, 2026-10-18): ожидание блокировки или запрос сверки дольше
`INTEGRITY_DB_LOCK_TIMEOUT_MS` / `INTEGRITY_DB_STATEMENT_TIMEOUT_MS` — ошибка только этого эквивалента (SQLSTATE `55P03`
/ `57014` в записи лога `debt_reconciliation.error`), следующие эквиваленты сверяются в том же прогоне; попытка целиком
дольше `INTEGRITY_ATTEMPT_TIMEOUT_SECONDS` или ВЗЯТИЕ замка Redis дольше `INTEGRITY_REDIS_CALL_TIMEOUT_SECONDS` — задание
`integrity` в состоянии `failed` с событием `<reason>_timed_out` (`/health` — `degraded`). Ни то ни другое не
результат и не удержание. Иначе с ОСВОБОЖДЕНИЕМ замка (исправлено 2026-10-19 по §15-ревью Codex): если освобождение
не ответило в срок, завершённая проверка остаётся завершённой, в лог пишется `lock.release_uncertain`, а ключ
истекает по TTL. Повторяющийся `_timed_out` на выросшей истории — поднять `INTEGRITY_ATTEMPT_TIMEOUT_SECONDS`
по замеру длительности прогона (`app/config.py`), а не выключать цикл.

Как увидеть: `summary` — `status: critical`, `hold: true`; `status` (админ) — alert `Integrity hold on <CODE>` с
`hold_result_id` и находки последнего результата.

## 2. Как восстановить согласованность

Не делать: обнулять `integrity_hold_result_id` вручную (нет аудита, и следующий `FAILED` поставит его
снова), округлять долги, выключать цикл целостности (`INTEGRITY_CHECKPOINT_ENABLED=false` отключает обнаружение для
всех эквивалентов и причину не снимает).

**Демо- и dev-база — пересев.** База создаётся заново реальными операциями по рецепту:

```powershell
.\scripts\run_local.ps1 reset-db
```

Рецепт сам создаёт эквиваленты через `POST /admin/equivalents` (строка и baseline одной транзакцией) до первого
платежа. Удержание после пересева не переносится: база новая.

**Рабочая база — исправление прямо в базе.** Только на остановленных писателях (хаб остановлен или эквивалент
заморожен), одной транзакцией обслуживания, по находкам последнего результата (`detail` в
`debt_reconciliation_results`):

1. Критерий (а) — долг расходится с журналом: привести строку `debts` к значению, которое объясняет журнал. Прямая
   запись в `debts` вне операции отказывается триггерами защиты журнала (`GE001`), поэтому правка идёт с
   отключёнными триггерами: `BEGIN; SET LOCAL session_replication_role = replica; …правка…; COMMIT;` — и сразу
   проверяется. Именно `SET LOCAL`, а не `SET`: `SET LOCAL` действует до конца транзакции, а обычный `SET` остаётся
   в сессии и после `COMMIT`, и следующая запись того же соединения тоже пройдёт мимо триггеров защиты журнала и
   внешних ключей (так же устроен помощник стендов порчи `tests/ledger_corruption.py`).
2. Критерий (б) — запись операции расходится с её намерением: записи журнала и конверты неизменяемы, новый baseline
   их не исправляет (критерий (б) смотрит всю историю). Для демо — только пересев; для рабочей базы — исправление
   записи с отключёнными триггерами по согласованию с владельцем.
3. Если исправленные долги журнал не объясняет и это принято владельцем как верные значения — **новый baseline**:
   удалить старый (`DELETE FROM debt_reconciliation_baseline_offsets WHERE equivalent_id = …`, затем
   `DELETE FROM debt_reconciliation_baselines WHERE equivalent_id = …`) и взять заново:

   ```powershell
   .\.venv\Scripts\python.exe scripts\take_reconciliation_baseline.py --equivalent <CODE>
   ```

   Baseline принимает необъяснённое смещение и ничего не удостоверяет — поэтому он берётся только после правки
   данных, а не вместо неё.

### Случай «в базе долги мельче шага» → пересев

Решение владельца В2 (2026-10-05): база с долгами, не кратными шагу эквивалента (`10^-precision`), кодом не
чинится — она пересеивается. **Сам пересев ничем не сигнализирует.** Действует страж шага клиринга (030
`F-030-1`, стадия S2, слита 2026-10-05): исполнение клиринга с суммой, не кратной шагу, отказывается с причиной
`occurrence_amount_not_in_step` (`app/core/clearing/service.py:1742`), в Interact — `409 CLEARING_REFUSED`. Каждое
плечо платежа тоже проверяется на шаг (`app/core/payments/service.py:1836-1838`). Отказ стража удержания не ставит и
долги не правит: он лишь не даёт клирингу исполнить сумму мельче шага. Найти такие долги заранее — запросом (только
чтение):

```sql
SELECT eq.code, eq.precision, d.debtor_id, d.creditor_id, d.amount
FROM debts d JOIN equivalents eq ON eq.id = d.equivalent_id
WHERE mod(d.amount * power(10::numeric, eq.precision), 1) <> 0
ORDER BY eq.code;
```

Непустой результат на демо-базе — `reset-db`.

## 3. Чем подтверждается и как снимается удержание

1. Новый baseline (если брался, п. 2.3) — вывод `take_reconciliation_baseline.py` с числом смещений.
2. Прогон сверки даёт `PASSED`. Плановый идёт раз в сутки (с 2026-10-18, программа 047), поэтому после правки его
   не ждут, а запускают сразу — та же сверка с той же реакцией, на базе из `DATABASE_URL`:

   ```powershell
   .\.venv\Scripts\python.exe scripts\reconcile_debts.py --equivalent <CODE>
   ```

   Exit `0` — `PASSED`; `1` — `FAILED`/`UNVERIFIABLE`, находки напечатаны (`FAILED` ставит
   удержание, если его ещё нет; сохранённый `FAILED` без удержания команда удерживает без проверки и печатает с пометкой —
   запустите её ещё раз, чтобы проверить); `2` — проверки не было (база недоступна, неизвестный код, ошибка сверки) — это не «всё хорошо».
   В Compose — `docker compose exec app python scripts/reconcile_debts.py --equivalent <CODE>`. После `PASSED` в
   `GET /api/v1/integrity/status` у эквивалента нет alert о `FAILED`, есть `Debt reconciliation PASSED … after the
   integrity hold; an admin may clear it`.
3. Явное снятие с причиной и записью аудита — на экране «Целостность» админки (с 2026-10-07, программа 032 S5):
   эквивалент на удержании отмечен, действие «Снять» спрашивает причину, отказ показан текстом. Тот же маршрут:
   `POST /api/v1/admin/equivalents/{code}/integrity-hold/clear` с `{"reason": "…"}`. Маршрут отказывает (`409`,
   `no_later_passed_reconciliation_result`), если последний результат не `PASSED`, если это результат самого
   удержания, или если **сверка эквивалента, выполненная при снятии под блокировкой его строки, не `PASSED`**
   (030 `F-030-10`: сохранённый `PASSED` может быть старше удержания). Автоматического снятия нет.

Не проверено этим документом: исправление критерия (б) на живой рабочей базе (процедура описана, стендом не
исполнялась).
