## Problem

Экран принят, но три группы замечаний владельца подтверждены кодом: (1) правые края трёх нижних элементов («клиринг: было → стало», «Общий долг», «Показать всю сеть») не совпадают, строка ошибки прогона шире полосы контролов, шапка карточки участника режет имя и бейдж; (2) зритель не понимает по экрану, что происходит в живом прогоне: луч, вспышки и исчезающие суммы не оставляют текстового следа, история показывает только собственные ручные успехи, отказы и автоплатежи — никогда; (3) на экране остаются служебные строки без пользы зрителю: «код запроса», коды состояний в скобках, «неизвестно — UAH» в шапке карточки, номер платежа в результате.

## Решения (советник по поручению владельца, 2026-10-20)

1. **Линия контролов — одна для всех неподвижных краевых групп** (28 px от края экрана в comfortable, из существующих токенов: safe-area + `--ds-ov-inset` + `--ds-hud-bar-px`); содержимое группы выровнено к той же стороне; ширина растёт внутрь экрана. Правый нижний блок — одна колонка, все дети по правому краю, ширина по самому широкому; при 1024 px фраза клиринга переносится между смысловыми частями (сумма с единицей неразрывна). Проверка при числах 49745.90 и 1049745.90. Новых токенов не вводить.
2. **Строка ошибки прогона и Stall** — в той же горизонтальной сетке, что `HudBar` (те же внешние границы, что у контролов).
3. **Шапка карточки участника** — две строки: имя (ellipsis + `title`) и две кнопки; «человек · активен», состояние баланса, баланс с единицей неразрывно. «неизвестно» + «— UAH» → одно сообщение «Баланс не получен» / «Balance unavailable»; нулём не заменять.
4. **История «Последние действия»** — на линии контролов (п. 1).
5. **Лента событий прогона** — существующий `InteractHistoryLog` становится «Событиями сети»: 5 строк; один переключатель «Показывать события» в «Подробнее», по умолчанию выключен, предпочтение сохраняется в хранилище как тема и язык (история не сохраняется). Источник — уже принятые SSE-события после проверки контекста и дедупликации по `event_id`: `tx.updated` → «Анна → Пекарня: 120 UAH»; `tx.failed` → «Анна → Пекарня: платёж не прошёл — <причина словами из словаря 046>», без суммы и без финансового диагноза при неизвестной причине; `clearing.done` → «Клиринг: общий долг уменьшился на X UAH; N кругов», X — разница пары до/после (`debtChange.ts`), не `cleared_amount`; без пары — «Клиринг: N кругов»; `topology.changed` с причиной `trust_drift_growth` → «После клиринга выросли лимиты доверия». Серии за 2-секундное окно сводятся в одну строку «За 2 с: 6 платежей; последний — …» (отдельно платежи и отказы). Пометка «вы» только у достоверно локальных результатов (ручные действия, как сейчас); SSE-платежам она не обещается. Параллельные записи ручных успехов убираются (одна строка на событие). Отдельной паузы ленты нет (043 реш. 3 уже ставит прогон на паузу при ручном действии); смена прогона или эквивалента очищает строки. При выключенном переключателе — как сейчас: 3 строки собственных действий. Без новой панели, polling, фильтров, журнала на сервере.
6. **Тост успеха убрать:** результат уже в окне и в строке истории/ленты. Владелец вправе вернуть одним словом.
7. **С экрана уходят:** видимый «код запроса» (остаётся `data-request-id` и консоль — §12 «несёт» выполнено разметкой; решение владельца 2026-10-20), коды состояний в скобках (`REAL_MODE_TICK_FAILED` → в `title`/консоль), номер платежа из результата в окне (маршрут остаётся).
8. **Тексты пяти состояний** (словарь 046, RU/EN): сбой прогона — «Демо остановилось из-за сбоя. Перезагрузите страницу, чтобы начать новый прогон.» / «The demo stopped because of an error. Reload the page to start a new run.»; потеря потока — «Обновления сети прервались; показанные данные могут быть устаревшими. Перезагрузите страницу.» / «Network updates stopped; the displayed data may be outdated. Reload the page.»; Stall — «Последние платежи не проходят. Попробуйте клиринг или увеличьте лимит нужной линии.» / «Recent payments are not going through. Try clearing or increase the relevant trustline's limit.» (мягче прежнего «лимиты исчерпаны» — детектор причину не доказывает); лимит — «Платёж не прошёл: сейчас доступно не больше {max} {eq}. Уменьшите сумму.» / «Payment declined: at most {max} {eq} is available now. Reduce the amount.»; нет баланса — «Баланс не получен.» / «Balance unavailable.». Показатель «Доступно для платежей» → «Свободно по линиям» / «Free on lines». Краткие определения показателей — в `title` плашек «Подробнее», не новым текстом на экране.
10. **Темп платежей — посетителю, тремя ступенями** (слово владельца 2026-10-20: «темп платежей демо где-то регулируется? чтобы можно было замедлить и смотреть более информативно» → сетка «1 платёж в 3 секунды / 1 в секунду / 3 в секунду»; на оговорку о целых процентах — «да»). Регулятор возвращается посетителю в «Подробнее» одним контролом из трёх ступеней словами: «медленно» = 2 % (1 платёж в 2.5 с), «обычно» = 5 % (1 в секунду), «быстро» = 15 % (3 в секунду); по умолчанию «обычно» (`VISITOR_DEFAULT_INTENSITY_PERCENT` 15 → 5, `useInteractAutoBootstrapRun.ts:16`). Это частичный возврат решения 8 спеки 048 (только темп; сценарий и Старт/Стоп остаются у админа); поле процентов с «Применить» у админа остаётся. **Нижняя ступень требует правки планировщика:** сейчас `target_actions = max(1, int(ACTIONS_PER_TICK_MAX × intensity))` при любом темпе > 0 даёт не меньше одного действия за такт 1 с (`app/core/simulator/real_payment_planner.py:283`); нужен накопитель дробного бюджета между тактами (0.4/такт → действие каждые 2–3 такта), без изменения контракта (`intensity_percent` остаётся integer 0..100, `api/openapi.yaml:7577`) и без новой сущности. Ровно «1 в 3 с» целыми процентами невыразимо (1.67 %) — принято 2.5 с.
9. **Переполнение:** у всех обрезаемых строк (имена, сценарий, фразы ленты) — ellipsis и `title`; суммы с единицей не рвутся.
