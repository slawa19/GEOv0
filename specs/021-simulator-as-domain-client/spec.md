## Problem

1. **Линии доверия пишутся мимо домена в девяти местах.** Сидер — `real_scenario_seeder.py:226` (`TrustLine(...)`); дрейф — Core `UPDATE trust_lines` в росте (`trust_drift_engine.py:324`) и в затухании (`:531`); инжект — `inject_executor.py:688` и `:827` (`TrustLine(...)`), `:915` (статус `frozen`); Interact-действия — `app/api/v1/simulator.py:1117` (`TrustLine(...)`), `:1359` (`tl.limit =`), `:1541` (`tl.status = "closed"`). Действия дублируют предусловия `TrustLineService` (`:1086-1088` называет это прямо: «второй, независимый экземпляр проверки»).
2. **Наблюдаемое расхождение — журнал аудита, а не деньги.** `TrustLineService` пишет строку `IntegrityAuditLog` (`TRUST_LINE_CREATE`/`UPDATE`/`CLOSE`, `service.py:253`, `:409`) и две контрольные точки целостности на каждую операцию; ни один из девяти путей симулятора не пишет ни того, ни другого (`grep IntegrityAuditLog` по блоку действий и модулям сидера, дрейфа и инжекта — ноль совпадений). Линия, созданная через Interact-действие, в журнале аудита не существует.
3. **Причина обхода структурна.** `TrustLineService` проверяет подпись Ed25519 по `participant.public_key` (`service.py:156`, `:349`, `:474`); сидер и инжект дают симулированным участникам `public_key = sha256(pid).hexdigest()` (`real_scenario_seeder.py:121`, `inject_executor.py:581`) — 64 hex-символа, не ключ Ed25519, без приватной половины. Серверного примитива подписи нет (`crypto.py` умеет только проверять, `:11`, и генерировать пару, `:24`).
4. **Второй экземпляр оркестрации.** Тик собран из шести модулей `real_tick_*` (2 050 строк) и порта `_RealRunnerPort` (`real_tick_orchestrator.py:40-74`: 19 атрибутов, 10 методов); драйвер клиринга `real_clearing_engine.py` (773) с собственной лестницей глубины (`:211-222`) и координатор (583), из которого `:176-453` существуют только ради адаптивного режима `adaptive_clearing_policy.py` (429), нигде не включённого (раздел «Решения», п. 1).
5. **Блок `action_*`** — `app/api/v1/simulator.py:977-2322`, 1 346 строк, тень публичного API на 366 строк (`trustlines.py` 87, `payments.py` 138, `clearing.py` 55, `participants.py` 86).

## Current / Intended / Optimal

- **Current.** Платежи тика — через `PaymentService.execute` (внутренний неподписанный путь) в одной `SERIALIZABLE`-транзакции денежной фазы с ограниченным повтором `money_replay.py`; клиринг — собственный драйвер поверх `ClearingService`; инжект долга — через `Book`. Линии доверия пишутся мимо `TrustLineService` в девяти местах, без подписи, без аудита и без контрольных точек. Ключи симулированных участников — `sha256(pid)`. Адаптивный режим клиринга выключен по умолчанию и нигде не включается.
- **Intended.** Решение владельца 2026-09-21: симулятор — клиент домена, новых фич нет; адаптивный режим удаляется (там же, П3). Граница 023: вызывающие клиринга переводит 023(d).
- **Optimal.** Каждая запись линии доверия симулятора — операция `TrustLineService` с настоящей подписью в транзакции вызывающего, с аудитом, как у любого клиента; инжект долга — `Book` (уже); платежи — `PaymentService.execute` (уже); клиринг — общий раннер 023 (после 023(d)). Тик — один модуль, владеющий последовательностью «до-фаза → денежная фаза с повтором → хвост», без порта и координаторов. Статус `frozen` при заморозке участника инжектом — единственная названная запись вне сервиса (протокол §5 не знает операции заморозки линии, `docs/ru/02-protocol-spec.md:313-384`).

## Решения

1. **Адаптивный режим клиринга удаляется.** Решение по П3 принято 2026-09-21 консультацией Codex (`ANSWER-3: ADOPT-WITH-CHANGES`, `ADAPTIVE-POLICY: REMOVE`) в рамках протокола решений владельца от того же дня, где П3 признан техническим (`specs/README.md:254-257`). Основания (перепроверены на `b886fa8`): включается только сырой переменной `SIMULATOR_CLEARING_POLICY=adaptive` (`real_runner_impl.py:176`), её не ставит ни один конфиг, скрипт, CI или сценарий (закомментированный пример — `scripts/run_full_stack.ps1:63`); не виден ни в API, ни в SSE, ни в UI (F-021-18); сравнительный тест утверждает только «не хуже static на 15 п.п.» (`test_simulator_adaptive_clearing_effectiveness_ab.py:49-50`) и нигде не исполняется; сигналы `TickSignals.total_debt` (`adaptive_clearing_policy.py:133`) и `last_clearing_cost_ms` (`:149`, `:199`) не читаются; это не дизайн клиринга хаба `09:38-46`. **Дополнительно после 023:** решение 8 023 снимает `max_depth` из исполнения — масштабирование глубины, главная ручка режима, теряет предмет. Выживающие контракты static-пути — «Verification plan», п. 3.
2. **Драйвер клиринга симулятора получает только миграцию вызывающего, и её доставляет 023(d)** (`023 spec.md:6`, решение 7, `T2304`). 021 не переписывает `real_clearing_engine.py:204-462` и цикл Interact-действия `api/v1/simulator.py:1891-1993`. **До переключения 023 тик вызывает нынешний драйвер поверх `ClearingService`; после — общий раннер 023** (задача `T2109`). `T2109` зависит от слияния `T2304` и **не блокирует** стадии 1–4. Контракт зафиксированного прогресса 023 (решение 10) сохраняется: каждое долговечное вхождение учитывается и публикуется, в том числе закоммиченное после отмены; рост доверия получает затронутые рёбра из этого контракта (сегодня — вызов `real_clearing_engine.py:466`). Объём клиринга симулятора `V_cyc` и объём MTCS `V_edge` хранятся раздельно (023, решение 1).
3. **Ключи симулированных участников — настоящие Ed25519; форма хранения решается `T2100`.** Варианты на консультацию:
   - (а) черновик: случайная пара на ран в хранилище рана — **отвергается посылками** F-021-5 (участники переживают ран; хранилище отключаемо; миграция);
   - (б) **рекомендуемый:** детерминированный вывод `SigningKey(seed = HMAC-SHA256(secret, "geo-sim-participant:" ‖ pid))` из одного секрета хаба; ключ не хранится нигде, вычисляется в памяти по месту подписи; `public_key` участника — выведенный. Таблиц и миграций 0; одна настройка. Существующие участники с ключом устаревшей формы (64 hex, не декодируется в 32 байта) получают выведенный ключ при сидировании — **только** если их ключ имеет эту устаревшую форму; валидный ключ Ed25519 не переписывается никогда (иначе сидер перехватил бы настоящего участника с тем же `pid`). Выведенный ключ для `pid` настоящего участника не совпадает с его зарегистрированным ключом, поэтому подпись не проходит — отказ, а не подмена.
   - Решение `T2100` записывается датой; для (б) — источник секрета и отказ старта в не-dev при пустом секрете (образец — `SIMULATOR_SESSION_SECRET`, `app/config.py:220`, `:358-371`).

## Внешнее ревью

Обязательно по §15: периметр безопасности (крипто-примитив, ключи на хабе, вход в публичный API), писатели линий доверия под `SERIALIZABLE` рядом с денежным путём, конкурентность тика, удаление тестов. Направление — Codex при оркестраторе Claude Code (`docs/external-review-runbook.md`): credential-free клон в `.local-run/codex-review/<id>/`, `--sandbox read-only`, замороженные `<BASE>..<HEAD>` и промпт, маркер вердикта, запрошенная модель записывается как requested; ревьюер ничего не запускает, гейты им не покрываются — это пишется. Ревьюеру ставится: (1) найти оставшуюся запись в `trust_lines` или `participants.public_key` из симулятора, включая raw SQL; (2) найти путь, где приватный ключ или секрет вывода покидает процесс (SSE, артефакты, снапшоты, логи, ответы `action_*`, исключения); (3) найти путь, где сидер переписывает валидный ключ или подписывает за настоящего участника; (4) проверить, что `sign` принимает ключ явно и не открывает подписи за участника, чьего ключа хаб не выводит; (5) проверить, что хвост тика остался одной транзакцией и ошибка хвоста не трогает денег; (6) механизмы, а не только код: гард R-021-1 и его исключение, сканер R-021-7 (`VERDICT-SENTINELS`). Находки классифицируются по §19.5: класс 1 чинится до слияния стадии (один круг fix-delta), класс 2 — в `BACKLOG.md`.
