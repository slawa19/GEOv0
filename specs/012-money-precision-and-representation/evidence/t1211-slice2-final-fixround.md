## Находки

### P1 — лестница глубины фактически не работает в цикле `RealClearingEngine`

В [real_clearing_engine.py:183](/app/core/simulator/real_clearing_engine.py:183) сначала выполняется поиск с глубиной 4 и при пустом результате — с глубиной 6. Но полученный список используется только для приоритизации/визуализации. Исполнительный цикл на [real_clearing_engine.py:284](/app/core/simulator/real_clearing_engine.py:284) сразу заново вызывает:

```python
find_cycles(..., max_depth=max_depth)
```

то есть полный поиск глубины 6 на каждой итерации.

Инструментированный запуск существующего сценария `_SuccessThenE010Service` дал:

```text
find_depths= [4, 6, 6]
```

Это не только не убирает прежнюю цену полного обхода, но добавляет перед ним короткий поиск. Заявление фикса о лестнице в обоих исполнительных циклах не выполнено для `RealClearingEngine`.

Обычные тесты этого не замечают:

```text
test_real_clearing_engine_partial_failure.py: 7 passed
test_tick_money_paths_carry_the_run_perimeter.py: 3 passed
```

Последний считает вызовы/perimeter, но не проверяет последовательность глубин.

### P1 — после неудачной смены backend используется precision предыдущего backend

В [useSimulatorRealMode.ts:1048](/simulator-ui/v2/src/composables/useSimulatorRealMode.ts:1048) ошибка загрузки каталога оставляет «whatever precisions are already in force». Watcher на `apiBase` запускает новую загрузку, но не инвалидирует старый каталог.

Воспроизведение в in-memory Vitest-пробе:

1. backend A возвращает `HOUR.precision = 4`;
2. `apiBase` меняется на B;
3. запрос каталога B падает;
4. ожидается штатный fallback `HOUR.precision = 1`.

Результат:

```text
expected 4 to be 1
1 failed, 10 passed
```

Это не только stale UI-state: `NodeCardOverlay.vue` преобразует `net_balance_atoms` через активный precision. Если данные B уже доступны, а каталог B нет, величина может быть показана с масштабом backend A — ошибка на степени десяти.

Существующий успешный сценарий A→B этого не покрывает:

```text
useSimulatorRealMode.equivalentPrecisionContext.test.ts: 10 passed
```

### P2 — часовые и общая таблица различают несколько ошибок, но остаются уязвимы к той же подгонке популяции

Один часовой против снятой реализации достаточен только для утверждения «выборка не эквивалентна именно этой функции». Он не доказывает пригодность выборки против класса правдоподобных ошибок. Один различающий случай среди двадцати вырожденных формально полностью удовлетворяет текущий assert.

Перебазированные контрпроверки действительно проверяют только добивку. Реализацию «добивать до precision, но обрезать лишние значащие цифры» отвергают обычные exact-output случаи вроде `0.05 @ 1`, а не сами контрпроверки. Следовательно, при случайной потере этих обычных случаев часовой останется зелёным.

Практическая мутация — терять знак только при `precision=0` — прошла оба локальных набора:

```text
graphPageHelpers.test.ts: 38 passed
moneyPrecisionByEquivalent.test.ts: 6 passed
44 passed
```

Она также проходит общую таблицу: отрицательные случаи там есть только для precision 1 и 2.

Общая таблица существенно лучше одиночного часового: она отвергает half-up maximum, усечение, отсутствие добивки, всегда восемь знаков, сохранение лишних нулей, общую потерю знака и float round-trip. Но в [money-rendering-conformance.json:31](/api/money-rendering-conformance.json:31) представлены только precision:

```text
[0, 1, 2, 8]
```

Контракт допускает `0..18`. Проверка трёх дополнительных неверных реализаций дала:

```text
cap_precision_at_storage_scale_8 disagreements= 0
supports_only_sampled_precisions_0_1_2_8 disagreements= 0
loses_negative_sign_only_at_precision_0 disagreements= 0
```

Первая особенно правдоподобна: реализация может ошибочно ограничить display precision историческим storage scale 8. Это оставит все 21 строки зелёными и не свяжет admin-ui с контрактом при precision 9–18.

Итог по механизму: нужна не обязательно буквально одна «пара», но минимум несколько независимых мутаций и покрытие границ домена. Одна историческая функция-часовой логически недостаточна.

### P3 — anti-vacuum генератора плана не закреплён исполняемой проверкой

Текущий сохранённый артефакт действительно использует популяцию, на которой предикат работает:

```text
Rows Removed by Join Filter: 51
buffers: 61898 / 62204
```

То есть текущий замер не построен только на отсутствии эффекта.

Однако заявление генератора, что различие доказывается числом возвращённых строк, неверно:

```text
with predicate rows = 100
without predicate rows = 100
```

Обе ветки ограничены `LIMIT 100`. Скрипт не разбирает `Rows Removed by Join Filter` и ничего не падает, если оно станет нулём. Кроме того, случайные boundary edges через каждые 50 строк не гарантируют конструктивно, что эти рёбра войдут в цикл. Артефакт сейчас содержателен, но механизм не защищает следующий замер от вырожденной популяции.


  Оба утверждения исполнителя подтверждены.

- Второго стабильного контрпримера для нового `auto_clear` не нашёл. Просмотрел все шесть `return None`, изменения состояния между `find` и исполнением и исключения. Нового engine-only отказа без парного фильтра не обнаружено. Изменившиеся locks/policy могут сорвать текущий tick, но на следующем `find` короткий цикл фильтруется, после чего широкая ступень становится достижима. Асимметрия по конечному состоянию выглядит обоснованной; найденная выше проблема `RealClearingEngine` — отдельная проблема стоимости.

- `formatDecimalFixed` не имеет вызывающих. Полный tracked scan `.ts`, `.vue`, JS, Python, PowerShell, e2e и скриптов нашёл только комментарии/исторические упоминания.

- Отрицательный ноль: достижимого backend wire-пути не нашёл. SQLite `Numeric(20,8)` нормализовал `Decimal("-0.00")` в `Decimal("0E-8")`, sign 0; остальные найденные пути либо требуют положительную сумму, либо читают уже сохранённый Numeric. PostgreSQL отдельно не проверен — тестового URL в среде нет. Исключение из таблицы выглядит оправданным, хотя само утверждение о DB-нормализации тестом не закреплено.

- Граница документации выдержана. Оставшиеся числовые суммы относятся к protocol/internal/unimplemented сообщениям. `max_single_payment`, в частности, текущей REST-дверью отвергается как неизвестное поле. Обратного случая — принимаемый текущей дверью числовой денежный пример — не найдено.
