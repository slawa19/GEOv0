## Problem

Ручной платёж в Interact работает и идёт через ядро, но как **прототип мобильного «отправить платёж»** он не годится: путь — до шести кликов через выпадающие списки плюс перезагрузка страницы при входе; перед подтверждением пользователь видит одно число одного ребра без маршрута, хопов и максимума; после подтверждения панель исчезает, экрана результата нет (история есть только как лог сессии в памяти, `useInteractMode.ts:541`); раскладки для телефона нет, касания идут только через общий `@pointerdown` фокуса окна (`WindowShell.vue:258`), полноценный touch-поток — UNVERIFIED; подтверждение одношаговое; тексты панелей только на английском; у ручного платежа нет ключа идемпотентности, хотя текст отказа советует «повторите». Оконный менеджер (2774 строки) обслуживает этот путь привязкой окон к узлам, каскадом и политикой размеров по фазам — ничего из этого мобильному потоку не нужно, а то, что нужно (Esc как шаг назад, возврат фокуса, двухшаговое подтверждение), — около 300 строк внутри него.

Наблюдаемый вред — продуктовый: цель владельца «красиво, понятно, минимальный путь, как в мобильном приложении» не достигается; плюс два дефекта честности (подсказка ёмкости без источника чисел, совет повторить платёж без идемпотентности).

## Целевое поведение

**Один поток в одном контейнере — «мастер платежа».** Пять шагов, каждый — один экран контейнера, навигация «Назад/Дальше» и Esc как шаг назад:

1. **От кого.** Список участников рана с поиском и именами (не PID); выбор на холсте тоже работает. Если включён режим «я — участник X» (П1), шаг пропускается.
2. **Кому.** Список целей из `payment-targets` с `include_max_available=true`: имя, **две раздельные подписи** — «кратчайший путь: N шагов» (BFS) и «оценка максимума: X» (max-flow, `simulator.py:2311,2332`; это разные вычисления, не «до X за N шагов»); недостижимые — серые с причиной; выбор на холсте подсвечивает только достижимых.
3. **Сколько.** Сумма с шагом эквивалента, выбор эквивалента здесь же (П2); живая подсказка «оценка максимума: X» из `max_available` с **источником чисел** — состояние относится к ответу `payment-targets` (запрошен / получен / не получен / `null` — «сервер не оценил», отличается от измеренного нуля), а не к состоянию строки линии из `trustlines`; при превышении — предупреждение, не блокировка (сервер решает), с текстом почему.
4. **Проверьте.** Итог: кто → кому, сумма, эквивалент, «кратчайший путь N шагов» (один BFS-путь **не** выдаётся за маршрут будущего платежа — его выбирает роутер в момент исполнения), двухшаговое подтверждение (`useDestructiveConfirmation`, как у закрытия линии).
5. **Результат.** Успех: `payment_id`, статус, сумма, **фактический маршрут(ы) с именами посредников и суммами по шагам** из ответа (`routes[]`, источник — `res.routes`, `simulator.py:1719`; решение П3) и «долг до → после» по каждому ребру с источником чисел, кнопка «Ещё платёж» и «Показать на графе»; отказ: текст из `paymentRefusalText` с `request_id` (после 034 S5) и честный совет (повторить — только если ключ идемпотентности есть). Экран держится, пока пользователь не закроет.

**Контейнер.** Один фиксированный: правый док на десктопе, на всю ширину (bottom-sheet) при ширине ≤ 520 px; касания работают как клики (pointer events). Внутри — **новый** хелпер Esc/фокус/подтверждение (≈200 строк) — он пишется как отдельный модуль по образцу кода WM, **сам WM при этом не редактируется**. Инспектор ребра/узла открывается **из** мастера как шаг «подробнее», а не рядом с ним: одновременно одно окно, копии линии нет (закрывает F-034-16 со стороны UX).

**Решение арбитра 2026-10-10 (Changelog) меняет этот абзац в трёх местах:** (1) ключ клиента **не становится `tx_id`** — сервер выводит идентичность платежа: `"man:" + sha256("manual|{run_id}|{client_key}")[:32]`, без эпохи запуска; (2) обещание «без второй публикации `tx.updated`» действует для последовательного повтора, для двух одновременных одинаковых запросов принята остаточная гонка — один платёж, до двух публикаций; (3) ключ и замороженное намерение держатся, пока исход **исходного платежа** неизвестен, и снимаются после известного успеха или окончательного отказа — HTTP-ответ сам по себе исход исходного платежа не доказывает. Исходный текст:

**Идемпотентность (`T3700`: отдельное optional поле `idempotency_key`, смысл корреляционного `client_action_id` не меняется; сейчас строгая схема `extra="forbid"` отвергнет неизвестное поле — `schemas/simulator.py:657`).** Жизненный цикл ключа: UI генерирует его на шаге «Проверьте» для **неизменного подтверждённого намерения** (от кого, кому, сумма, эквивалент); ключ **сохраняется при неизвестном исходе** (таймаут, обрыв — `payments/service.py:2558-2562`) и используется для повтора; смена любого поля намерения — новый ключ. Сервер: тот же ключ + то же тело → сохранённый результат (ядро это уже умеет: `payments/service.py:911,925,952,1277`), тот же ключ + другое тело → 409, **без второго денежного эффекта и без второй публикации `tx.updated`** (сейчас блок публикации `simulator.py:1712` идёт после любого успешного ответа — хендлер обязан отличать сохранённый результат от нового). Текст отказа `busy` советует повтор только с тем же ключом.

**Клиринг и линии в том же контейнере:** `ClearingPanel` показывает результат до «Закрыть» и перечисляет, кто кому сколько погашено по рёбрам цикла (данные в ответе уже есть) — `F-034-D8`; создание/изменение/закрытие линии — тем же мастером в три шага.

**Как показывается прохождение платежа и клиринга (решение оркестратора по делегированию владельца, 2026-10-08).** Цель — чтобы зритель за один платёж и один клиринг понял три вещи: (1) платить можно тому, кому не доверяешь напрямую, потому что между вами стоит тот, кому доверяют обе стороны; (2) платёж не передаёт «деньги», а переписывает долги вдоль цепочки; (3) клиринг гасит долги по замкнутому кругу, не меняя ничьей чистой позиции. Отсюда правила показа:

- **Платёж — как цепочка, а не как стрелка.** На экране результата — маршрут по шагам с именами: «Аня → Борис → Вера, 10». Под каждым шагом — что изменилось: «долг Ани перед Борисом: 5 → 15», «долг Бориса перед Верой: 0 → 10». Одна фраза-объяснение: «У Ани нет линии доверия с Верой; платёж прошёл через Бориса — теперь Аня должна Борису, а Борис — Вере». На холсте луч идёт **последовательно по рёбрам маршрута** с подсветкой посредников (в Interact это владение 037; в Auto-Run то же правило — D4 у S9), без спрямления. Если маршрутов несколько (`res.routes` может нести больше одного) — показываются все, каждый со своей суммой. **Источник данных:** фактический маршрут(ы) и суммы по шагам — из ответа `payment-real`, поле `routes[] {hops: [{from, to, amount}]}` (`Contract: yes`; на сервере это уже есть — `simulator.py:1719`); «долг до → после» на ребре — из кэша линий до операции и ответа `GET trustlines` после неё, **с источником чисел** (`TrustlineFiguresSource`): если «после» ещё не получено — показывается только «до» и пометка «обновляется». Ничего не выдумывается: нет маршрута в ответе — нет цепочки на экране, только факт платежа.
- **Клиринг — как замкнутый круг.** Результат `clearing-real` уже несёт `cycles[]` с рёбрами и суммой зачёта на цикл. Экран результата перечисляет каждый цикл как петлю имён: «Аня → Борис → Вера → Аня: зачтено по 7», под ним — каждое ребро «15 → 8», и итог по циклу: «обязательства сокращены на 3 × 7 = 21, чистые позиции участников не изменились». Внизу — «общий долг сети: до → после». На холсте — импульс по рёбрам **именно этого цикла** (данные есть в ответе), а не по всем задетым рёбрам разом. Результат держится до «Закрыть» (закрывает `F-034-D8` в части Interact). Отказ клиринга (мелкий шаг, нет циклов) — текстом из `clearingStepRefusalText`, с объяснением, почему нечего гасить.
- **Отказ платежа — как урок, а не как ошибка.** Текст из `paymentRefusalText` плюс одна строка «что сделать»: нет пути — «никто из тех, кому доверяет получатель, не доверяет отправителю; откройте линию»; не хватает ёмкости — «доверие исчерпано: максимум сейчас X». Это уже существующие причины ядра, новых не выдумывается.
- **Границы.** В Auto-Run (SSE, П7) `tx.updated.edges` несёт только первый маршрут без сумм по шагам — там показывается луч по рёбрам и журнал (S9), без «до → после» по шагам; в туре и Interact, где есть REST-ответы, показывается полная картина. Поле `routes[]` — единственное контрактное изменение этого решения; SSE не трогается.


**Что происходит с WM — одна граница (`T3700`).** В срезах A–C WM **не редактируется**; мастер и хелпер — новые модули рядом. Потребители WM мигрируют на контейнер по мере срезов B–C. **Срез D — условный cleanup**, который начинается только когда `grep -r "windowManager\|useWindowController" src --include=*.vue --include=*.ts | grep -v test` показывает единственного потребителя `node-card`; тогда `node-card` переезжает на контейнер и WM удаляется отдельным revertable-коммитом с тегом (§14). Если условие не наступает — WM остаётся, и это записывается честно; **обещания удалить все 2774 строки нет**.

## Продуктовые вопросы владельцу

- **П1 — решено 2026-10-08: «от любого к любому».** Режим «я — участник X» в первой версии не делается; шаг «От кого» остаётся в мастере (список с поиском, выбор на холсте). Мобильный чертёж (фиксированный отправитель) — для рабочей версии, не для демо.
