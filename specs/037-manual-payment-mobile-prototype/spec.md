## Problem

Ручной платёж в Interact работает и идёт через ядро, но как **прототип мобильного «отправить платёж»** он не годится: путь — до шести кликов через выпадающие списки плюс перезагрузка страницы при входе; перед подтверждением пользователь видит одно число одного ребра без маршрута, хопов и максимума; после подтверждения панель исчезает, результата и истории нет; раскладки для телефона и обработки касаний нет; подтверждение одношаговое; тексты панелей только на английском; у ручного платежа нет ключа идемпотентности, хотя текст отказа советует «повторите». Оконный менеджер (2774 строки) обслуживает этот путь привязкой окон к узлам, каскадом и политикой размеров по фазам — ничего из этого мобильному потоку не нужно, а то, что нужно (Esc как шаг назад, возврат фокуса, двухшаговое подтверждение), — около 300 строк внутри него.

Наблюдаемый вред — продуктовый: цель владельца «красиво, понятно, минимальный путь, как в мобильном приложении» не достигается; плюс два дефекта честности (подсказка ёмкости без источника чисел, совет повторить платёж без идемпотентности).

## Целевое поведение

**Один поток в одном контейнере — «мастер платежа».** Пять шагов, каждый — один экран контейнера, навигация «Назад/Дальше» и Esc как шаг назад:

1. **От кого.** Список участников рана с поиском и именами (не PID); выбор на холсте тоже работает. Если включён режим «я — участник X» (П1), шаг пропускается.
2. **Кому.** Список целей из `payment-targets` с `include_max_available=true`: имя, число хопов, максимум; недостижимые — серые с причиной; выбор на холсте подсвечивает только достижимых.
3. **Сколько.** Сумма с шагом эквивалента, выбор эквивалента здесь же (П2); живая подсказка «доступно до X за N шагов» из `max_available` с **источником чисел** (`TrustlineFiguresSource`: подтверждено сервером / из снимка / не запрошено); при превышении — предупреждение, не блокировка (сервер решает), с текстом почему.
4. **Проверьте.** Итог: кто → кому, сумма, эквивалент, маршрут словами «через A, B» (если П3 даёт поле маршрута; иначе — «N шагов через посредников»), двухшаговое подтверждение (`useDestructiveConfirmation`, как у закрытия линии).
5. **Результат.** Успех: `payment_id`, статус, сумма, кнопка «Ещё платёж» и «Показать на графе»; отказ: текст из `paymentRefusalText` с `request_id` (после 034 S5) и честный совет (повторить — только если ключ идемпотентности есть). Экран держится, пока пользователь не закроет.

**Контейнер.** Один фиксированный: правый док на десктопе, на всю ширину (bottom-sheet) при ширине ≤ 520 px; касания работают как клики (pointer events). Внутри — хелпер Esc/фокус/подтверждение (≈200 строк, выделяется из WM). Инспектор ребра/узла открывается **из** мастера как шаг «подробнее», а не рядом с ним: одновременно одно окно, копии линии нет (закрывает F-034-16 со стороны UX).

**Идемпотентность.** UI генерирует ключ операции на шаге «Проверьте» и передаёт его в `payment-real` (`Contract: yes`: поле `client_action_id` становится ключом идемпотентности или добавляется `idempotency_key`); повтор того же ключа возвращает тот же результат — ядро это уже умеет (015). Текст отказа `busy` советует повтор только с тем же ключом.

**Клиринг и линии в том же контейнере:** `ClearingPanel` показывает результат до «Закрыть» и перечисляет, кто кому сколько погашено по рёбрам цикла (данные в ответе уже есть) — `F-034-D8`; создание/изменение/закрытие линии — тем же мастером в три шага.

**Что происходит с WM.** После того как мастер покрывает все три потока (платёж, линия, клиринг) и инспектор переезжает внутрь контейнера, у `windowManager/**` не остаётся потребителей кроме `node-card` по двойному клику. Тогда — отдельным cleanup-срезом по AGENTS §14 (reference scan, тег, revertable commit) WM удаляется, `node-card` переезжает на тот же контейнер. **До этого WM не трогается** (П4 034).

## Продуктовые вопросы владельцу

- **П1. Режим «я — участник X».** Мобильный чертёж фиксирует «от кого» = текущий пользователь. В симуляторе предлагается переключатель «играть за участника»: выбрав его, пользователь пропускает шаг 1, видит свои линии, баланс и историю, платит только от себя; без переключателя — текущая свобода «от любого к любому». Делать переключатель в первой версии или оставить только свободный режим?
- **П2. Эквивалент в потоке.** Переносить выбор эквивалента в шаг «Сколько» (как `EquivalentPicker` чертежа) или оставить глобальным в BottomBar? Рекомендация: в поток — иначе мобильный сценарий не воспроизводится.
- **П3. Маршрут на экране.** Показывать имена посредников требует поля `path` (список PID) в ответе `payment-targets` или `payment-real` — это `Contract: yes` (OpenAPI, §8; SSE не трогается, П7 не нарушается). Без него мастер показывает «N шагов через посредников». Добавлять поле (≈30 строк бэкенда + OpenAPI) или обойтись числом хопов в первой версии?

Техническая развилка, решается `T3700`: ключ идемпотентности — переиспользовать `client_action_id` (меняется семантика существующего поля) или добавить `idempotency_key` (новое поле). Также `T3700`: `/payments/capacity` как preflight (чертёж PWA) против `max_available` из `payment-targets` (уже в контракте Interact) — предлагается второе, без новых вызовов.

## Non-goals

- Это **прототип UX**, не мобильный клиент: нет подписи ключом участника, нет refresh-токенов, нет Redis (BACKLOG «Перед мобильным приложением»), нет PWA-манифеста. Чертёж `docs/ru/pwa/**` не правится.
- Денежная семантика и `payments/service.py` не меняются; маршрут и ёмкость считает сервер, UI показывает.
- SSE не расширяется (П7 034). Все новые данные — по REST в узлах Interact.
- Тур «Понять GEO», легенда, журнал, словарь — 034 S9; 037 **потребляет** словарь RU/EN, а не вводит второй.
- Сценарии и движок — 036. Шаг тура «Попробовать самому» передаёт управление в мастер 037.
- Удаление WM — не в этой программе: отдельный cleanup-срез после того, как у WM не останется потребителей (условие проверяется grep'ом, записывается в Changelog).
- Новые фреймворки UI, дизайн-системы, store-библиотеки не вводятся: Vue 3 + существующие `ui-kit` примитивы.

## Проверка на переусложнение (§19.2)

1. **Наблюдаемая потеря.** Денежной нет. Продуктовая: цель владельца не достигается (шесть кликов, нет итога и результата, нет мобильной раскладки — п. 1–11). Честность: подсказка без источника (F-037-1), совет повторить без идемпотентности (F-037-2).
2. **Протокол.** Не затрагивается; мастер — клиент существующих путей ядра. Поле `path` (П3) — данные, которые роутер уже вычислил.
3. **Противник.** Нет.
4. **Дешевле.** (а) Оставить панели, добавить только `@media` и экран результата: закрывает раскладку и результат, но не маршрут, источник чисел и путь в шесть кликов.
