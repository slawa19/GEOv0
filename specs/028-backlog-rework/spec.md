### S1 — дефекты продукта, видимые пользователю

**F-028-1. Сид рана не помещается в колонку (№ 187).**
- *Current:* `seed = int.from_bytes(sha256(run_id)[:4], "big")` (`run_lifecycle.py:190-191`) — до 2³²−1; колонка `Integer` (`simulator_storage.py:30`, миграция 013). При сиде ≥ 2³¹ `upsert_run` падает, ошибка проглатывается (`storage.py:89-93`), строки `simulator_runs` нет. Сид — зерно генератора нагрузки тика (`real_payment_planner.py:363`, `:587`; повтор денежной фазы на нём держится — `money_replay.py:24-33`). *Intended:* каждый ран сохраняется с тем сидом, на котором шёл. *Optimal:* новая миграция `ALTER COLUMN seed TYPE BIGINT` и `BigInteger` в модели; генерация сида не меняется.
- §19.2: (1) примерно половина ранов без строки — нет истории, и проверка изоляции периодического клиринга (`clearing/runner.py:465`) такой real-ран не видит; (2) хранилище ранов; решение 9 программы 023; (4) **маска `& 0x7FFFFFFF` отвергнута:** дешевле (1 строка против ~40), но меняет зерно, а с ним последовательность нагрузки планировщика, для половины `run_id` — ломает правило «сид = первые 4 байта sha256(run_id)», по которому ран воспроизводим по его идентификатору; миграция поведения не меняет, а её цена не «явно больше»: §15-ревью у S1 и так есть; (5) миграция ~25 строк, модель 1, тест миграции ~40; (6) `simulator_runs` мала; апгрейд — смена типа без переписи значений, даунгрейд обратим только при сидах < 2³¹ — записывается в миграции.
- *Репродьюсер (PG):* `run_id` с первым байтом sha256 ≥ `0x80` → строка `simulator_runs` есть, `seed` равен сгенерированному. Сегодня — строки нет. Плюс проверка планировщика: для фиксированного `run_id` порядок кандидатов тика до и после правки совпадает.
- §8/§15: **да** — миграция; затрагивает вход проверки изоляции периодического клиринга.
