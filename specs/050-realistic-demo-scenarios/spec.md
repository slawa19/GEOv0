## Problem

Демо должно показывать сообщество, которое торгует по ролям, накапливает взаимные долги и регулярно гасит их клирингом. Сегодняшние «реалистичные» сценарии этого не делают, и причины — в данных и в трёх слепых зонах планировщика, а не в клиринге:

- **Долгов на старте нет.** Прогон начинается с нуля: сидер прогона создаёт эквиваленты, участников и линии, платежей и долгов не создаёт (`app/core/simulator/real_scenario_seeder.py:166-395`); долги рецептов админки симулятор не читает. Первый клиринг (такт 25) почти пуст.
- **Долги текут в одну сторону, кольца тонки.** В `greenfield-village-100-realistic-v2` структурных треугольников household → retail → producer → household всего 6 на 35 домохозяйств (пересчёт советника по фикстуре 2026-10-21); обратный поток в households (зарплаты) почти непроходим: прямых линий «households доверяют retail/services» нет, транзит через людей запрещён (`can_be_intermediate:false` у 237 из 432 линий; `producers` и `agents` — `person`). Два независимых офлайн-замера чистой функцией `plan_payments` (инвентаризация B; ревью Fable 2026-10-21 правилом роутера) — households отправляют ~60 % платежей, из запланированных платежей «в households» проходимы единицы процентов (194 → 2; 91.4 % пар непроходимы). `flow_chains` профилей не образуют кольца (producers→retail, retail→producers/households, households→retail) и не сверены с линиями. Итог: клиринг на деревне гасит 1.25–2.2 % общего долга против −58 % на `clearing-demo-10`. **Все числа этого абзаца — оценки до перезамера `T5001`** (скрипты замеров в дереве отсутствуют; §15 «невоспроизводимое утверждение — находка»).
- **Планировщик не видит политику транзита.** Получатель выбирается BFS глубины 3 по статическому графу линий без политики пары, ёмкости пути и `blocked_participants` (`app/core/simulator/real_payment_planner.py:861-887`), роутер же судит путь правилом пары по **обеим** линиям (`app/core/payments/capacity.py:46-79`, `router.py:242,304-308`). Два замера: 13.3 % (инвентаризация B, 2000 тактов при 5 %) и 22.4 % (Fable, по правилу роутера) запланированных платежей непроходимы ещё до появления долгов. Наблюдаемая доля отказов ~24 % (гипотеза: остаток — насыщение линий).
- **Планировщик останавливает платежи к связанным кредиторам.** Верхняя граница суммы вычитает **сумму** долгов по всем линиям участника из лимита **одной** максимальной линии: `available_in = max(0, max_incoming_limit − debt_in_agg)` (`real_payment_planner.py:427-436` против `:807-815` и `:830-838`). Магазин с семью должниками, заполнившими линии наполовину, получает `available_in = 0`, `pick_amount` возвращает `None` (`:169`), и платежи к нему **молча** перестают планироваться. Найдено ревью Gemini Argon 2026-10-21, подтверждено советником по коду. Со стартовыми долгами (решение 3) это остановило бы трафик сразу.
- **Контрагенты не держатся.** Получатель — случайный достижимый член целевой группы (`:925-940`), `flow_chains` без весов; частота отправителя ∝ числу линий-должника (`:121-155`, `:293-312`); абсолютное число действий за такт задаёт бюджет интенсивности (`:285`, `:312-316`), `tx_rate` — только относительный вес.
- **Структуру нельзя пересобрать.** Лимиты и линии `community.json` — замороженный вывод генераторов `admin-fixtures/tools/generate_seed_*_v2.py`, удалённых `b186e0f7` 2026-10-07 (`docs/ru/simulator/realistic-scenarios.md:92`); `scripts/generate_simulator_seed_scenarios.py` только накладывает профили (блок не менялся с 2026-02-10, `bf8d9869`), а `tooling-tests/portable/test_p017_t1712_community_descriptions.py:257-291` закрепляет равенство линий сценария и описания.
- **Цель нечем измерить.** Критерий INT-01a «clearing.done 2–5/мин» (`docs/ru/simulator/backend/acceptance-criteria.md:71`) — SHOULD/manual; доли отказов, доли платежей по ролям и доля погашения не измеряются ни тестом, ни скриптом.

Клиринг менять не нужно: MTCS без порогов находит ту циркуляцию, которая есть в долгах (`app/core/clearing/flow_planner.py:7-14,59-63`); встречные долги неттятся уже при платеже (`app/core/ledger/book.py:374-401`), поэтому циклы длины 2 не нужны и невозможны; при нуле циклов события не шлётся (`app/core/simulator/tick.py:1308`). Если циркуляции мало — это свойство данных и планировщика.

## Current / Intended / Optimal

- **Current:** см. Problem. Прогон деревни: односторонний поток, ~24 % отказов, клиринг 1–2 %; к хорошо связанным кредиторам платежи перестают планироваться по мере заполнения линий (F-050-4).
- **Intended:** протокол — «участники открывают линии доверия, платят по цепочкам связей, долги гасятся клирингом в замкнутых циклах» (`docs/en/00-overview.md`); `realistic-scenarios.md` §1.2 — «клиринг возникает только на циклах долгов… сценарий должен содержать замыкающее ребро household → producer», §2.3 — «циклы структурно, не случайно»; слово владельца 2026-10-21 (Origin).
- **Optimal (принято ниже):** экономика сообщества описывается кольцами ролей **на уровне участника** — у каждого есть постоянные контрагенты, приток ≈ отток, приток и отток через разные пары; линии, профили и стартовые платежи выводятся из этой модели одним детерминированным генератором; планировщик перестаёт планировать заведомо непроходимое, перестаёт глушить связанных кредиторов и предпочитает прямых контрагентов; цель измеряется скриптом и тестами с порогами, выведенными из модели до прогона.

## Решения (советник, 2026-10-21; правки по `T5000` отмечены)

1. **Модель экономики — кольца ролей на уровне участника; одно описание для всех сообществ.** Роли — существующие группы `anchors, producers, retail, services, households, agents`. Потоки (плательщик → получатель, то есть направление долга; нужна линия получатель → плательщик): households → retail (покупки: часто, мелко), households → services (услуги: реже, средне), households → anchors (аренда/взносы: редко, средне); retail → producers (опт: редко, крупно), retail → agents (поставки), retail → services (обслуживание); producers → households (зарплата) — **замыкает** households → retail → producers → households; producers → services; anchors → households (зарплата), anchors → producers (закупки); services → retail, services → households; agents → producers. Каждому участнику назначаются **постоянные контрагенты** по роли (household: 1–2 магазина, один работодатель, один сервис; retail: 2–4 производителя, 1–2 посредника; константы генератора), **с условием замыкания на уровне участника**: работодатель домохозяйства — поставщик одного из его магазинов или якорь, связанный с ним; приток и отток участника идут через **разные** пары (встречные долги одной пары неттятся при платеже, `book.py:374-401`, и клирингу не достаются — `T5000`, Fable 15). Генератор **отказывает**, если у какого-либо участника с потоками ожидаемый |приток − отток| > 25 % его оборота или у роли > 10 % (константы): без баланса по участнику циркуляция ограничена `Σ_v min(in_v, out_v)` (`flow_planner.py:59-63`; `T5000`, Codex 3/Fable 5). Ожидаемые потоки считаются **не формулой, а прогоном настоящей `plan_payments`** офлайн на сгенерированном сценарии (измеритель, решение 8), потому что абсолютное число действий задаёт бюджет интенсивности, а `tx_rate` — лишь относительный вес (`T5000`, Codex 2/Fable 9/Gemini 2).
2. **Линии выводятся из потоков, не наоборот.** На каждую назначенную пару плательщик → получатель — линия получатель → плательщик с лимитом `k × p90` пары (k — константа порядка 4–6). Транзит — **как сейчас, по типу участника:** `can_be_intermediate = (type == business)`, то есть `anchors` и `retail`; `producers`, `agents`, `services`, `households` — люди без транзита (`T5000`, Gemini 8б: прежняя формулировка «кредиторам-бизнесам: retail, producers, anchors, agents» была неверна — producers и agents в описаниях сообществ `person`). Кольца замкнуты **прямыми** линиями и в транзите не нуждаются. Существующие линии `community.json` в сценарий **не переносятся** (решение 9). Эквивалент — только `UAH`. Текст `role` описания сообщества переносится в `participants[].metadata.role` (`scenario.schema.json:204`; на верхний уровень участника схема не пускает).
3. **Стартовые долги — обычные платежи сценария, растянутые на такты 1–20.** Генератор выпускает детерминированный набор событий `type: payment` (существующий тип, `scenario.schema.json:278,305-309`) с `time = 1000 × t`, t = 1..20 (`sim_time_ms = tick_index × 1000` выставляется **до** исполнения такта, `runtime_impl.py:748-749`; событие с `time 0` сработало бы вместе с `1000` на такте 1 — `T5000`, все трое), **не больше 5 за такт и не больше одного на пару за такт** (платежи фазы идут последовательно в одной транзакции такта, `tick.py:571-598`; роутер внутри такта читает граф из кэша/отдельного соединения и второй платёж той же пары мог бы упереться в `E002` при привязке — `T5000`, Gemini Q1), сумма по паре ≤ 50 % лимита прямой линии. К такту 20 долги лежат по кольцам, и первый клиринг на такте 25 находит циклы; посетитель видит сеть, которая «оживает». Платежи идут **тем же путём, что и все** (`real_runner_impl.py:815-847` → `PaymentService`), через леджер и журнал 015; при прямой линии с остатком ≥ суммы роутер берёт один прямой хоп (`router.py:310,333-341,481-497`). **Рестарт прогона исполняет стартовые платежи заново поверх уцелевших долгов** — это контракт 036 B1 (`test_p036_b1_scripted_events_postgres.py:181-202`), не дефект 050: суммы ≤ 50 % лимита дают после одного рестарта ≤ 100 %, отказы стартовых платежей при рестарте допустимы и регрессией не считаются; проверяется, что прогон не падает и клиринг продолжается. **Отвергнуто:** запись долгов сидером в обход платежа (обходит журнал 015 и верификатор; §8), новое поле сценария «initialDebts» (новая сущность ради того, что выражается существующим событием), все платежи в один такт (один такт на 100–150 последовательных платежей; > 5 таймаутов роняют прогон — F-050-9).
4. **Частота и сумма — через существующие профили, как веса.** Генератор пишет профиль на **роль × число контрагентов**: `tx_rate` как относительный вес с поправкой на степень (`целевой вес роли / число линий-должника участника`, в [0, 1]; проверка генератора `mean(tx_rate) ≥ 0.05`, иначе бюджет такта не заполняется — `max_iters = 50 × target`, `:312`); `flow_chains` — кольцо из реш. 1 с `flow_affinity` по умолчанию (0.7), остальные направления — `recipient_group_weights`; `amount_model` — модель плательщика (сумма по паре ролей **принимается не чинить**: различие сумм выражается ролью плательщика — household тратит мелко, retail платит производителю крупно). Фактические доли по ролям и доля платежей на назначенных парах **измеряются** (решение 8), не постулируются. Периодичность во времени (зарплата раз в N тактов) **не вводится** — нет механизма, а ценность для зрителя за 3–10 минут не показана (§19.2 п. 6).
5. **Планировщик — три узкие правки, каждая с репродьюсером до правки.** (а) **Достижимость по правилу пары:** `_reachable_nodes` (`real_payment_planner.py:861-887`) не продолжает путь через хоп, который запрещает `route_breaks_policy` с правилами из `pair_rules` по обеим линиям пары (`capacity.py:46-79`) — **импорт, не копия правила**; кандидаты (`:121-155`) несут политику обеих линий. Ёмкость пути и долги маршрута планировщик по-прежнему не считает (это роутер; отказ `NO_CAPACITY` остаётся честным сигналом). (б) **Агрегат долга против суммы лимитов** (F-050-4): `available_out/in` считаются от **суммы** лимитов линий участника, не от максимума одной; на прямом ребре встречный долг учитывается как в `capacity.py:30` (`T5000`, Gemini 1). (в) **Предпочтение прямых соседей:** в `_choose_receiver` (`:898-952`) при выборе внутри целевой группы сначала берутся прямые соседи (1 хоп) с положительным остатком, глубже — только если их нет; иначе через транзитные бизнесы за 2–3 хопа достижима вся группа и назначенные пары размываются (`T5000`, Gemini 2/Codex 1). Все три меняют план при том же seed (`:281-283`) — тесты из owner surface обновляются **по измерению** с записью «что изменилось и почему», не подгонкой.
6. **Каденция клиринга не меняется:** 25 тактов (`app/config.py:245`, `tick.py:990`) — при такте ≥ 1 с это клиринг не чаще раза в 25 с, 7–24 раза за визит 3–10 минут; владелец просил регулярность **с результатом**, регулярность есть, не хватает материала. Поле каденции в сценарии — **не вводится** (§19.2 п. 4).
7. **Затухание доверия — по замеру, не заранее.** Три ревью разошлись (`decay_rate = 0`; дефолты и замер; `enabled: false`), значит решает стенд: `T5001` измеряет максимум `debt/limit` по линиям между клирингами на регенерированной деревне при 5 % и 15 %. Если ни одна линия не держится ≥ 0.8 между клирингами — параметры остаются по умолчанию; если держатся — `decay_rate: 0` с сохранением роста после клиринга, и причина записывается в Changelog. Код движка не трогается.
8. **Измеритель цели — скрипт плюс тесты с порогами, выведенными из модели до прогона.** `scripts/measure_scenario_economy.py` для фикстуры считает: (а) долю запланированных пар, непроходимых **по правилу роутера** (`pair_rules`/`route_breaks_policy` из `capacity.py`, не своя реализация; на статическом графе — независимо от правки 5(а), иначе метрика после правки равна нулю по построению, `T5000` Gemini 6б); (б) матрицу потоков по ролям и баланс приток/отток по участнику и по роли прогоном настоящей `plan_payments` на N тактов; (в) верхнюю границу циркуляции `Σ_v min(in_v, out_v) / Σ_v out_v`; (г) число и длины структурных колец и долю участников каждой роли в проходимых кольцах длины 3–4; (д) долю запланированных платежей на назначенных парах. По записи живого прогона (события SSE) — отдельно по окнам: **старт** (такты 1–20) и **установившийся режим** (с 21-го): доля `tx.failed` и доли ролей только по **плановым** платежам (стартовые исключаются, иначе они маскируют плохой поток — `T5000`, Gemini 5); погашение каждого клиринга как **доля оборота с предыдущего клиринга** (`cleared / объём платежей интервала`; первый клиринг судится отдельно как доля стартового долга) — доля общего долга недостижима арифметически после первого прохода (`T5000`, Fable 1). Пороги — константы теста, **выводятся из модели генератора до первого живого прогона** (ожидаемая циркуляция из (в) × коэффициент запаса) и датируются; менять их по результату прогона запрещено (Verification plan). Живой тест (PG, `slow`, по образцу `test_simulator_super_smoke.py`): 100 тактов, `tick_seconds` 0.25, темп 15 % (посетительская ступень «быстро»), клиринги на тактах 25/50/75/100; ассерты — на тактах 50/75/100 `cleared ≥ MIN_CLEARED_TURNOVER_SHARE × оборот интервала`, на такте 25 `≥ MIN_OPENING_CLEARED_SHARE × стартовый долг`, доля `tx.failed` среди плановых ≤ `MAX_REJECT_SHARE`, каждая роль с профилем и отправляет, и получает ≥ `MIN_ROLE_SHARE` плановых платежей, доля плановых платежей на назначенных парах ≥ `MIN_ASSIGNED_PAIR_SHARE`, плашки Stall (3 подряд полностью отклонённых такта) нет; затем рестарт и ещё 25 тактов — прогон жив, клиринг на такте 25 после рестарта непуст. `T5001` дополнительно измеряет (без ассертов) темп 5 % — посетительское «обычно». **Ролевые критерии применяются только к сценариям с профилями** (`*-realistic-v2`); `clearing-demo-10` (две группы, без профилей, `scenario.json:20-23`) измеряется только по отказам и доле погашения и остаётся сетью посетителя по умолчанию (решение владельца 2026-10-21, путь (а)); ему 050 ничего не меняет — **первый визит посетителя этой программой не улучшается до решения `T5007`**.
9. **Два мира данных признаются и разводятся явно.** `community.json`/`recipe.json` — состав и рукописные операции для базы админки и CI `ui-smoke` (`quality.yml:725`); из них генератор берёт **только состав** (участники, группы, статусы, `type`, `role`). Линии и поведение симулятора — вывод генератора 050. Тест `test_the_scenario_keeps_no_second_roster` (`test_p017_t1712_community_descriptions.py:257-291`) сегодня требует равенства линий — он **сознательно сужается** до равенства состава и групп, проверка линий переезжает в `test_p050_*` (это замена контракта T1712, а не правка ожидания; `T5000`, все трое). **Альтернатива рассмотрена и отвергнута:** писать линии модели в `community.json` — тогда 37 рукописных команд рецепта `riverside-town-50` (33 платежа, 2 заморозки, 2 клиринга на конкретных парах) и CI `ui-smoke` пришлось бы переписывать под новые линии ради админки, которой кольца не нужны. Расхождение линий между админкой и симулятором — **принятый долг** с записью в `realistic-scenarios.md`; перенос модели в `community.json` — находка BACKLOG, если админке понадобится та же сеть.
10. **Сеть посетителя по умолчанию не меняется этой программой.** После закрытия 050 владелец выбирает между `clearing-demo-10` и регенерированной деревней по кадрам одного прогона с числами измерителя (`T5007`); это его решение, не часть спеки.

## Проверка на переусложнение (§19.2, 2026-10-21)

1. **Наблюдаемая потеря.** Не деньги — цель демо: посетитель видит односторонний поток и клиринг на 1–2 %, то есть не видит сути GEO (слово владельца). Воспроизводится измерителем на текущих фикстурах (`T5001`): доля непроходимых по правилу роутера планов (оценки 13–22 %), треугольники через households (6), погашение (1.25–2.2 %); дефект F-050-4 — юнит-репродьюсером.
2. **Протокол.** `docs/en/00-overview.md` (взаимный кредит, клиринг в замкнутых циклах); `docs/en/02-protocol-spec.md` — направление линии creditor → debtor и платёж по цепочке линий. Демо должно показывать именно это; циклы — свойство данных.
3. **Противник.** Нет. Качество данных и три слепые зоны планировщика.
4. **Что дешевле и чего не хватает.** (а) Править `scenario.json` руками — 432 линии, невоспроизводимо; (б) только профили/`tx_rate`/`flow_chains` на существующих линиях — колец 6 на 35 домохозяйств, обратный поток непроходим, баланс по участнику профилями не достичь; (в) существующие линии + детерминированная добивка замыкающих (как удалённая `_add_extra_uah_service_links`) — оставляет 432 линии без ролевого смысла, которые владельцу не объяснить («магазин доверяет покупателю» объяснимо, 70 линий household↔household из PID-диапазонов — нет), и всё равно требует баланса по участнику, то есть переназначения пар; (г) каденция клиринга в сценарии — чаще гасить нечего; (д) долги сидером напрямую — обходит журнал 015; (е) только правки планировщика — снимают непроходимое и глушение, но кольца не создают; (ж) линии модели в `community.json` — переписывание 37 команд рецепта и `ui-smoke` ради админки (реш. 9). Выбрано: генератор по модели на уровне участника + стартовые платежи существующим событием + три узкие правки планировщика с репродьюсерами.
5. **Цена.** Генератор: переработка 532 строк в ~700–900 (модель — константы в модуле, без нового файла данных); измеритель ~300 строк (импортирует `plan_payments` и правила `capacity.py`); планировщик ~80 строк в трёх местах + обновление ожиданий 5 юнит-тестов по измерению + 2 интеграционных теста (темп 0) + сужение одного теста T1712; 2 регенерированных фикстуры (дифф в тысячи строк — проверяется измерителем и схемой, не глазами); 3–4 tooling-теста (детерминизм, баланс, кольца, схема/стартовые события); 1 `slow` живой тест ~60–120 с (вне обязательного гейта, `-IncludeExpensive`); `simulator-super-smoke` часть 3 идёт на деревне при 50 % — её время вырастет на стартовые платежи (замер в `T5001`); обязательный гейт: + секунды (tooling без БД, юнит-тесты планировщика). Новых сущностей в приложении — 0; новых скриптов — 1.
6. **Крайние случаи.** Берём: замороженные участники (5 в деревне) без потоков; участник без контрагентов по роли — отказ генератора; рестарт — по контракту 036 (отказы стартовых платежей допустимы). Не берём: сценарий с несбалансированной численностью ролей (генератор отказывает с указанием роли; численность — входные данные описания сообщества); многовалютность; старые базы.
