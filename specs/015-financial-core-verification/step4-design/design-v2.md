## 4. Money precision rule
SQLite Numeric binds as float, reads via to_decimal_processor_factory(Decimal, 8) (SA/sql/sqltypes.py:568-586). Analytically every scale-8 |v| < 2^26 round-trips exactly; empirically 300k random below 2^26: 0 lost; last 200k atoms below 2^26 exhaustive: 0 lost; first 200k atoms from 2^26: 65,782 lost; [1e8,1e9): 83,170/100k lost.
Rules: 1 PG is money-acceptance tier; expectations int atoms from literals; exact compare; no tolerance. 2 SQLite tests only |v| < 2^26 via helper asserting real DB round-trip; SQL aggregates on SQLite not money evidence. **[fix] Exception, required by mandatory condition 4:** a value outside that domain may appear in a SQLite test **when the assertion is the hook's refusal before any debt SQL**, never as stored money evidence. Rule 2 was written with no exception and therefore forbade condition 4's own counterexample, which exists only near `1e11`: in `100000000000 → 0.00000001` both operands are exactly storable while the delta `−99999999999.99999999` is not. A refusal needs no round-trip, so the two requirements never actually collided — the text did, and the text is what an implementer follows. 3 hook storability is **four independent predicates, and every refusal names the one it violates [fix]**: (i) finiteness — NaN, ±Infinity; (ii) magnitude — |v| < 10^12; (iii) quantization — v == v.quantize(1E-8); (iv) dialect round-trip — result_processor(bind_processor(v)) == v for the session's actual dialect (PG identity; SQLite refuses values it would change). These were previously one undifferentiated list called “storability”, and C12 then used round-trip language for values that violate (i) and (ii) instead: `1E12` and `Infinity` round-trip on SQLite **byte for byte**, so a round-trip assertion on them passes while proving nothing. Naming the wrong predicate in a refusal is the same overclaim this programme exists to remove. Every ORM write checked → in-memory history equals stored value for journaled changes. Limit: a raw writer not bumping version under READ COMMITTED can make amount_before stale; prod PG SERIALIZABLE; residual shows as per-edge continuity break in step 6.
**NaN, and a live defect in the money column itself — `T1526` [fix].** On SQLite a NaN bind becomes NULL, so “NaN refused” is satisfied **today**, by `debts.amount NOT NULL` — a constraint that names a different problem; the hook's refusal must therefore be asserted before any SQL and by predicate (i), with the mutation that shows the two mechanisms are distinguishable (C12). On PostgreSQL the production column accepts NaN outright: `'NaN'::numeric(20,8) > 0` is true and the constraint is literally `CHECK ((amount > (0)::numeric))`, so a single NaN debt turns every sum over the equivalent into NaN. That is a live defect of existing code, filed as **`T1526`**, and it is **not** step-4 work — named here only so the next reader does not mistake the journal's own rejection for coverage of `debts`. The journal's money CHECKs (§5) do exclude NaN, but through the **upper bound** — `abs('NaN') < 1e12` is false — and not through positivity, which is why they must be written with the bound and not tightened into a positivity test.

**[T1526, measured 2026-09-12] The journal's money CHECKs cannot refuse NaN on SQLite, so the columns need the bind-layer guard too.** A CHECK excludes NaN on PostgreSQL through the upper bound (`abs(v) < 1e12` is FALSE for NaN), which is what the money clauses above rely on. On SQLite that reasoning does not hold for a different reason than expected: a bound NaN has `typeof` `'null'`, so it never reaches the CHECK at all and is refused, if at all, by `NOT NULL` - a constraint naming the wrong problem. Infinity does reach the CHECK and the magnitude clause refuses it, so the two are not interchangeable. Therefore every money column of the journal tables must use `app/db/types.py::MoneyNumeric` (the bind-layer refusal introduced by T1526 for `debts.amount` and `trust_lines.limit`), not bare `Numeric`, or the design's claim that its CHECKs exclude NaN is true on one backend only.

**[scope 2026-09-12, owner decision, binding] The checksum chain is deferred — not part of the plan — until an external trusted anchor exists.** Dropped from the step-5 shape above: `debt_journal_heads.head_hash`, `debt_journal_slots.prev_hash` / `hash` / `algorithm_version`, `debt_ledger_epochs.baseline_digest` **in its role as the chain's start of trust**, and every reading of the head CAS as tamper-protection. The reason is this design's own admission, already written into the accepted contract (`spec.md`, decision 8, «Граница гарантии»): a chain without a key detects change relative to the stored hashes and the head, and anyone able to rewrite the database together with the baseline and the head simply recomputes it. So it protects only against an adversary who has no database access — and an adversary without database access cannot alter debts either. It reads as tamper-protection while not being it, which is the exact class of overclaim this programme exists to remove. **Precondition for un-deferring:** an external trusted anchor — a value the database cannot rewrite. Until that exists, no column name, no verifier output and no prose in this programme may describe the journal as tamper-evident.

**The baseline/epoch stays, and its justification changes [fix].** It was carried partly as the chain's start of trust; that reason leaves with the chain. What remains is the only one it ever needed: the baseline is **the anchor that bounds reconciliation**, so the check does not have to sum history from the beginning of time — genesis is unreachable in this repository, which is why a baseline exists at all (`spec.md`, `T1501`). It is **not** anti-tamper and must not be described as such anywhere downstream. Surviving on that reason: `debt_ledger_epochs` (minus the chain role of its digest), `debt_ledger_baseline_edges`, the per-equivalent transactional ordering counter, `head_seq_at_open`, and the heads row as the holder of `epoch_no`/`last_seq`. Not surviving: the hash columns and the claim they carried.
