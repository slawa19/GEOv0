# 044 — Публичное демо: у каждого посетителя свой прогон; ревизия кода жизненного цикла прогонов

- **Date:** 2026-10-17, против `main` на `1edd0491`.
- **Status:** **АВТОРИЗОВАНА 2026-10-17 словом владельца** («У каждого свой прогон — делаем спеку и реализацию, встрой в план, когда это логично сделать. Демка будет публичной, поэтому один прогон никак не устраивает. Заодно внимательно посмотреть и оптимизировать код этого среза до реализации, если там тоже много мусора и устаревшего кода»). - **Origin.** 043 S2 сделал запуск прогона автоматическим при открытии демо; при `SIMULATOR_MAX_ACTIVE_RUNS=1` (`app/config.py:246`) второй посетитель получает 409 `global_active_limit` (`run_lifecycle.py:104-115`), а чужой прогон закрыт (`_check_run_access`, deny-by-default). Владелец 2026-10-17 решил: демо публичное, каждому посетителю — свой прогон; одновременно — ревизия кода этой области.

## Problem

Публичное демо с одним активным прогоном на сервер непригодно: второй посетитель видит ошибку вместо сети. Поднять лимит без остального нельзя: (а) прогон, брошенный посетителем, живёт дальше — тикает, пишет платежи в базу и держит записи; на публичном сервере это накопление без границы (BACKLOG 043-2); (б) каждый прогон — живой процесс с тиком раз в секунду (`SIMULATOR_TICK_MS_BASE=1000`), до 20 действий за тик, клиринг каждые 25 тиков, запись артефактов каждые 5 с — нагрузка на одну базу растёт линейно с числом прогонов; (в) граница по ресурсам сейчас — только число активных прогонов и число SSE-соединений (50 всего, 10 на прогон).

**Наблюдаемая потеря (§19.2 п. 1):** публичное демо не показывается второму человеку (потеря смысла главного демо), и ресурсы сервера расходуются на прогоны без зрителя. Денежной потери нет; изоляция прогонов по периметру участников — предмет стадии 0 (не предполагать, а показать).

## Решения владельца (терминальные, 2026-10-17)

1. **У каждого посетителя свой прогон.** Один активный прогон на владельца (`SIMULATOR_MAX_ACTIVE_RUNS_PER_OWNER=1` — уже есть), общий лимит поднимается до измеренного значения `N` (стадия 0 называет число по замеру нагрузки, не наугад). Чужой прогон остаётся закрытым.
2. **Брошенный прогон останавливается сам.** Прогон без ни одного SSE-подписчика дольше `T` минут переводится в `stopped` с причиной `idle_no_subscribers`; данные и артефакты не удаляются (исключение 2026-10-10 по диску остаётся). Это новая сущность — шесть вопросов §19.2 ниже.
3. **Исчерпание общего лимита — человеческий текст и повтор** («Сейчас демо смотрят N человек, попробуйте через минуту»), без сырого 409.
4. **Сначала ревизия, потом реализация.** Код жизненного цикла прогонов (owner surface) проверяется на мусор, устаревшие ветви и дубли **до** правки; найденное удаляется отдельными коммитами с доказательством (grep, вызовы, история), по §14.

## §19.2 — шесть вопросов к новой сущности «остановка по простою»

1. **Потеря:** прогоны без зрителя тикают и пишут в базу неограниченно долго; на публичном сервере это гарантированное исчерпание лимита `N` брошенными прогонами (второй посетитель снова видит ошибку) и рост нагрузки. Воспроизводится: открыть демо, закрыть вкладку, через `T` минут `GET /simulator/runs` (admin) показывает `running` без подписчиков — репродьюсер стадии 2.
2. **Протокол:** не требует; это требование публичного демо, не протокола GEO.
3. **Противник:** нет; это гигиена ресурсов, не безопасность.
4. **Дешевле:** (а) ручная остановка оператором — не покрывает публичный вход без оператора; (б) остановка при закрытии вкладки (`beforeunload`) — ненадёжно (сеть, краш, мобильный браузер) и не покрывает уже брошенные; (в) не поднимать лимит — противоречит решению владельца. Остановка по отсутствию подписчиков — минимальный автоматический вариант: счётчик подписчиков уже ведётся в `sse_broadcast.py`, нужен только порог времени и один проход в существующем тике/планировщике, без нового фонового процесса.
5. **Цена, числом:** 0 новых таблиц и endpoint'ов; 1 ключ конфигурации; одна проверка в существующем цикле (тик или `run_persist`); причина остановки — новое значение существующего поля; ≈ 60–120 строк продукта; тесты — 3–5 на Postgres-тире (без `sleep`: управляемые часы). Записать фактическое число в Changelog стадии 2.
6. **Крайние случаи:** переподключение SSE в пределах `T` (не останавливать — считать по последнему отключению, не по первому); пауза без подписчика (останавливать — пауза не держит прогон живым для зрителя, которого нет); прогон оператора через Admin ▾ (тот же закон; оператор держит подписку или перезапускает); прогон стенда/тестов (`T` настраивается, тесты ставят большой `T` или управляют часами); несколько вкладок одной cookie (одна подписка достаточно). Гипотетические пути без входа в приложении — не покрывать.

## Non-goals

- Не открывать чужие прогоны для чтения и не делать «один общий прогон» (решение владельца — путь 1).
- Не удалять артефакты на диске и записи прогонов автоматически (исключения 2026-10-10 остаются; `scripts/cleanup_simulator_runs.py` — ручной путь).
- Не трогать тик, денежный путь, `allowed_participant_pids`, SSE-формы, OpenAPI кроме текста 409 и нового значения причины остановки.
- Не вводить очередь ожидания, приоритеты, аутентификацию посетителей.

## Запланированное расширение дизайна 044 — изоляция прогонов по участникам (2026-10-17)

**Основание.** Стадия 0 (`T4401` (б), тест `tests/integration/test_p044_s0_two_visitors_runs_are_isolated.py`, коммит `c6d6e2dc`) показала класс 1 для публичного демо: доступ к чужому прогону закрыт, но периметр прогона — список pid сценария, разрешаемый по общей таблице `participants`; два прогона одного сценария (а это и есть публичное демо: каждый посетитель автозапускает `clearing-demo-10`) действуют на одних строках участников, линиях и долгах. Техническое решение — Codex 2026-10-17 (`DECISION-044-ISOLATION: PER-RUN-SCOPED-PIDS`), решения советника 2026-10-17. Это **запланированное расширение дизайна**, а не попутная правка: по §19.1 широкому определению связывание идентичностей — один новый механизм (без таблиц, миграций и фоновых процессов). Предусловие стадии 2.

**(i) Посылка** (решение 9 советника 2026-10-17, дословно): «Публичное демо работает на отдельной одноразовой базе без производственных обязательств. Pruning прогонов не освобождает участников, линии, долги, транзакции и журнал. Хранилище растёт с числом прогонов до явной замены базы оператором. Автоматического удаления денежных строк нет.»

**(ii) Расширение периметра.** Owner surface программы расширяется на: `app/core/simulator/run_perimeter.py` (связывание), `real_scenario_seeder.py` (принятие только строк своего прогона), `inject_executor.py` / `scenario_story.py` в части ссылок на участников, `snapshot_builder.py` (превью шаблона), `scenario_registry.py` / `runtime_impl.py` / `app/api/v1/simulator.py` (допуск сценариев), `api/openapi.yaml` (тексты допуска и загрузки), места Simulator UI v2, печатающие pid человеку. Прогон при создании получает **свежих участников** под идентичностями `<полный run_id>:p<порядковый номер>`, связанными один раз в `create_run` и сохраняемыми через `/restart` (тот же прогон — те же участники и долги). Переписываются только типизированные ссылки на участника: участники, концы линий, `policy.blocked_participants`, платежи сценария, `expected_cycle`, `anchor`, `focus.pids`/`focus.edges`, участники `add_participant`, `sponsor`, цели `freeze_participant`; группы, профили, подписи и прочие строки — нет. Ссылка на необъявленного участника отклоняется при создании прогона, а не разрешается глобально. Шаблон сценария не меняется. Имена событий SSE, формы и алиасы `from`/`to` не меняются — меняются только значения идентификаторов. Эквиваленты, журнал, сверка и baseline не трогаются (ни перебазирования, ни копирования истории долгов, ни обхода писателей). Вне периметра остаются: таблицы арендаторов, RLS, база на прогон, сборка мусора денежных строк, регенерация фикстур, общие ACL, фреймворк восстановления.

**(iii) Тест стадии 0.** Буквальные ожидания идентификаторов (`{"p1","p2"}`, `{"alice","bob"}`, ключи линий) заменяются идентичностями, которые возвращает прогон; все утверждения изоляции, долгов и доступа остаются; сценарии теста явно вносятся в allowlist теста. Тест сливается только вместе с исправлением, не отдельно и не как xfail.

**(iv) Имена.** Тосты, история, выбор участника и навигация Simulator UI v2 показывают `name`; при пустом `name` — короткий исходный pid сценария без префикса прогона. Колонка PID админки показывает настоящий идентификатор.

**(v) Допуск.** Allowlist сценариев (`SIMULATOR_SCENARIO_ALLOWLIST`) действует на запуск прогона и публичные чтения сценария (деталь, превью) для не-администратора; загрузка сценария (`POST /scenarios`) — только администратор; публичное превью строится из шаблона без глобального обогащения участниками.

**(vi) §19.2 — шесть ответов (Codex 2026-10-17, датировано):**
1. **Потеря:** платёж прогона A появляется в прогоне B; B действует на ту же сеть долгов; новый прогон наследует долги прошлого прогона. Репродьюсер — тест стадии 0 (`same_scenario`, `shipped_scenarios_sharing_pids`, красные на `c6d6e2dc`).
2. **Протокол:** GEO задаёт обязательства участников, лимиты, платежи и клиринг и не требует пространств имён посетителей; изоляция — требование демо 2026-10-17, реализуемое без изменения денежной семантики.
3. **Противник:** обычные одновременные посетители и враждебные анонимные HTTP-вызывающие, подставляющие id сценариев и pid. Защиты от произвольного кода внутри процесса и доверенных администраторов базы не заявляется.
4. **Дешевле:** проверки доступа и allowlist сами строк не разделяют; префикс по сценарию не разделяет двух посетителей одного сценария; отказ второму прогону противоречит решению владельца; база на прогон или колонки арендатора затрагивают существенно больше кода; копии на владельца переносят состояние между прогонами одного владельца и не ограничены по хранению (смена cookie).
5. **Цена (оценка Codex, факт — в Changelog):** 12–14 файлов продукта, 350–650 строк продукта, 6–8 файлов тестов, 3 файла контракта/документов; 0 таблиц, 0 миграций, 0 фоновых процессов, 0 дополнительных запросов за тик от связывания; один проход отображения на прогон, линейный по объявлениям. Число запросов не меняется, но их стоимость растёт: общая маршрутизация и сверка сканируют больше сохранённых строк.
6. **Крайние случаи с путём в приложении:** одновременные запуски, одинаковые исходные pid, участники inject, враждебные чужие pid, длинные id, гонка ленивого сидирования и тика, повторы, `/restart` того же прогона, чтения остановленного прогона, пустые имена, недопущенные сценарии.

**(vii) Цель по числу прогонов (слово владельца 2026-10-17, через советника).** Цель N = 10 живых прогонов (слово владельца 2026-10-17). Темп автоматических платежей у прогонов посетителей — отдельный настраиваемый параметр (ориентир 10–15 %); операторский Start может оставаться 30. Остановка по простою освобождает места. Окончательное N подтверждает замер стадии 2 на 10 одновременных прогонах. Текст при исчерпании мест называет число.

**(viii) Результат замера 2026-10-17 (советник, 2026-10-17).** Результат замера 2026-10-17 (не оценка): темп прогонов посетителей по умолчанию 15 (10 одновременных прогонов на одном процессе — 64 % ядра, растяжение тика 1.24); операторский Start — 30; N = 10 подтверждён на одном процессе при темпе 15. Стадия 2 начинается с поиска растущего объекта памяти (BACKLOG 044-3) — предусловие выбора N.
