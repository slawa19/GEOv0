## Problem

Таблицы `debts` и `trust_lines` пишут **девять** модулей в трёх архитектурных слоях (инвентаризация 2026-09-21, перепроверено): `payments/engine.py:1799-1845`, `clearing/service.py:2100-2102`, `trustlines/service.py:215,370`, `simulator/inject_executor.py:531,555,707,846`, `simulator/real_scenario_seeder.py:226`, `simulator/trust_drift_engine.py:310,488` (Core `UPDATE` в обход сервиса), `api/v1/simulator.py:1117,1359` (HTTP-обработчик строит `TrustLine`), `api/v1/integrity.py:378,384,479` (ремонт правит и удаляет долг), и поверх всех — `ledger/journal.py:1784,1979,2842`, перехватывающий первых. Протокол называет ровно два места, где долг меняется: `apply_commit` (`docs/ru/02-protocol-spec.md:898-923`) и `apply_clearing` (`:1119-1137`); третье, `COMPENSATION`, зарезервировано. Ремонтного писателя в протоколе нет вовсе; §10.7 (`:1747-1755`): «транзакции не удаляются и не модифицируются… для исправления ошибок создаются новые транзакции».

## Что решает программа

### Одна точка записи

`app/core/ledger/book.py` — единственный модуль в `app/`, который конструирует `Debt`, присваивает `Debt.amount` или удаляет `Debt`. Интерфейс из одной операции:

```
Book.post(session, op: Operation, effects: Sequence[EdgeFlow]) -> Posted
```

`Operation` несёт `kind ∈ OPERATION_KINDS` (`journal_tables.py:72`, **без изменений**: `PAYMENT`, `CLEARING`, `INJECT`, `SEED`, `TEST_FIXTURE`; правило «после baseline `SEED`/`TEST_FIXTURE` отвергаются» из `T1501` сохраняется), `identity`, `intent` (версионированный, как сегодня в конверте), для `PAYMENT`/`CLEARING` — `tx_id` **уже существующей** строки `transactions` (FK `debt_operations.tx_id → transactions.tx_id`, `journal_tables.py:124-130`, и CHECK `chk_debt_operations_tx_id_iff_kind`, `:158-162`: вызывающий вставляет `Transaction` **до** `Book.post` в той же транзакции). `EdgeFlow` — направленная пара и сумма в атомах `10⁻⁸`. Внутри `post`, в **той же транзакции вызывающего**:

1. `INSERT debt_operations (state=OPEN, intent, intent_digest, tx_id)`;
2. `SET LOCAL geo.operation_id = <id>`;
3. применение эффектов по алгебре Phase B 1b (015 `spec.md:680-687`): встречный долг гасится первым, затем создаётся или растёт прямой; направленный ключ `(debtor, creditor, equivalent)` существующей строки неизменяем — смена направления есть `DELETE` + `INSERT`; строка с нулём удаляется (`02-protocol-spec.md:208-211`). Цикл повторов `StaleDataError` из `_apply_flow` (`engine.py:1788-1824`) **не переносится**: под `SERIALIZABLE` конкурентное изменение строки даёт `40001` раньше, а `StaleDataError` после программы — целостностная ошибка, не повтор; повтор целой единицы работы на `40001` остаётся у вызывающего (`_run_uow_with_retry` до 019, предикат 019 после);
4. `SELECT ordinal, ... FROM debt_journal_entries WHERE operation_id=<id> ORDER BY ordinal` — записи, которые оставил триггер; `UPDATE debt_operations SET state=COMPLETED, effect_count=<n>, effect_digest=<digest записей>`;
5. `SET LOCAL geo.operation_id = ''` — контекст **снимается на выходе** (в `finally`), потому что `SET LOCAL` живёт до конца транзакции, а не savepoint'а: без сброса случайная запись позже в той же транзакции тика приписалась бы уже завершённому конверту.

Никакого `commit` внутри `Book`: транзакцией владеет вызывающий (платёж, клиринг, тик). Это сохраняет решение Phase B 5 («инжект отдаёт владение транзакцией», `spec.md:726-732`) как свойство конструкции, а не как дисциплину.

### Журнал пишет база, а не слушатель

Миграция создаёт функцию и триггер `AFTER INSERT OR UPDATE OR DELETE ON debts FOR EACH ROW`:

- `ctx := nullif(current_setting('geo.operation_id', true), '')` — именно `nullif`: у пользовательского GUC после первого `SET LOCAL` на том же физическом соединении пула значение вне транзакции — пустая строка, а не `NULL`; проверка `IS NULL` без `nullif` пропустила бы неинструментированную запись на переиспользованном соединении;
- при `ctx IS NULL` — `RAISE EXCEPTION` с собственным SQLSTATE (`GE001`, «debts: write without operation context»);
- при `(SELECT state FROM debt_operations WHERE id = ctx) <> 'OPEN'` — тот же отказ: запись в завершённый конверт невозможна, «одна операция — один конверт» (Phase B 9, `spec.md:785-787`) держится базой;
- при `UPDATE`, меняющем `debtor_id`/`creditor_id`/`equivalent_id`, — отказ (направленный ключ неизменяем, Phase B 1b);
- иначе — `INSERT debt_journal_entries (operation_id, ordinal, debtor, creditor, equivalent, effect, amount_before, amount_after, delta)`: `effect` из `TG_OP` (`I`/`U`/`D`), суммы из `OLD`/`NEW`, `ordinal` из последовательности `debt_journal_entries_ordinal_seq` (`BIGSERIAL`): внутри одной операции пишет ровно одна транзакция, поэтому порядок по последовательности — порядок эффектов; `reconciliation.py` сортирует по нему там, где сортировал по `flush_ordinal`. Существующий CHECK `chk_debt_journal_entries_delta_arithmetic` (миграция 024) остаётся.

Что это даёт **по построению**, а не по перечислению: (а) ни одна строка `debts` не меняется без открытого конверта — ни через ORM, ни через Core DML, ни через `bulk_*`, ни через DML-CTE, ни через `psql` оператора; все пять «не перехватываем» из Phase B 2d (`spec.md:700-702`) закрываются одним триггером; (б) запись журнала равна фактически записанной строке — `_reconcile` (`journal.py:2151`) и `_verify_entries` (`:2348`) с их измерением `T1530` («`debts` держит 11, запись говорит `10 → 12`») становятся тавтологией внутри базы и удаляются; (в) сбой журнала прерывает денежную транзакцию (Phase B 2b) — потому что журнал и есть часть транзакции.

**Граница гарантии, сказанная вслух.** Триггер останавливает писателя **вне приложения** и **неинструментированного писателя внутри** (он не знает про `SET LOCAL`). Он **не** останавливает враждебный код в том же процессе: тот выполнит `SET LOCAL` сам. Это ровно модель угроз, принятая 2026-09-13 закрытием `T1531`/`T1536`; программа её не расширяет и не заявляет большего. Оператор с правом `ALTER TABLE ... DISABLE TRIGGER` также вне модели; разделение ролей БД — отдельное решение, здесь не вводится (§19.2 п. 6).

### Что остаётся без изменений

`debt_operations` (кроме `flush_count`), `debt_journal_entries` (кроме `flush_ordinal → ordinal`), baseline (`T1501`: один неизменяемый на эквивалент), `reconciliation.py` с критериями (а) и (б) (015 `spec.md:3764-3767`), интегрити-hold (`T1546`) и реакция из планового цикла (`T1516`). Проверено 2026-09-21: `verify_journal_equals_change` (`reconciliation.py:780-846`) читает только таблицы и не зависит от того, кто вставил записи; `effect_digest` сверкой не читается. Контрпример 7c Phase B («неправильный писатель: (а) проходит, (б) падает», `spec.md:766-768`) сохраняется как обязательный тест — писатель, двигающий не то ребро, по-прежнему честно записан триггером и по-прежнему пойман эталоном (б).

## Проверка на переусложнение (§19.2) — 2026-09-21

1. **Какую наблюдаемую потерю это предотвращает?** Два встречных долга через инжект (`F-015-12`, воспроизведено), снос долга ремонтом на замороженной линии (`F-015-6`, воспроизведено), долг `11` при записи `10 → 12` (`T1530`, измерено). Каждая — путь, где писатель вне единственной точки записи двигает деньги не по протоколу.
2. **Что говорит протокол?** §3.4 «обновляется атомарно в рамках транзакций» (`:208-211`); §11.2.4 симметрия; §10.7 неизменяемость истории; §6.7/§7.6 — ровно два писателя.
3. **Кто противник?** Оператор с `psql`, будущий неинструментированный модуль, каскад БД — все **вне** процесса приложения или вне знания о контексте; против них триггер — предотвращение. Враждебный код в процессе — вне модели, названо.
4. **Что дешевле и чего ему не хватает?** (а) Оставить `journal.py`: 3 078 строк, проигрывает соседнему слушателю по собственному признанию. (б) Явные `INSERT` в журнал из каждого писателя без триггера: Phase B отвергла как «правильность на перечислении»; с одним писателем перечисление длины 1, но оператор `psql` и каскад по-прежнему невидимы — не закрывает `N1`-класс. (в) Только `Book` без триггера: то же. Триггер дешевле любого из них (оценка около 60 строк SQL) и единственный, кто видит всех.
5. **Цена, числом.** Новых сущностей: 1 модуль (`book.py`, оценка 250–350 строк), 1 миграция (функция, триггер, последовательность, две правки колонок — оценка около 80 строк), 1 собственный SQLSTATE. Удаляется: 3 078 строк `journal.py` (точно), 19,3 тыс. строк тестов механизма (инвентаризация), два эндпоинта ремонта. Запросов на операцию: `+1` `SET LOCAL`, `+1` чтение записей при завершении, `+1` сброс контекста; вставки записей журнала переходят из хука в триггер один к одному. Время прогона: замер до/после в `T1809`.
6. **Крайние случаи.** Частичный flush, потерянный savepoint, AUTOCOMMIT-детекция, «нет открытой транзакции» — у всех после программы нет пути: писатель один, транзакция вызывающего одна, триггер срабатывает на строке, а не на flush. Оператор, отключивший триггер, — гипотеза без входа в приложении, кодом не покрывается (§18).

### 2. Инварианты, обязанные выжить, и контрпроверка

- Критерий (а): `baseline + Σdelta == debts` по объединению ключей; контрпробы `T1508` (один атом мимо приложения — теперь **отказ на записи**, а не `FAILED` постфактум; форма контрпробы меняется и это записывается; обычная операция — `PASSED`; отсутствие baseline — `UNVERIFIABLE`).
- Критерий (б): полный пересчёт `CLEARING` и `PAYMENT v2`; контрпример 7c: писатель, двигающий не то ребро, — (а) проходит, (б) падает. Эталонная модель по-прежнему не импортирует ничего из `book.py` (7a, `spec.md:757-760`).
- Одна операция — один конверт (Phase B 9): `effect_count` равен числу записей триггера; контрпроверка — операция с нулём эффектов даёт `COMPLETED` с `effect_count = 0`, а не отсутствие конверта; запись после `COMPLETED` — отказ базы.
- `RESTRICT` на `debts → participants/equivalents` — `T1524`/`T1533` без изменений.
- Hold (`T1546`): `FAILED` → `integrity_hold` → отказ платежу и клирингу; контрпроверка — другой эквивалент продолжает клириться.
