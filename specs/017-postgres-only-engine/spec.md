# 017 — PostgreSQL как единственный движок

- **Date:** 2026-09-21
- **Status:** DRAFT — черновик для вычитки владельца; реализация не авторизована
- **Status authority:** метка описательная; завершённость устанавливают success criteria и записанные evidence, а не поле статуса.
- **Owner surface:** `app/config.py` (`DATABASE_URL` и его умолчание), `app/db/session.py`, `app/db/sqlite_transaction_control.py` (удаление), `app/main.py:323-500` (три SQLite-пробы схемы), dialect-ветки в 8 модулях `app/` (50 вхождений; перечень — задача `T1703`) и упоминания `sqlite` в 17 модулях (109 вхождений, из них часть — датированные записи измерений в docstring, которые сохраняются), `scripts/{run_local,run_full_stack,verify_local}.ps1`, `scripts/{init_sqlite_db,check_sqlite_db,check_real_snapshot_debts_sqlite}.py` (удаление), `tests/conftest.py`, `tests/scratch_db.py`, `pytest.ini` (маркер `postgres`), `.github/workflows/quality.yml` (backend-часть `required-quality` и job `postgres`). **Исключено:** `api/openapi.yaml`, `migrations/` (новых миграций нет), любая денежная логика: ни одна строка `payments/`, `clearing/`, `ledger/` не меняется по существу, удаляются только ветки `if not self._is_postgres()` с сохранением Postgres-ветки дословно.
- **Origin:** решение владельца 2026-09-21 о рефакторинге ядра (`specs/README.md`, раздел «Рефакторинг ядра — программы 017–022»). Это первая программа последовательности: она не меняет поведение денег, а убирает второй диалект, из-за которого (а) дефолтный тир тестов не видит исходов, ради которых построен денежный путь, и (б) в программе 015 был отвергнут самый дешёвый механизм журнала — триггер БД.
- **Depends on:** закрытие 015 (`T1509`, `READY-TO-CLOSE: YES`, 2026-09-21). Ничего из 015 не переоткрывает.
- **Blocks:** 018 (журнал долгов триггером БД невозможен, пока дефолтный тир собирается `create_all` на SQLite — 015 `spec.md:670-675`) и 019 (SSI-корректность одной транзакции существует только на Postgres, `app/db/session.py:67-69`).

## Problem

Продукт работает на PostgreSQL (`docker-compose.yml:41`; решение `T1544`: «авторитетна PostgreSQL», 015 `spec.md:868`), а по умолчанию всё остальное работает на SQLite: `app/config.py:54-57` (`DEFAULT_SQLITE_DATABASE_URL`), `scripts/run_local.ps1:96-97`, `scripts/run_full_stack.ps1:95-96`, `scripts/verify_local.ps1:86` (`$defaultTestDb = "sqlite+aiosqlite:///..."`), `tests/conftest.py:39-44`. Из этого следуют три измеренных дефекта.

1. **Дефолтный тир тестов не способен увидеть исход, ради которого построен денежный путь.** Все advisory-локи короткого замыкаются вне Postgres: `app/core/payments/engine.py:182` (`if not self._is_postgres(): return`), то же на `:237`, `:308`; interlock клиринга — отдельная ветка по диалекту, `app/core/clearing/service.py:1523`. Это ровно правило §15 AGENTS.md «проверяйте, способен ли стенд увидеть тот исход, ради которого построен»: зелёный дефолтный прогон ничего не говорит о блокировках, а Postgres-тир CI идёт только по расписанию (`.github/workflows/quality.yml:156-159`). Ложное зелёное встроено в сам выбор диалекта.
2. **Три денежные потери родились из семантики SQLite, а не из протокола.** `app/db/sqlite_transaction_control.py:14-28` перечисляет их дословно: платёж `ABORTED` с сохранённым долгом `7.00000000`; тик, сохранивший два `COMMITTED`-платежа и долг `925.31` при отчёте об откате; 113 savepoint'ов в 63 тестах без открытой транзакции БД. Все три закрыты `T1525` **датированным принятием риска, а не пройденным ревью** (015 `spec.md:849`). Модуль на 182 строки, из которых 60 — docstring о том, почему pysqlite не открывает транзакцию, существует только чтобы SQLite вёл себя как Postgres. И всё равно не ведёт: локов на нём нет.
3. **Второй диалект — налог на каждый модуль ядра.** Ветвление по диалекту стоит в 8 модулях `app/` (50 вхождений `_is_sqlite` / `_is_postgres` / `dialect_name` / `get_backend_name`; слово `sqlite` — 109 вхождений в 17 модулях, замер 2026-09-21): `LEAST` против `min()` (`clearing/service.py:658-660`, `:787`), нормализация UUID для raw SQL (`:664`), `_PARAMSTYLES` журнала (`ledger/journal.py:2035-2042`), float-round-trip денег (`journal.py:2084-2101`), три стартовые пробы схемы в `app/main.py:323-500` (около 178 строк, включая regex-разбор DDL SQLite), `sqlite_busy_error_name` в пяти модулях. Оценка объёма — 900–1000 строк, чья единственная цель — эмуляция. Хуже строк — правило «каждый механизм обязан быть верен на обоих диалектах»: из-за него Phase B 015 **отвергла триггер БД** как писатель журнала (`spec.md:670-675`: «дефолтный SQLite-тир, собираемый `create_all`, проверял бы систему без писателя журнала — встроенное ложное зелёное») и построила вместо него 3 078 строк перехвата событий SQLAlchemy.

## Что решает программа

- **Один диалект.** `DATABASE_URL` без схемы `postgresql+asyncpg://` — отказ при старте с внятной ошибкой; умолчание из `app/config.py` удаляется вместе с `DEFAULT_SQLITE_DATABASE_URL`. Локальный запуск требует живой Postgres: `docker-compose.yml` уже поднимает `postgres:16-alpine`; стенд владельца живёт в WSL2. Скрипты запуска перестают подставлять SQLite и требуют URL явно, с подсказкой на `docker compose up db`.
- **Один тир тестов.** `TEST_DATABASE_URL` обязателен и обязан быть Postgres; страж `tests/conftest.py:39-48` (только `geov0_test_*`) и `:76-89` сохраняются. Маркер `postgres` теряет смысл: **каждый** DB-тест идёт на Postgres. Маркер удаляется из `pytest.ini`, `scripts/verify_local.ps1` и файлов; суффикс `_postgres` в именах файлов остаётся историческим, переименование не делается (§14: не смешивать классы cleanup). Маркер `slow` остаётся.
- **Одна стратегия изоляции тестов.** Из `db_session` (`tests/conftest.py:326-424`) остаётся только non-SQLite ветвь (внешняя транзакция плюс savepoint, откат в конце); SQLite-ветвь с `engine.dispose()` и циклом на «database is locked» (`:353`, `:363`, `:375-403`) удаляется. Схема строится **один раз** на сессию через `alembic upgrade head` в шаблонную БД, тестовые БД создаются `CREATE DATABASE ... TEMPLATE`. Это закрывает `T1541` (схема строилась трижды, около 17 с) без отдельной задачи.
- **CI видит Postgres на каждом PR.** Backend-часть `required-quality` переезжает на `ubuntu-latest` с сервисом `postgres:16` (как уже сделано в job `postgres`, `quality.yml:156-178`); UI-часть остаётся где есть. Job `postgres` по расписанию упраздняется, его селекторы входят в обязательный тир. Это изменение механизма проверки, то есть триггер внешнего ревью по §15.
- **Удаление.** `app/db/sqlite_transaction_control.py`; три пробы в `app/main.py:323-500`; `scripts/init_sqlite_db.py`, `scripts/check_sqlite_db.py`, `scripts/check_real_snapshot_debts_sqlite.py`; `tests/scratch_db.py::install_test_sqlite_pragmas`; все ветки `if not self._is_postgres()` / `_is_sqlite`. Postgres-ветка остаётся **дословно**, чтобы diff денежного кода читался как удаление строк, а не как правка логики.
- **Храповик.** Тест-гард `tests/unit/test_p017_no_second_dialect.py` из двух частей: (а) ветвления по диалекту в исполняемом коде `app/` (`_is_sqlite` / `_is_postgres` / `dialect_name` / `get_backend_name` / импорт `aiosqlite`) — константа `0`, сегодня `50`; (б) слово `sqlite` вне docstring и комментариев — константа `0`, сегодня отдельный замер в `T1707`; датированные записи измерений в docstring (например `app/db/journal_tables.py:270-282`, `T1526`/`T1530`) сохраняются по §1 и в подсчёт не входят. Плюс **контрпроверка** (§9 anti-vacuum): тот же сканер, направленный на зафиксированный фрагмент с одним вхождением каждого вида, находит его. Гард проверяет форму, а не истину: он не докажет, что оставшийся код корректен на Postgres, это делают тесты корзин A/B/C.

## Non-goals

- Не меняет ни одного денежного правила, ни одной схемы, ни одной миграции. `Numeric(20,8)`, CHECK-ограничения, `RESTRICT` — как есть.
- Не убирает advisory-локи, `prepare_locks`, interlock клиринга и журнал 015: их судьбу решают 018–020; здесь у них лишь исчезает ветка `if not postgres`.
- Не трогает `api/openapi.yaml` и wire-контракты.
- Не вводит testcontainers, embedded Postgres или иной новый инструмент: стенд — `docker compose` или внешний URL, как сегодня у Postgres-тира.
- Не переименовывает файлы `*_postgres.py` и не чистит архивы и `_audit*`.

## Проверка на переусложнение (§19.2) — 2026-09-21

1. **Какую наблюдаемую потерю это предотвращает?** Три потери из `sqlite_transaction_control.py:14-28` воспроизведены (`925.31`, `7.00000000`) и существуют только на диалекте, на котором продукт не работает. Плюс ложное зелёное: тир, в котором локи — no-op (`engine.py:182`). Потеря названа через данные, а не через механизм.
2. **Что говорит протокол?** `docs/ru/09-decisions-and-defaults.md` и `T1544`: авторитетна PostgreSQL. Advisory-локи, `FOR UPDATE`, `SERIALIZABLE` (`app/config.py:68`) — все примитивы, на которых стоят решения 2026-08-11, есть только в Postgres. Протокол нигде не требует SQLite.
3. **Кто противник?** Никакого: программа ничего не защищает, она удаляет.
4. **Что дешевле и чего ему не хватает?** (а) Оставить SQLite только для unit-тестов без БД: таким тестам БД не нужна вовсе, диалект для них пуст, экономии нет, а два диалекта остаются. (б) Оставить SQLite как dev-БД, Postgres для тестов: тогда стартовые пробы `main.py`, `sqlite_transaction_control` и dialect-ветки остаются в продовом коде ради окружения, в котором продукт не работает, и триггер 018 всё ещё нельзя объявить обязательным. Оба варианта не закрывают потерю 1.
5. **Цена, числом.** Новых сущностей: 0 (один тест-гард). Удаляется: 1 модуль (182 строки, точно), около 178 строк `main.py` (`:323-500`), 3 скрипта, 50 dialect-веток в 8 модулях (точно), файлы тестов корзины D-SQLite (8 по инвентаризации; файлов со `sqlite` в имени — 11, разница — тесты корзин A/E, которые остаются с переименованием или без) и по одному тесту `test_this_modules_engine_has_the_application_sqlite_pragmas` в пяти файлах симулятора. Меняется: `conftest.py` (одна стратегия), `verify_local.ps1`, `quality.yml`. **Цена, которую надо признать вслух (оценка по подсчёту фикстур, не замер):** порядка 450 тестовых функций в 118 файлах, сегодня не помеченных `postgres`, но трогающих БД, начинают требовать живой Postgres; точное число — в `T1706` по факту сборки. Замер времени тира — часть приёмки (`T1706`): тот же Postgres-селектор шёл 82 с и 669 с в зависимости от состояния WSL (015, `T1523`), поэтому «схема один раз на сессию» — не оптимизация, а условие пригодности тира.
6. **Крайние случаи.** Не берём ни одного: у «приложение стартовало на SQLite» после программы нет пути.

## Отменяемые решения владельца

Программа просит снять **одно** датированное решение и уточняет одно правило:

- **Снять:** Phase B 015, решение 1 (`spec.md:670-675`) в части «триггер отвергнут, потому что SQLite-тир его не увидит», и шаг 8 порядка первого среза (`:842-844`) «функциональное покрытие на SQLite». Основание — новая находка (потеря 1 в `## Problem`: тир не видит локов), а не новое прочтение.

Остальные решения 2026-08-11 (идентичность локов, пиннутое соединение клиринга, L1–L3) программа **не трогает**: они принадлежат 019 и 020.
