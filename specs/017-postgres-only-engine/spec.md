## Problem

Продукт работает на PostgreSQL (`docker-compose.yml:41`; решение `T1544`: «авторитетна PostgreSQL», 015 `spec.md:868`), а по умолчанию всё остальное работает на SQLite: `app/config.py:54-57` (`DEFAULT_SQLITE_DATABASE_URL`), `scripts/run_local.ps1:96-97`, `scripts/run_full_stack.ps1:95-96`, `scripts/verify_local.ps1:86` (`$defaultTestDb = "sqlite+aiosqlite:///..."`), `tests/conftest.py:39-44`. Из этого следуют три дефекта, и важно различать, какой из них **живой**.

1. **Живой дефект — покрытие проверки.** Дефолтный тир тестов не способен увидеть исход, ради которого построен денежный путь. Все advisory-локи короткого замыкаются вне Postgres: `app/core/payments/engine.py:182` (`if not self._is_postgres(): return`), то же на `:237`, `:308`; interlock клиринга — отдельная ветка по диалекту, `app/core/clearing/service.py:1523`; уровень изоляции ставится только для Postgres (`app/db/session.py:67-69`). Это ровно правило §15 AGENTS.md «проверяйте, способен ли стенд увидеть тот исход, ради которого построен»: зелёный дефолтный прогон ничего не говорит о блокировках, SSI и `FOR UPDATE`, а Postgres-тир CI идёт только по расписанию (`.github/workflows/quality.yml:156-159`). Phase B 015 уже записала, что scheduled-CI для этого недостаточен (`spec.md:842-844`).
2. **Исторические потери — закрыты, но их цена осталась.** `app/db/sqlite_transaction_control.py:14-28` перечисляет три денежных дефекта, рождённых семантикой SQLite: платёж `ABORTED` с сохранённым долгом `7.00000000`; тик, сохранивший два `COMMITTED`-платежа и долг `925.31` при отчёте об откате; 113 savepoint'ов в 63 тестах без открытой транзакции БД. Сегодня они **не достижимы**: контроль транзакций установлен в `app/db/session.py:61`, и закрытие `T1525` (015 `spec.md:849`, `:3246`) фиксирует, что подтверждённые дефекты исправлены до принятия остаточного риска. Что осталось — модуль на 182 строки, из которых 60 — docstring о том, почему pysqlite не открывает транзакцию, и класс дефектов, который может вернуться с любой новой точкой записи, потому что второй диалект требует отдельной правильности.
3. **Второй диалект — налог на каждый модуль ядра.** Ветвление по диалекту стоит в 8 модулях `app/` (50 вхождений `_is_sqlite` / `_is_postgres` / `dialect_name` / `get_backend_name`; слово `sqlite` — 109 вхождений в 17 модулях, замер 2026-09-21): `LEAST` против `min()` (`clearing/service.py:658-660`, `:787`), нормализация UUID для raw SQL (`:664`), `_PARAMSTYLES` журнала (`ledger/journal.py:2035-2042`), float-round-trip денег (`journal.py:2084-2101`), три стартовые пробы схемы в `app/main.py:323-500` (около 178 строк, включая regex-разбор DDL SQLite), `sqlite_busy_error_name` в пяти модулях. Оценка объёма — 900–1000 строк, чья единственная цель — эмуляция. Хуже строк — правило «каждый механизм обязан быть верен на обоих диалектах»: из-за него Phase B 015 **отвергла триггер БД** как писатель журнала (`spec.md:670-675`: «дефолтный SQLite-тир, собираемый `create_all`, проверял бы систему без писателя журнала — встроенное ложное зелёное») и построила вместо него 3 078 строк перехвата событий SQLAlchemy.

**Чему SQLite на самом деле служит — полная инвентаризация 2026-09-21.** Для развёртывания он **уже не используется**: `docker/docker-entrypoint.sh:13-19` завершает процесс на любой схеме URL кроме `postgresql`, драйвер `aiosqlite` стоит только в `requirements-dev.txt:5` и ни в один образ не попадает, `docker-compose.yml:41` задаёт Postgres. SQLite держит другое — путь «без установки чего-либо» для разработчика и тестировщика: оба лаунчера (`run_local.ps1:96`, `run_full_stack.ps1:95`; их `-ResetDb`/`reset-db` работают **только** на SQLite-файле, `run_full_stack.ps1:1032`), дефолтный тир тестов (151 файл неявно, 21 строит свой SQLite-движок, 11 названы `*sqlite*`), единственный e2e админки с настоящим бэкендом (`verify_admin_phase4_real_contract.ps1:57`), пять утилит без Postgres-двойника (`init_sqlite_db.py`, `check_sqlite_db.py`, `check_real_snapshot_debts_sqlite.py`, фаза анализа `run_simulator_run_and_analyze.py:348`, `t1525_savepoint_detector.py`) и два блока README «no-Docker quickstart (SQLite)». В CI на SQLite сидят ровно два job'а — `required-quality` и `simulator-super-smoke`; ни один job не поднимает Python-бэкенд за UI. Postgres-лаунчер уже есть, но только для симулятора (`scripts/run_real_simulator.ps1`), и есть runbook переносного Postgres без Docker (`docs/ru/backend/postgres-local-portable.md`). Честный объём: около **97 файлов** должны измениться (25 `app/`, 2 конфигурации, 13 скриптов, 1 workflow, 30 тестов и модулей поддержки, 27 документов). Ответ владельца на П1 («SQLite как способ запуска не нужен») с этой картиной согласуется, но означает: **удалить SQLite можно только после того, как у разработчика и тестировщика появится равноценный путь на Postgres одной командой.**

**Чем SQLite полезен сегодня и что из этого сохраняется.** Внешнее ревью нашло один случай, где SQLite-тест поймал мутацию, пропущенную Postgres-тиром (015 `spec.md:1748`): `tests/unit/test_p015_t1544_inject_refuses_a_deactivated_equivalent.py:51-80,115-124` записывает выполненный SQL и утверждает отказ **до** вставки конверта операции. Ассерт переносим и **сохраняется** в Postgres-форме; проверка только итоговых строк потеряла бы покрытие. Незаменимого второго оракула для Postgres-продукта ревью не нашло.

## Что решает программа

- **Один диалект.** `DATABASE_URL` без схемы `postgresql+asyncpg://` — отказ при старте с внятной ошибкой; умолчание из `app/config.py` удаляется вместе с `DEFAULT_SQLITE_DATABASE_URL`. Локальный запуск требует живой Postgres: `docker-compose.yml` уже поднимает `postgres:16-alpine`; стенд владельца живёт в WSL2. Скрипты запуска перестают подставлять SQLite и требуют URL явно, с подсказкой на `docker compose up db`. **Два URL со стороны хоста, не один:** имя `db` из compose видно только внутри сети контейнеров (`docker-compose.yml:8`, `:41`), а его база `geov0` — не тестовая; для тестов страж требует `geov0_test_*` на `127.0.0.1`. **Существующие файлы `.local-run/*.db` — пользовательские данные:** снятие движка не разрешает их удалять (`docs/ru/09-decisions-and-defaults.md:17-19`); скрипты их не трогают, README называет, что с ними делать.
- **Лаунчер полного стека на Postgres — в стадии 1, до удаления чего-либо** (решение по консультации Codex 2026-09-21, `ANSWER-1: ADOPT-WITH-CHANGES`). `run_full_stack.ps1` и `run_local.ps1` получают Postgres-путь: схема через общий вход миграций вместо `init_sqlite_db.py`, **наполнение настоящими операциями** (следующий пункт), админка и симулятор в real-режиме. **Граница сброса задаётся до замены удаления файла удалением базы** (P2 консультации): сегодня сброс отказывает на любом URL кроме своего SQLite-файла (`run_full_stack.ps1:1032`), а сброс тестовой Postgres-базы требует имени `geov0_test_*` и явного `GEO_TEST_ALLOW_DB_RESET=1` (`validate_test_database_url.py:112-118`). Dev-сброс получает ту же строгость: сбрасывается только база, **принадлежащая лаунчеру**, с проверяемым именем (`geov0_dev_<slug>`), после остановки процессов приложения; произвольный переданный URL сбросить нельзя, но запуститься на нём можно. **Проверка готовности перед стартом бэкенда** (P2): схема на `head`, ожидаемая популяция сида, baseline по каждому эквиваленту; автоматически инициализируется только свежая база лаунчера, незавершённая инициализация — отказ с инструкцией (baseline «усыновляет» необъяснённые остатки, `reconciliation.py:977`, поэтому молчаливый пересев недопустим). **Токен админа** передаётся каждому клиенту его переменной — `VITE_ADMIN_TOKEN` для админки (`realApi.ts:378`), `VITE_GEO_ACCESS_TOKEN` для симулятора (`useSimulatorApp.ts:543`); сегодня не передаётся никому, и при своём `ADMIN_TOKEN` в `.env` каждый вызов админки отвечает `403`. Обещание «без Docker» сохраняется через обновлённый runbook переносного Postgres. Две используемые утилиты осмотра (`check-db`, фаза анализа рана) переносятся на Postgres; остальные SQLite-утилиты удаляются с записью.
- **Данные для проверки админки производит сам продукт, а не заготовленный JSON** (вопрос владельца 2026-09-21: «может, проверять админку на реальных данных, а не тянуть прицеп с фикстурами»; решение по консультации Codex, `SEED-BY-RUNNING-THE-PRODUCT: ADOPT-WITH-CHANGES`, `ADMIN-FIXTURES-JSON: KEEP-SMALL-THROUGH-DOMAIN`, `WHEN: WITH-017-LAUNCHER`). Сегодня `scripts/seed_db.py` кладёт строки **прямо в таблицы** (`:133,146,187,331,359,426,487,597,635`), мимо доменных сервисов; генератор строит долги из линий доверия (`admin-fixtures/tools/seedlib.py:48`), а транзакции — отдельно (`generate_seed_greenfield_village_100.py:541`), то есть 248 засеянных транзакций не породили 374 засеянных долга; долги идут конвертом `SEED`, который критерий (б) сверки не проверяет (`reconciliation.py:38`), а baseline их «усыновляет» (`:977`). Для проекта, чья цель — «каждый долг объяснён записанными операциями», это та же фикстура, только в базе. Замена: **компактный упорядоченный рецепт операций** (участники, линии, платежи — не строки долгов и не выдуманные результаты транзакций), который `seed_db.py` исполняет через уже существующие подписанные доменные пути — `ParticipantService.create_participant` (`participants/service.py:24`), `TrustLineService.create` (`trustlines/service.py:117`), `PaymentService.create_payment` (`payments/service.py:371`), клиринг — с настоящими тестовыми парами ключей, символическими именами, разрешаемыми в PID, последовательно и с явной проверкой завершения каждого шага. Порядок на свежей базе лаунчера: каталог эквивалентов → **пустой baseline по каждому эквиваленту до первого движения денег** → операции → сверка обязана дать `PASSED` с нулевыми остатками baseline и ожидаемым покрытием операций (именно сверка `reconciliation.py:780`, а не `/integrity/verify`, который её не вызывает — `integrity.py:223-230`). Рецепт обязан зажечь экраны: ребро с доступной ёмкостью ниже 10 % (порог bottleneck — `admin.py:757,791`), исполненный клиринг, **отдельный выживший цикл долгов** (эндпоинт циклов показывает клирящиеся сейчас, а не исторические — `admin.py:2376`), активность в каждом выбранном эквиваленте. **Прогон симулятора источником сида не становится** (первая редакция предложения оркестратора это предлагала и опровергнута): сид рана берётся из времени и случайных байт (`runtime_utils.py:128-130`, `run_lifecycle.py:167-169`), такт ждёт одну секунду реального времени (`runtime_impl.py:907`), у Greenfield 50 тактов прогрева (`scenario.json:5533`), первый клиринг возможен с такта 25 и не гарантирован; тест детерминизма планировщика фиксирует сид вручную и отключает БД. Прогоны симулятора остаются для широких демонстраций и интеграционных проверок. Ждать 021 не нужно: подписанные пути уже есть, а зависимость проверки админки от корректности симулятора не вводится. Старый маленький сид `seeds/*.json` тоже пишет мимо домена (`seed_db.py:146,187`) и переписывается на тот же рецепт, а не остаётся как есть.
- **Тестовые сообщества на 50 и 100 участников сохраняются — как описание плюс рецепт, а балансы получаются из операций** (вопрос владельца 2026-09-21; решение по консультации Codex, `COMMUNITIES-PRESERVED: YES-WITH-CHANGES`, `ORDER-BOOK: COMMITTED`, `DEFINITION-FORMAT: OWN-FORMAT`, `DEV-KEYS: GENERATED-PER-RUN`, `BALANCE-POSTCONDITIONS: STRUCTURAL-ONLY`). ## Проверка на переусложнение (§19.2) — 2026-09-21, уточнено по внешнему ревью

1. **Какую наблюдаемую потерю это предотвращает?** Честный ответ — двухчастный. **Живая** проблема — покрытие: тир, в котором локи, SSI и `FOR UPDATE` не наблюдаемы (`engine.py:182`, `session.py:67-69`), и Postgres только по расписанию; это дефект измерителя, а не движение денег. **Исторические** потери из `sqlite_transaction_control.py:14-28` (`925.31`, `7.00000000`) воспроизведены, закрыты `T1525` и сегодня недостижимы (`session.py:61`); они — цена второго диалекта, а не текущая потеря, и спека их таковой не выдаёт. Отсюда следствие для владельца: программа авторизуется как **устранение ложного зелёного и долга сопровождения**, а не как починка живой денежной потери, и её место в очереди определено тем, что 018/019 без неё невозможны в выбранной форме.
2. **Что говорит протокол?** Атомарность и корректность долга — требования (`02-protocol-spec.md:208-211`); PostgreSQL как единственный движок — **реализационный выбор**, протокол его не требует. Что требует практика проекта: `T1544` («авторитетна PostgreSQL»), advisory-локи, `FOR UPDATE`, `SERIALIZABLE` (`app/config.py:68`) — примитивы решений 2026-08-11 существуют только там.
3. **Кто противник?** Никакого: программа ничего не защищает, она упрощает и чинит измеритель.
4. **Что дешевле и чего ему не хватает?** Три альтернативы, две из них добавлены по внешнему ревью. **(а) Сначала сделать существующий Postgres-job обязательным на PR** (`quality.yml:156`, `:203`, `:218` — job и селекторы уже есть), SQLite оставить: закрывает живой дефект 1 за один срез без миграции 450 тестов. **Это стадия 1 программы**; чего ей не хватает — двух диалектов в ядре остаётся ровно столько же, триггер 018 по-прежнему нельзя объявить обязательным в дефолтном тире, и Phase B `:670-675` остаётся в силе. **(б) Переходный ограниченный SQLite-тир** только для неденежных persistence-тестов (поиск участников `tests/integration/test_participants_search.py:40`, обновление токена `tests/integration/test_auth_refresh.py:15`), всё денежное — на Postgres: остаточная цена — второй драйвер, второй путь построения схемы, вторая стратегия фикстур и граница покрытия, которую надо охранять; спека этот вариант отклоняет как постоянное обязательство, но допускает как **временное состояние между стадиями 1 и 3**. **(в) Полное приложение на обоих диалектах** (сегодня): альтернативные реализации журнала, контекста и конкурентности — самый дорогой вариант, и ревью его не рекомендует.

- **Подметание сирот уничтожало базу соседней задачи.** Слаг `a__b` валиден, и задача `a` дропала `geov0_test_a__b` — воспроизведено на живом Postgres. Разделитель `__` **зарезервирован**: имя тира не может его содержать, поэтому `<тир>__<суффикс>` по построению принадлежит `<тиру>`. Владение задаётся пространством имён, а не префиксом строки; сузить сам предикат подметания нельзя — имя `geov0_test_a__b` по одному только имени неразличимо между тиром задачи `a__b` и клоном задачи `a`. Цена названа: слаг для Postgres-тира не может содержать `__`; ни один слаг репозитория и CI не затронут, ограничение записано в `AGENTS.md` §5.
- Гард «отказ, а не skip» **сам скипался** на мутации, которую обещал ловить (`Skipped` наследует `BaseException`). Гарды workflow читали только `job.get("if")` и были слепы к шаговым `if:` и `continue-on-error` — обход защиты, а не её отсутствие (§15).

## Changelog

**2026-09-24 — принцип для правил, которые ограничение схемы делает недостижимыми на Postgres (решение оркестратора, стадия 3).** На Postgres стоят CHECK-ограничения, которых нет в SQLite: например, `chk_debt_journal_entries_delta_arithmetic` требует `delta = after - before`. Из-за них часть проверок денежного кода — сравнение дельты при readback журнала (`journal.py` `_effect_code` / `_stored_entry_code`), построчная проверка арифметики в сверке — на базе тира **сработать не может**, и мутация такой проверки оставляет тир зелёным.

**Решение: такое правило остаётся измеренным одним тестом на одноразовом клоне, где ограничение снято, а не удаляется вместе с тестом.** Сначала оркестратор решил обратное для сверки — удалить тест как проверяющий недостижимое состояние. Исполнитель среза S2b для журнала поступил иначе, и его довод сильнее: предмет не гипотетический путь, под который строится новый код (§19.2, п. 6), а **правило, которое уже существует** в денежном коде. Удалить его тест — оставить существующий код денежного пути неизмеренным, и сломать его можно будет молча. Ограничение схемы может снять будущая миграция; правило журнала — независимая проверка ровно против этого. Цена — один тест и одна сборка шаблона режима B за сессию. Срез удаления применяет тот же принцип к построчной проверке в сверке (`test_p015_step5a_reconciliation.py:427`).
