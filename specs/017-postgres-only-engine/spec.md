## Problem

Продукт работает на PostgreSQL (`docker-compose.yml:41`; решение `T1544`: «авторитетна PostgreSQL», 015 `spec.md:868`), а по умолчанию всё остальное работает на SQLite: `app/config.py:54-57` (`DEFAULT_SQLITE_DATABASE_URL`), `scripts/run_local.ps1:96-97`, `scripts/run_full_stack.ps1:95-96`, `scripts/verify_local.ps1:86` (`$defaultTestDb = "sqlite+aiosqlite:///..."`), `tests/conftest.py:39-44`. Из этого следуют три дефекта, и важно различать, какой из них **живой**.

1. **Живой дефект — покрытие проверки.** Дефолтный тир тестов не способен увидеть исход, ради которого построен денежный путь. Все advisory-локи короткого замыкаются вне Postgres: `app/core/payments/engine.py:182` (`if not self._is_postgres(): return`), то же на `:237`, `:308`; interlock клиринга — отдельная ветка по диалекту, `app/core/clearing/service.py:1523`; уровень изоляции ставится только для Postgres (`app/db/session.py:67-69`). Это ровно правило §15 AGENTS.md «проверяйте, способен ли стенд увидеть тот исход, ради которого построен»: зелёный дефолтный прогон ничего не говорит о блокировках, SSI и `FOR UPDATE`, а Postgres-тир CI идёт только по расписанию (`.github/workflows/quality.yml:156-159`). Phase B 015 уже записала, что scheduled-CI для этого недостаточен (`spec.md:842-844`).
2. **Исторические потери — закрыты, но их цена осталась.** `app/db/sqlite_transaction_control.py:14-28` перечисляет три денежных дефекта, рождённых семантикой SQLite: платёж `ABORTED` с сохранённым долгом `7.00000000`; тик, сохранивший два `COMMITTED`-платежа и долг `925.31` при отчёте об откате; 113 savepoint'ов в 63 тестах без открытой транзакции БД. Сегодня они **не достижимы**: контроль транзакций установлен в `app/db/session.py:61`, и закрытие `T1525` (015 `spec.md:849`, `:3246`) фиксирует, что подтверждённые дефекты исправлены до принятия остаточного риска. Что осталось — модуль на 182 строки, из которых 60 — docstring о том, почему pysqlite не открывает транзакцию, и класс дефектов, который может вернуться с любой новой точкой записи, потому что второй диалект требует отдельной правильности.
3. **Второй диалект — налог на каждый модуль ядра.** Ветвление по диалекту стоит в 8 модулях `app/` (50 вхождений `_is_sqlite` / `_is_postgres` / `dialect_name` / `get_backend_name`; слово `sqlite` — 109 вхождений в 17 модулях, замер 2026-09-21): `LEAST` против `min()` (`clearing/service.py:658-660`, `:787`), нормализация UUID для raw SQL (`:664`), `_PARAMSTYLES` журнала (`ledger/journal.py:2035-2042`), float-round-trip денег (`journal.py:2084-2101`), три стартовые пробы схемы в `app/main.py:323-500` (около 178 строк, включая regex-разбор DDL SQLite), `sqlite_busy_error_name` в пяти модулях. Оценка объёма — 900–1000 строк, чья единственная цель — эмуляция. Хуже строк — правило «каждый механизм обязан быть верен на обоих диалектах»: из-за него Phase B 015 **отвергла триггер БД** как писатель журнала (`spec.md:670-675`: «дефолтный SQLite-тир, собираемый `create_all`, проверял бы систему без писателя журнала — встроенное ложное зелёное») и построила вместо него 3 078 строк перехвата событий SQLAlchemy.

**Чем SQLite полезен сегодня и что из этого сохраняется.** Внешнее ревью нашло один случай, где SQLite-тест поймал мутацию, пропущенную Postgres-тиром (015 `spec.md:1748`): `tests/unit/test_p015_t1544_inject_refuses_a_deactivated_equivalent.py:51-80,115-124` записывает выполненный SQL и утверждает отказ **до** вставки конверта операции. Ассерт переносим и **сохраняется** в Postgres-форме; проверка только итоговых строк потеряла бы покрытие. Незаменимого второго оракула для Postgres-продукта ревью не нашло.

## Что решает программа

- **Один диалект.** `DATABASE_URL` без схемы `postgresql+asyncpg://` — отказ при старте с внятной ошибкой; умолчание из `app/config.py` удаляется вместе с `DEFAULT_SQLITE_DATABASE_URL`. Локальный запуск требует живой Postgres: `docker-compose.yml` уже поднимает `postgres:16-alpine`; стенд владельца живёт в WSL2. Скрипты запуска перестают подставлять SQLite и требуют URL явно, с подсказкой на `docker compose up db`. **Два URL со стороны хоста, не один:** имя `db` из compose видно только внутри сети контейнеров (`docker-compose.yml:8`, `:41`), а его база `geov0` — не тестовая; для тестов страж требует `geov0_test_*` на `127.0.0.1`. **Существующие файлы `.local-run/*.db` — пользовательские данные:** снятие движка не разрешает их удалять (`docs/ru/09-decisions-and-defaults.md:17-19`); скрипты их не трогают, README называет, что с ними делать.
- **Один тир тестов.** `TEST_DATABASE_URL` обязателен и обязан быть Postgres; страж `tests/conftest.py:39-48` (только `geov0_test_*`) и `:76-89` сохраняются. Маркер `postgres` теряет смысл: **каждый** DB-тест идёт на Postgres. Маркер удаляется из `pytest.ini`, `scripts/verify_local.ps1` и файлов; суффикс `_postgres` в именах файлов остаётся историческим, переименование не делается (§14: не смешивать классы cleanup). Маркер `slow` остаётся.
- **Две стратегии изоляции, а не одна.** Внешнее ревью показало, что оставить только savepoint-фикстуру нельзя: она даёт сессию, привязанную к соединению (`tests/conftest.py:409-411`), а клиринг на Postgres такую сессию **отвергает** (`app/core/clearing/service.py:1530-1539`, до 019 это поведение живо); тесты снапшотов симулятора ждут чужой коммит, который внутри одного `SERIALIZABLE`-снимка не виден никогда (`tests/integration/test_simulator_real_snapshot_db_enrichment.py:59-69`); тест перезапуска требует настоящих коммитов, видимых другому процессу (`tests/integration/test_p015_t1523_restart_after_commit_postgres.py:174`). Поэтому: режим **A** — внешняя транзакция плюс savepoint, откат в конце, для тестов, где приложение не владеет соединением; режим **B** — одноразовая база с настоящими корневыми коммитами для клиринга, конкурентности, фоновых задач и перезапуска. Потребители каждого режима перечисляются в инвентаре `T1706` **до** авторизации. Семантика транзакций приложения под фикстуры не подгоняется.
- **Схема — один раз, с bootstrap.** Порядок: bootstrap `alembic_version VARCHAR(128)` (`tests/migrated_schema.py:47-50`, `:81`; решение `T1535` 2026-09-20 сохраняется — голый `alembic upgrade head` падает на `010→011`) → `alembic upgrade head` в шаблонную базу → отключение от шаблона → `CREATE DATABASE ... TEMPLATE` на задачу или тест режима B, с очисткой и требованием права `CREATEDB` у тестовой роли. Это провизионирование живёт в `tests/migrated_schema.py`, а не в `conftest.py`, и ставится **до** массовой миграции тестов. `T1541` (схема строится трижды) закрывается только если консолидируются **и** две pytest-сессии CI (`quality.yml:198-226`), **и** bootstrap entrypoint'а — без потери покрытия самого entrypoint'а (015 `spec.md:865`); шаблон сам по себе этого не делает.
- **CI видит Postgres на каждом PR.** Backend-часть `required-quality` переезжает на `ubuntu-latest` с сервисом `postgres:16` (как уже сделано в job `postgres`, `quality.yml:156-178`); UI-часть остаётся где есть. Job `postgres` по расписанию упраздняется, его селекторы входят в обязательный тир. Job `simulator-super-smoke` (`quality.yml:677-708`) сегодня гоняет backend-тесты без Postgres и без URL — он получает сервис и URL в том же срезе, иначе обязательный Postgres его сломает. Это изменение механизма проверки, то есть триггер внешнего ревью по §15.
- **Порядок реализации — три стадии, каждая ревьюема отдельно** (условие внешнего ревью): **(1)** провизионирование и обязательный Postgres-гейт на PR, SQLite ещё жив — это закрывает живой дефект 1 раньше всего остального; **(2)** миграция тестов на два режима фикстур по инвентарю, замер времени тира; **(3)** удаление совместимости — модуль, пробы, ветки, скрипты, зависимость. Стадия 3 не начинается, пока бюджет времени тира (`T1706`) не принят владельцем.
- **Удаление (стадия 3).** `app/db/sqlite_transaction_control.py`; три пробы в `app/main.py:323-500`; `scripts/init_sqlite_db.py`, `scripts/check_sqlite_db.py`, `scripts/check_real_snapshot_debts_sqlite.py`; SQLite-ветка `scripts/run_simulator_run_and_analyze.py:348`; `aiosqlite` из `requirements-dev.txt:5`; `tests/scratch_db.py::install_test_sqlite_pragmas`; все ветки `if not self._is_postgres()` / `_is_sqlite`. Postgres-ветка остаётся **дословно**, чтобы diff денежного кода читался как удаление строк, а не как правка логики.
- **Храповик.** Тест-гард `tests/unit/test_p017_no_second_dialect.py` из двух частей: (а) ветвления по диалекту в исполняемом коде `app/` — константа `0`, сегодня `50`; в перечень входят не только именованные helper'ы, но и прямые обращения `dialect.name` / `engine.dialect` / `url.get_backend_name()` и сравнение со строкой `"postgresql"`/`"sqlite"` — иначе обычная запись `if engine.dialect.name != "postgresql": return` прошла бы мимо; (б) слово `sqlite` в исполняемом коде — константа `0`; docstring отличаются от исполняемых строк **по AST** (`ast.get_docstring`), а не по тройным кавычкам, чтобы SQL в строковых литералах не прятался; датированные записи измерений в docstring (например `app/db/journal_tables.py:270-282`, `T1526`/`T1530`) сохраняются по §1 через узкий allow-list. Контрпроверки (§9 anti-vacuum) — и положительные (сканер находит подложенный фрагмент каждого вида), и отрицательные (сканер не срабатывает на allow-list и на слово внутри docstring). Гард проверяет форму, а не истину: он не докажет, что оставшийся код корректен на Postgres, это делают тесты корзин A/B/C; наблюдение SQL-вызова лока доказывает исполнение ветки, а не исключение — конкурентные расписания корзины B остаются рядом.

## Non-goals

- Не меняет ни одного денежного правила, ни одной схемы, ни одной миграции. `Numeric(20,8)`, CHECK-ограничения, `RESTRICT` — как есть.
- Не убирает advisory-локи, `prepare_locks`, interlock клиринга, `version_id_col` и журнал 015: их судьбу решают 018–020; здесь у них лишь исчезает ветка `if not postgres`.
- Не трогает `api/openapi.yaml` и wire-контракты.
- Не вводит testcontainers, embedded Postgres или иной новый инструмент: стенд — `docker compose` или внешний URL, как сегодня у Postgres-тира.
- Не переименовывает файлы `*_postgres.py` и не чистит архивы и `_audit*`.
- Не удаляет пользовательские SQLite-файлы и не берёт на себя миграцию данных из них: у dev-БД по решению `09:14-19` данных, требующих переноса, нет; если владелец назовёт такой набор, это отдельная задача.

## Проверка на переусложнение (§19.2) — 2026-09-21, уточнено по внешнему ревью

1. **Какую наблюдаемую потерю это предотвращает?** Честный ответ — двухчастный. **Живая** проблема — покрытие: тир, в котором локи, SSI и `FOR UPDATE` не наблюдаемы (`engine.py:182`, `session.py:67-69`), и Postgres только по расписанию; это дефект измерителя, а не движение денег. **Исторические** потери из `sqlite_transaction_control.py:14-28` (`925.31`, `7.00000000`) воспроизведены, закрыты `T1525` и сегодня недостижимы (`session.py:61`); они — цена второго диалекта, а не текущая потеря, и спека их таковой не выдаёт. Отсюда следствие для владельца: программа авторизуется как **устранение ложного зелёного и долга сопровождения**, а не как починка живой денежной потери, и её место в очереди определено тем, что 018/019 без неё невозможны в выбранной форме.
2. **Что говорит протокол?** Атомарность и корректность долга — требования (`02-protocol-spec.md:208-211`); PostgreSQL как единственный движок — **реализационный выбор**, протокол его не требует. Что требует практика проекта: `T1544` («авторитетна PostgreSQL»), advisory-локи, `FOR UPDATE`, `SERIALIZABLE` (`app/config.py:68`) — примитивы решений 2026-08-11 существуют только там.
3. **Кто противник?** Никакого: программа ничего не защищает, она упрощает и чинит измеритель.
4. **Что дешевле и чего ему не хватает?** Три альтернативы, две из них добавлены по внешнему ревью. **(а) Сначала сделать существующий Postgres-job обязательным на PR** (`quality.yml:156`, `:203`, `:218` — job и селекторы уже есть), SQLite оставить: закрывает живой дефект 1 за один срез без миграции 450 тестов. **Это стадия 1 программы**; чего ей не хватает — двух диалектов в ядре остаётся ровно столько же, триггер 018 по-прежнему нельзя объявить обязательным в дефолтном тире, и Phase B `:670-675` остаётся в силе. **(б) Переходный ограниченный SQLite-тир** только для неденежных persistence-тестов (поиск участников `tests/integration/test_participants_search.py:40`, обновление токена `tests/integration/test_auth_refresh.py:15`), всё денежное — на Postgres: остаточная цена — второй драйвер, второй путь построения схемы, вторая стратегия фикстур и граница покрытия, которую надо охранять; спека этот вариант отклоняет как постоянное обязательство, но допускает как **временное состояние между стадиями 1 и 3**. **(в) Полное приложение на обоих диалектах** (сегодня): альтернативные реализации журнала, контекста и конкурентности — самый дорогой вариант, и ревью его не рекомендует.
5. **Цена, числом.** Новых сущностей: 0 (один тест-гард, одна функция провизионирования). Удаляется: 1 модуль (182 строки, точно), около 178 строк `main.py` (`:323-500`), 3 скрипта и одна ветка анализатора, 50 dialect-веток в 8 модулях (точно), одна dev-зависимость, файлы тестов корзины D-SQLite (8 по инвентаризации; файлов со `sqlite` в имени — 11, разница — тесты корзин A/E, которые остаются) и по одному тесту `test_this_modules_engine_has_the_application_sqlite_pragmas` в пяти файлах симулятора.
