# 047 — Периодическая проверка целостности: пик памяти не растёт с историей

- **Date:** 2026-10-18, против `main` на `c53a254f`.
- **Status:** **ЗАВЕДЕНА 2026-10-18 решением советника по находке 044 ст. 2; реализация — после закрытия 044 ст. 2 и слова владельца** (находка касается денежного ядра — программа 015; владелец информирован сводкой 2026-10-18). Денежной потери нет (класс 2 по §19.5); потеря — память процесса публичного демо, растущая линейно с историей операций.
- **Status authority:** метка описательная; завершённость устанавливают записанные evidence с SHA, командой и exit code, а не поле статуса.
- **Owner surface.** `app/core/ledger/reconciliation.py` (`verify_journal_equals_change` `:969`, `_journal_sums` `:354`, `_operations` `:458`), `app/core/maintenance_jobs.py` (цикл чекпойнта `:150-170`, интервал `INTEGRITY_CHECKPOINT_INTERVAL_SECONDS` `app/config.py:317`), тесты сверки 015 (`tests/integration/test_p015_*`, `tests/unit/test_p015_step5*`), новый тест пика памяти, `docs/ru/backend/**` в части чекпойнта. **Исключено:** семантика проверки (что сравнивается и с чем — не меняется), `Book`, журнал, триггеры БД, baseline, интервал и включённость чекпойнта по умолчанию (не ослаблять — принцип владельца «дрейф недопустим, проверки усиливать, не предупреждать»), симулятор (044).
- **Origin.** 044 стадия 2 (2026-10-18, агент Opus, `tracemalloc` на живом прогоне): RSS процесса растёт ступенями каждые 5 минут; с `INTEGRITY_CHECKPOINT_ENABLED=false` — плато ≈ 145 МБ; с чекпойнтом пик растёт 11 → 49 МБ при 1.5k → 7.4k операций (~6.5 КБ/операцию), и процесс удерживает RSS на максимуме. Причина: периодический чекпойнт читает **всю историю эквивалента** в память — все записи журнала и все операции с JSON-намерением (`_operations`, `_journal_sums`). Буфер SSE (2000 событий, ≈2.65 МБ) выходит на плато к 6-й минуте и утечкой не является.

## Problem

На публичном демо (044: отдельная одноразовая база, история растёт с каждым посетителем, автоудаления денежных строк нет) пик памяти чекпойнта растёт линейно: ~65 МБ на 10 тысяч операций; при 10 прогонах темпа 15 это часы, не дни. Сам чекпойнт при этом нужен: он и есть обнаружение дрейфа (015, §19.5 — «остановка допустима только когда стоит обнаружение»). Ослабить интервал или отключить — значит снять обнаружение ради памяти; это запрещено решением владельца.

**§19.2:** новая сущность не вводится — меняется реализация существующего верификатора; потеря — исчерпание памяти публичного сервера (воспроизводится замером 044); протокол не касается; противника нет; дешевле: (а) разрежать интервал — не закрывает рост, лишь растягивает; (б) перезапуск по порогу — операционная мера 044 (в), не починка; цена — один модуль, ~100–200 строк, тесты 015 без изменения семантики.

## Решения

1. **Сверка агрегатами на стороне БД.** Суммы журнала и суммы операций по эквиваленту считаются `SUM(...) GROUP BY` в PostgreSQL (или потоково порциями фиксированного размера там, где нужна поэлементная проверка, например разбор JSON-намерений) — результат проверки идентичен нынешнему: те же сравниваемые величины, те же коды расхождения, та же реакция (удержание эквивалента).
2. **Пик памяти чекпойнта ограничен константой**, не зависящей от числа операций: тест меряет `tracemalloc` пик на 1k и на 10k операций — отношение ≤ 1.5 (сегодня ≈ линейное).
3. **Интервал, включённость и семантика не меняются.** Любая правка, меняющая, *что* сравнивается, — не 047.
4. **Операторская мера до 047** (записана в 044): измеренный потолок RSS и правило замены одноразовой базы по числу операций — не отключение проверки.

## Non-goals

- Не менять `Book`, журнал, триггеры, baseline, коды расхождений, реакцию на расхождение.
- Не менять `INTEGRITY_CHECKPOINT_INTERVAL_SECONDS` и `INTEGRITY_CHECKPOINT_ENABLED` по умолчанию.
- Не чистить историю операций (автоудаление денежных строк запрещено).
- Не оптимизировать «заодно» другие проверки 015.

4. **Запрещено:** ослаблять ассерты 015; менять интервал ради зелёного замера; считать «память не растёт» по RSS без `tracemalloc`-пика; порционная обработка, которая меняет момент обнаружения расхождения (проверка остаётся атомарной по эквиваленту в одном снимке/транзакции).
