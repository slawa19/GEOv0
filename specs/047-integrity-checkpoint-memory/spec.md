# 047 — Сверка целостности: каденция по решению владельца (старт + сутки + ручная команда); пик памяти не растёт с историей

- **Date:** 2026-10-18, против `main` на `763f8b0a`; поправка 2026-10-18 (вечер) по решению владельца.
- **Status:** **АВТОРИЗОВАНА 2026-10-18 словом владельца («B — согласен»)** в части каденции и ручной команды (`T4701`–`T4702`); починка памяти (`T4703`) остаётся в программе как **несрочная** и идёт после них. Исполнение — у оркестратора через агентов, после слияния 044 ст. 2 (общие документы о чекпойнте).
- **Status authority:** метка описательная; завершённость устанавливают записанные evidence с SHA, командой и exit code, а не поле статуса.
- **Owner surface.** `app/config.py` (`INTEGRITY_CHECKPOINT_INTERVAL_SECONDS` — значение по умолчанию и датированная причина), `app/core/maintenance_jobs.py` (цикл чекпойнта `:150-170` — без изменения логики; стартовый прогон остаётся), новый `scripts/reconcile_debts.py` (ручная команда), `docs/ru/runbook-integrity-hold.md` §3 (вместо «следующий плановый прогон» — команда), `docs/ru/05-deployment.md` (каденция), `app/core/ledger/reconciliation.py` (`verify_journal_equals_change` `:969`, `_journal_sums` `:354`, `_operations` `:458`) — только для `T4703`, тесты сверки 015, новый тест пика памяти, тесты порога свежести (`reconciliation.py:1120-1135`, следует интервалу). **Исключено:** семантика сверки (что сравнивается и с чем; критерии (а)/(б); коды; реакция — удержание эквивалента), `Book`, журнал, триггеры БД, baseline, `POST /integrity/verify` (не превращать в запуск сверки без отдельного решения), симулятор (044), автоудаление денежных строк.
- **Origin.** 044 ст. 2 (`tracemalloc`): рост RSS публичного демо — периодический чекпойнт читает всю историю эквивалента в память каждые 5 минут (~6.5 КБ/операцию, пик 11 → 49 МБ при 1.5k → 7.4k операций; без чекпойнта плато ≈ 145 МБ). Владелец 2026-10-18: «раз в 5 минут (и вообще периодически) запускать проверку целостности — это вообще ненужная операция; это и есть overengineering»; просил оценить достаточность защиты при транзакциях и оставить ручную проверку или редкую автоматическую. Аналитик (Fable, read-only, 2026-10-18; якоря перепроверены советником): см. Findings.

## Problem

Каденция 300 с не оправдана ничем воспроизводимым и стоит O(история) каждые 5 минут навсегда; при 0.1–1 tx/s прогон через недели становится длиннее интервала, а пик памяти растёт с историей (044). При этом **сам верификатор нужен**: он — единственное обнаружение правок в обход приложения и условие остановки программ по §19.5 («остановка допустима только когда стоит обнаружение»).

Периодичность не ловит ни одного класса**: все репродьюсеры вызывают один прогон; тестов цикла нет (`git grep "_integrity_loop(" -- tests` → 0). 300 с унаследовано от первого кода репозитория (`a97964ca`, 2026-01-04) и таблицы протокола `docs/ru/02-protocol-spec.md:2236-2246` «Zero-Sum — каждые 5 мин», написанной для проверки, снятой 2026-09-11 как вакуумная. - **F-047-4. Реакция не зависит от периодичности:** `react_to_failed` вызывается внутри `run_scheduled_reconciliation` (`reconciliation.py:1382-1466`) при любом вызове; удержание читается денежным путём из колонки; снятие перепроверяет эквивалент под блокировкой (`equivalents.py:206-234`). - **F-047-5. Ручного запуска сверки нет.** `POST /api/v1/integrity/verify` гоняет только `trust_limits`/`debt_symmetry` и сверку не запускает (`app/api/v1/integrity.py:306-320`, 024 `T2412.1`); единственный программный вход — `run_scheduled_reconciliation`, вызываемый только из `maintenance_jobs.py:61`.
- **F-047-6. Цена прогона:** ≈ 14 операторов на эквивалент, вся история читается (журнал, операции с JSON, транзакции, долги и линии дважды); замер 015 5b: 10k строк — 1.51 с, 100k — 16.7 с (до 030 S3a); память ~6.5 КБ/операцию (044). Писателей не блокирует (снимок `REPEATABLE READ READ ONLY`).

## Решение владельца 2026-10-18 — вариант B

1. **Прогон при старте процесса остаётся** (`maintenance_jobs.py:150-153`, `reason="startup"`).
2. **Автоматический прогон — раз в сутки:** `INTEGRITY_CHECKPOINT_INTERVAL_SECONDS` по умолчанию `86400` с датированной причиной в `config.py` (порог свежести `2 × интервал + 5 мин` следует автоматически, `reconciliation.py:1120-1135`); развёртывания могут задать иное значение. Логика цикла не меняется.
3. **Ручная команда** `scripts/reconcile_debts.py` (~40 строк, по образцу `take_reconciliation_baseline.py`): вызывает `run_scheduled_reconciliation(AsyncSessionLocal, equivalent_ids=…)` **с реакцией 5c**, печатает по эквиваленту статус последней строки `debt_reconciliation_results`, `findings`, `missing_evidence`, `entries_read`; exit `0` — все `PASSED`, `1` — `FAILED`/`UNVERIFIABLE`, `2` — ошибка прогона; `--equivalent CODE` (повторяемый), `--all`. Оговорка оператору: та же база через `DATABASE_URL`; при одновременном плановом прогоне возможен устаревший вердикт, опубликованный последним (`record_outcome`, `reconciliation.py:1050-1080`) — при суточной каденции пренебрежимо. Runbook §3 п. 2: вместо «следующий плановый прогон» — эта команда.
4. **Не делать:** отключать цикл (`ENABLED=false` снял бы и стартовый прогон); проверку «по событию» (связывает верификатор с денежным путём — названо дрейфом в банк, `015/spec.md:1850`); «при простое» (новый механизм); удалять верификатор (снимает единственное обнаружение в обход приложения, нарушает §19.5).
5. **Починка памяти (`T4703`) остаётся, но несрочная:** потеря переквалифицирована на «процесс с историей ≥ 10k операций при любой каденции»; сверка агрегатами в SQL/порциями с идентичной семантикой; §15 Codex + **Argon триггер 2** — только для `T4703` (денежная верификация), не для каденции.

Следствие: чужая открытая транзакция с блокировкой последней строки результата одного эквивалента вешала `record_outcome` навсегда, следующие эквиваленты (с настоящим расхождением) не сверялись и не удерживались, задание оставалось `running`, `/health` — здоровым, деньги двигались. Починка без новой сущности: (1) срок попытки `INTEGRITY_ATTEMPT_TIMEOUT_SECONDS` вокруг `_run_integrity_checkpoints_once` (`asyncio.timeout`) → `failed`, событие `<reason>_timed_out`, `False` — никогда не «проверено»; закрытие сессий экранировано и откатывает незафиксированное, замок Redis снимается по токену или истекает; (2) `SET LOCAL lock_timeout`/`statement_timeout` (`bound_the_waits`, `reconciliation.py`) на каждой транзакции планового прогона — перечень, сверка, публикация, реакция — и на транзакции чекпойнтов этого задания; денежные писатели не тронуты; 55P03/57014 — ошибка только этого эквивалента (`sqlstate` в логе `debt_reconciliation.error`), прогон не завершён, **следующий эквивалент сверяется** (выбран дизайн «провалить эквивалент и продолжить»); (3) `call_timeout_seconds` у `redis_distributed_lock` только для замка целостности: `SET` сверх срока → `TimeoutError` (не `ConflictException`, читаемый как «занято»), затем ограниченное compare-and-delete своего токена; освобождение сверх срока бросается, ключ истекает по TTL. **Замеры** (эта машина, 2026-10-18; одноразовый клон, один эквивалент, 8 000 платежей через `PaymentService`, ≈9 600 записей журнала; три прогона `run_scheduled_reconciliation`): прогон 0.61 / 0.67 / 0.61 с; самый медленный оператор — чтение операций с намерениями, 140 / 119 / 125 мс; следующий — журнал, 18–72 мс; вставка результата 1.6 мс. Вместе с прежними: 044 ст. 2 — 4.0 → 11.1 с при 1 522 → 7 436 операциях симулятора (под `tracemalloc`; ≈1.5 с на 1 000 — худший измеренный темп), ≈6.5 КБ пика на операцию; 015 5b — 19.4 с при 100 000 строк журнала. **Числа и запас:** срок попытки 1 800 с — при худшем темпе ≈1.2 млн операций, на которых пик памяти (≈7.8 ГБ) кончается раньше срока, ≈90× крупнейшего измеренного прогона; `lock_timeout` 60 с — законно дольше всех держит ожидаемую блокировку снятие удержания админом (эквивалент `FOR UPDATE` и последний результат `FOR SHARE` на одну полную сверку, 11.1 с при худшем измеренном) и денежный писатель (`FOR SHARE` эквивалента, срок платежа 10 с) — запас ≈5× и 6×; `statement_timeout` 120 с — 140 мс при 8 000 операциях линейно ≈17.5 с при 1 млн, запас ≈7×; Redis 5 с — прецедент `renew_timeout_seconds` аренды клиринга на том же клиенте, на этом пути не мерился. **Известное и принятое:** блокировка эквивалента писателем дольше 60 с откладывает удержание подтверждённого `FAILED` до следующей попытки (вердикт `FAILED` уже опубликован, прогон `failed`, `/health` — `degraded`) — тот же класс, что прежняя ошибка реакции; до починки такое ожидание вешало всё задание. Тесты: `tests/integration/test_p047_integrity_waits_are_bounded_postgres.py` (2), `tests/unit/test_p047_integrity_attempt_deadline.py` (3); красные на `main` (все пять — по собственному сроку теста), мутации — снять `lock_timeout`, снять продолжение после ошибки эквивалента, снять срок попытки, снять срок вызова Redis — каждая красная. Подставные сессии двух существующих тестов (`test_background_task_supervision.py`, `test_p024_integrity_status_sees_hold_postgres.py`) получили `execute` — чекпойнт теперь начинается с `bound_the_waits`.
