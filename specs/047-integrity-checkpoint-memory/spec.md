# 047 — Сверка целостности: каденция по решению владельца (старт + сутки + ручная команда); пик памяти не растёт с историей

- **Date:** 2026-10-18, против `main` на `763f8b0a`; поправка 2026-10-18 (вечер) по решению владельца.
- **Status:** **АВТОРИЗОВАНА 2026-10-18 словом владельца («B — согласен»)** в части каденции и ручной команды (`T4701`–`T4702`); починка памяти (`T4703`) остаётся в программе как **несрочная** и идёт после них. Исполнение — у оркестратора через агентов, после слияния 044 ст. 2 (общие документы о чекпойнте).
- **Status authority:** метка описательная; завершённость устанавливают записанные evidence с SHA, командой и exit code, а не поле статуса.
- **Owner surface.** `app/config.py` (`INTEGRITY_CHECKPOINT_INTERVAL_SECONDS` — значение по умолчанию и датированная причина), `app/core/maintenance_jobs.py` (цикл чекпойнта `:150-170` — без изменения логики; стартовый прогон остаётся; **узкое исключение 2026-10-18, fix-delta §15:** TTL замка по умолчанию 300 с вместо `max(30, интервал)` и правило «сутки — только после завершённой проверки» (fix-delta 2, `93bea48f`), — без этого «стартовый прогон остаётся» не выполнялось, см. Changelog), новый `scripts/reconcile_debts.py` (ручная команда), `docs/ru/runbook-integrity-hold.md` §3 (вместо «следующий плановый прогон» — команда), `docs/ru/05-deployment.md` (каденция), `app/core/ledger/reconciliation.py` (`verify_journal_equals_change` `:969`, `_journal_sums` `:354`, `_operations` `:458`) — только для `T4703`, тесты сверки 015, новый тест пика памяти, тесты порога свежести (`reconciliation.py:1120-1135`, следует интервалу). **Исключено:** семантика сверки (что сравнивается и с чем; критерии (а)/(б); коды; реакция — удержание эквивалента), `Book`, журнал, триггеры БД, baseline, `POST /integrity/verify` (не превращать в запуск сверки без отдельного решения), симулятор (044), автоудаление денежных строк.
- **Origin.** 044 ст. 2 (`tracemalloc`): рост RSS публичного демо — периодический чекпойнт читает всю историю эквивалента в память каждые 5 минут (~6.5 КБ/операцию, пик 11 → 49 МБ при 1.5k → 7.4k операций; без чекпойнта плато ≈ 145 МБ). Владелец 2026-10-18: «раз в 5 минут (и вообще периодически) запускать проверку целостности — это вообще ненужная операция; это и есть overengineering»; просил оценить достаточность защиты при транзакциях и оставить ручную проверку или редкую автоматическую. Аналитик (Fable, read-only, 2026-10-18; якоря перепроверены советником): см. Findings.

## Problem

Каденция 300 с не оправдана ничем воспроизводимым и стоит O(история) каждые 5 минут навсегда; при 0.1–1 tx/s прогон через недели становится длиннее интервала, а пик памяти растёт с историей (044). При этом **сам верификатор нужен**: он — единственное обнаружение правок в обход приложения и условие остановки программ по §19.5 («остановка допустима только когда стоит обнаружение»).

- **F-047-4. Реакция не зависит от периодичности:** `react_to_failed` вызывается внутри `run_scheduled_reconciliation` (`reconciliation.py:1382-1466`) при любом вызове; удержание читается денежным путём из колонки; снятие перепроверяет эквивалент под блокировкой (`equivalents.py:206-234`). - **F-047-6. Цена прогона:** ≈ 14 операторов на эквивалент, вся история читается (журнал, операции с JSON, транзакции, долги и линии дважды); замер 015 5b: 10k строк — 1.51 с, 100k — 16.7 с (до 030 S3a); память ~6.5 КБ/операцию (044). Писателей не блокирует (снимок `REPEATABLE READ READ ONLY`).

## Решение владельца 2026-10-18 — вариант B

1. **Прогон при старте процесса остаётся** (`maintenance_jobs.py:150-153`, `reason="startup"`).
2. **Автоматический прогон — раз в сутки:** `INTEGRITY_CHECKPOINT_INTERVAL_SECONDS` по умолчанию `86400` с датированной причиной в `config.py` (порог свежести `2 × интервал + 5 мин` следует автоматически, `reconciliation.py:1120-1135`); развёртывания могут задать иное значение. Логика цикла не меняется.
3. **Ручная команда** `scripts/reconcile_debts.py` (~40 строк, по образцу `take_reconciliation_baseline.py`): вызывает `run_scheduled_reconciliation(AsyncSessionLocal, equivalent_ids=…)` **с реакцией 5c**, печатает по эквиваленту статус последней строки `debt_reconciliation_results`, `findings`, `missing_evidence`, `entries_read`; exit `0` — все `PASSED`, `1` — `FAILED`/`UNVERIFIABLE`, `2` — ошибка прогона; `--equivalent CODE` (повторяемый), `--all`. Оговорка оператору: та же база через `DATABASE_URL`; при одновременном плановом прогоне возможен устаревший вердикт, опубликованный последним (`record_outcome`, `reconciliation.py:1050-1080`) — при суточной каденции пренебрежимо. Runbook §3 п. 2: вместо «следующий плановый прогон» — эта команда.
4. **Не делать:** отключать цикл (`ENABLED=false` снял бы и стартовый прогон); проверку «по событию» (связывает верификатор с денежным путём — названо дрейфом в банк, `015/spec.md:1850`); «при простое» (новый механизм); удалять верификатор (снимает единственное обнаружение в обход приложения, нарушает §19.5).
5. **Починка памяти (`T4703`) остаётся, но несрочная:** потеря переквалифицирована на «процесс с историей ≥ 10k операций при любой каденции»; сверка агрегатами в SQL/порциями с идентичной семантикой; §15 Codex + **Argon триггер 2** — только для `T4703` (денежная верификация), не для каденции.
