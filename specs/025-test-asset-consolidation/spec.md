## Problem

Тестов в 2,9 раза больше кода: 370 файлов, 116 623 строки против ~40 000 в `app/`; тир собирает 3 332 элемента и идёт 14–15 минут. Гипотеза владельца «много устаревшего и дублей» **подтверждается частично**, и измерение показывает, где именно лежит объём:

1. **Четверть тира не тестирует backend.** 784 элемента (24 %) и ~11 400 строк — тесты инструментов: PowerShell-лаунчеры, форма CI-YAML, парсер команд в документации, рецепты сидов, стенды замеров решённых развилок, экспериментальный детектор 020, которого нет в продукте. 728 из них не исполняют ни одной строки `app/`. Они живут в обязательном backend-гейте, потому что `tests/conftest.py` отказывает без Postgres-URL на уровне модуля и других корней тестов нет.
2. **Одно правило записано по разу на каждый вход.** 1 052 элемента (549 функций) — это ~80 правил: «повтор `tx_id` отвечает по исходу первого запроса» проверен в пяти файлах; «нет admin-токена → 403» скопировано 14 раз; «деньги на wire — строка Decimal» — по тесту на каждого из 21 производителя. Это не дубли, а отсутствие табличной формы.
3. **Настоящих дублей и мёртвого — 204 элемента (6 %).** Из них 95 дублей, 80 тестов удалённых механизмов, 29 пустых (8 тестируют копию функции, объявленную в самом тестовом файле). Их удаление теряет 219 строк покрытия `app/`, из которых 212 — в модулях адаптивного клиринга, удаляемых программой 021 вместе с тестами.
4. **Arrange размножен.** 14 способов получить сессию, движок или клон базы; 81 сидинг-хелпер (2 385 строк) в 80 файлах и 117 тестов, строящих участников инлайн; ~100 импортов из одних тестовых модулей в другие (`test_scenarios.py` служит библиотекой 26 модулям). 464 клона базы на прогон тира.
5. **Проза врёт и здесь.** 25 файлов зоны p015 и ещё ~20 в остальных описывают SQLite-тир, `PaymentEngine`, `PREPARED`, «RED TODAY»; 24 `pytest.skip` «не Postgres» недостижимы; имена файлов называют удалённые механизмы при живом содержимом.
6. **Пробелы важнее дублей.** Ревью нашло поведение без единого теста: неверный admin-токен (и 14 из 28 admin-маршрутов без проверки токена вовсе); «встречный долг без линии» (F-024-3); статусы ошибок, которые хендлер возвращает сам, не сверяются с каноном (харнесс проверяет только 2xx); согласие на клиринг в нестроковых кодировках покрыто только тестом экспериментального детектора.

## Current / Intended / Optimal

- **Current.** Тир зелёный и содержательный: вакуумных тестов почти нет, ядро обнаружения (015), конкурентность на Postgres и wire-контракт покрыты настоящими стендами. Объём дают инструменты в чужом тире, отсутствие табличной формы, размноженный arrange и история в докстрингах.
- **Intended** (AGENTS.md §11, «Правило для тестового актива» в `specs/README.md`): тест проверяет наблюдаемое поведение через публичный вход; гард проверяет форму и говорит об этом; удаление — только с evidence; маркер и тир — часть контракта запуска.
- **Optimal.** Backend-тир содержит только тесты backend-поведения; каждое правило — одна таблица с читаемыми id строк; данные строит одна фабрика; режимов изоляции четыре; инструменты проверяются своим тиром без базы. Оценка результата (по зонам, не замер): из backend-тира уходит ~37 000 строк (≈ 32 %) и ~990 элементов, из них ~11 400 строк переезжают в тир инструментов, остальное удаляется или сжимается; время тира — минус ~190 с инструментов, ~100 с удалений и часть из 468 с сливаемых тестов. **Это оценки агентов; целью программы является не число, а критерии приёмки срезов.**

## Что называется «универсальным тестом»

Одно правило — один параметризованный тест с таблицей «вход → ожидание» и **отдельным читаемым id на строку**. Не супер-тест на 300 строк; не параметризация, прячущая разные пути под одним именем; не новый фреймворк, DSL или генератор. Допустимые средства: `pytest.mark.parametrize`, фабрика данных, фикстуры четырёх режимов, перенос файлов. Каталог из ~100 предложенных таблиц (`U-A-*` … `U-G-*`) записан в вердиктах полем `universal`; ключевые:

## Пробелы покрытия (F-025-10)

Регистрируются здесь; тест пишет эта программа, **дефект продукта, если тест красный, чинит владелец поверхности**.

1. Неверный admin-токен не проверен ни одним HTTP-тестом; 14 из 28 admin-маршрутов не проверены на токен вовсе (U-E-8).
2. Ёмкость пары «встречный долг без линии» (F-024-3) — ни одного теста; существующие закрепляют формулу `+ reverse debt` (U-E-10, числа после П1 программы 024).
3. Статусы, которые хендлер возвращает `JSONResponse` или поднимает сам, не сверяются с каноном; тела ошибок не валидируются (`openapi_response_conformance.py:513` — только 2xx). Дешёвое общее правило: харнесс уже видит все ответы, достаточно требовать `status ∈ declared(op)`.
4. Согласие на клиринг в нестроковых кодировках (`None`, `[]`, `{}`, `0.0`, `""`, пропущенный ключ) покрыто только экспериментальным детектором 020 — **перенести каталог в тест планировщика 023 до выноса p020** (U-B-8).
5. Критерий (б) сверки и эквивалент: писатель «суммы верные, эквивалент не тот» не покрыт.
6. Внешние ключи схемы: паритет `create_all`/alembic сравнивает только CHECK и UNIQUE.
7. Request-id в конверте ошибки и в логе (F-024-8) — теста нет.
8. Подпись на `update` и `close` линии — неверная подпись не проверяется.
9. Окончательный отказ staged-пути после допуска на `SERIALIZABLE` — есть только через диагностический READ COMMITTED.
10. Продовый `SseEventEmitter.emit_topology_edge_patch` не имеет прямого теста (8 тестов проверяют его копию в тестовом файле).
11. Переполнение `simulator_runs.seed` (int32 против 32 бит без знака) не утверждается ничем.
12. Нижняя граница бюджета и ограниченное исполнение static-клиринга, которые 021 обязана сохранить, не утверждаются ничем.
13. Громкий отказ `client` режима A на `POST /payments` (`conftest.py:590`) не проверен; голый pytest без `GEO_TEST_USE_MIGRATED_SCHEMA` строит схему `create_all` (87 ограничений против 90).
14. Кэш маршрутов `PaymentRouter` переживает клоны базы; общая фикстура его не сбрасывает — берёт фабрика.
