## Problem

Симулятор умеет проигрывать нагрузку (автоплатежи по интенсивности, `stress`-множители, клиринг каждые 25 тиков) и показывать её анимацией, но **рассказать историю** не умеет: событие сценария не несёт текста, который дошёл бы до зрителя, темп зашит в секунду на тик, участники появляются и замораживаются только при глобальном флаге, а события «платёж» и «клиринг» в сценарии существуют в схеме и молча игнорируются раннером. Повествовательной фикстуры нет: все пять сценариев — либо нагрузка на 50–100 участников, либо статичная заготовка для ручного клиринга.

Наблюдаемый вред — продуктовый (цель владельца): посетитель не может за короткое время увидеть жизнь сообщества с пояснениями. Это та же ось, что `F-034-D*` в 034 («не показано» по всем пяти целям), но со стороны **источника событий**, а не экрана.

## Целевое поведение

**Сценарий как рассказ.** Сценарий — это сообщество из 8–15 участников и **эпизоды**: датированные события с подписью для зрителя. Один эпизод — одно наблюдаемое изменение на графе и одна-две фразы, почему оно произошло и что это значит для сообщества. Зритель видит эпизоды подряд, медленно, с паузой перед следующим, если сценарий так велит. Пример сюжета (предложение, не решение): знакомство (10 участников, несколько линий доверия) → первая покупка напрямую → покупка через посредника → долги накапливаются, цвета меняются → появляется новый участник и ему открывают доверие → долги замыкаются в цикл → клиринг: «общий долг до → после, чистые позиции не изменились» → участник замораживается, его долги остаются видны → отказ платежа без доверия → финал с итогом.

**Формат (схема, `Contract: yes` для REST).**

- У события — `caption: {ru, en}` (тексты сценария живут в сценарии на обоих языках, чтобы UI не заводил второй словарь под чужой контент — запрос S9 2026-10-08; то же для `description` сценария), `pause_after: true|false` (ран сам становится на паузу после события — через существующий pause), `label` остаётся служебным.
- **Куда смотреть:** `focus: {pids: [...], edges: [{from, to}]}` на эпизод — камера и подсветка в UI; пустой `focus` = общий план.
- **Якорь к событию, не только ко времени:** `anchor: {event: "tx.updated"|"tx.failed"|"clearing.done"|"topology.changed", from?, to?}` плюс `time_ms` как фолбэк. Причина — честность: если платёж эпизода отклонён или сдвинулся на тик, подпись по одному `sim_time_ms` отрисовалась бы над чужим событием; UI показывает эпизод при совпадении якоря с реально пришедшим событием и только при отсутствии якоря — по времени.
- **Для эпизодов клиринга:** `expected_cycle: [pid, ...]` с правилом честности: UI рисует объявленный цикл только если все его рёбра ⊆ рёбер пришедшего `clearing.done`; иначе — общий пульс без подписи цикла. Это проверка объявленного по фактическому, а не выдумывание (§9); `T3600` сверяет, что `clearing.done` сегодня несёт рёбра цикла в достаточной форме, иначе цикл показывается только в Interact и офлайн.
- **Единый «формат истории».** `episodes[]` не привязан к REST-ответу: та же структура переиспользуется статической офлайн-фикстурой S9 — `episodes[]` плюс запись событий рана этого сценария в форме SSE (рантайм уже пишет `events.ndjson` в артефакты, `artifacts.py`; плейлисты `demo-tx.json`/`demo-clearing.json` 2026-02 — ровно такая запись). Офлайн-тур тогда не рукописный, а снятый с настоящего рана 036 и проверяемый гардом «фикстура актуальна» (образец — 029 S4). Снятие записи — задача 036 (`T3631`), плеер и оверлей — S9.
- `settings.playback`: `tick_seconds` (реальная длительность тика, диапазон, например, 0.25–5 с; дефолт 1.0 — текущее поведение), `intensity_percent` по умолчанию для рана (чтобы `clearing-demo-10` не просил README), `inject_enabled: true|false` на сценарий (П2-техн.).
- `time` — только целое число мс; строковые токены **удаляются из схемы** (F-036-1), фикстуры со строками не существуют (проверить grep'ом).
- `payment`: `{from, to, amount, equivalent}` — исполняется тем же путём, что Interact `payment-real` (ядро, идемпотентность по ключу сценария); `clearing`: `{equivalent}` — тем же путём, что `clearing-real`; оба публикуют обычные `tx.updated`/`clearing.done`. Отказ scripted-платежа — обычный `tx.failed` плюс `caption` эпизода объясняет отказ (это и есть «один объясняющий отказ» тура).
- Новые операции `inject`: `unfreeze_participant`, `remove_participant` (статус `left` — семантика долгов по П1), `update_trustline_limit`, `close_trustline` — все через существующие сервисы ядра, как три существующие.
- `stress` — одно место истины: `effects[]` + `metadata.duration_ms`; `params` из схемы удаляется (F-036-3), фикстуры чистятся.

**REST наружу (`Contract: yes`).** `ScenarioSummary` получает `description: {ru, en}`; новый `GET /simulator/scenarios/{id}` (или расширение существующего ответа — решает `T3600`) отдаёт `episodes[]`: `{index, time_ms, caption: {ru, en}, pause_after, kind, focus?, anchor?, expected_cycle?}` и `playback`. UI (034 S9) сопоставляет эпизоды с `run_status.sim_time_ms` и показывает подпись; **новых SSE-событий нет** (П7).

**Темп.** `tick_seconds` рана берётся из сценария (переопределяется параметром создания рана), применяется в цикле heartbeat вместо константы `sleep(1.0)`. Пауза по событию — существующий `pause`; «Дальше» — существующий `resume`. Шаг вперёд и перемотка **не делаются** (§19: нет пути, кроме тура; тур живёт на паузах).

**Фикстура.** Одна новая, `fixtures/simulator/community-story-10/scenario.json`: 10–15 участников, ≈20–30 эпизодов, длительность 3–5 минут при `tick_seconds` 2–3; попадает в allowlist (`runtime_impl.py:69-71`) и в демо-снимки UI (`tooling-tests/portable/test_p029_s4_demo_fixtures_of_every_equivalent_are_current.py` — обновить осознанно).

## Продуктовые вопросы владельцу

- **П1. Что происходит с долгами участника, который «выпадает» (`left`).** Протокол задаёт `suspended` (не платит, циклы с ним пропускаются, линии не создаются — `docs/ru/02-protocol-spec.md:136`), для `left`/`deleted` — только подписи (`:137-138`); матрица переходов — `09-decisions-and-defaults.md:141-156`; что с его долгами — протокол **не описывает** (grep «выход|покида|leave» пуст). Для мультфильма нужен ответ: (а) долги остаются и видны, участник серый, цикл с ним не клирится (= `suspended` с другой подписью) — дёшево, без изменения ядра; (б) долги списываются/передаются — изменение протокола, отдельная программа. Рекомендация: (а), эпизод «выпадение» показывает именно это — «долг не исчез, его видят все».
- **П2. Сюжет.** Принять предложенный выше порядок эпизодов как основу первой фикстуры, или вы дадите свой список сцен? Решение не блокирует движок (срезы A–B), блокирует только фикстуру (срез C).

Техническая развилка, решается `T3600`, не владельцем: инъекции на сценарий (`settings.playback.inject_enabled`) против глобального флага — предлагается «оба условия: флаг процесса разрешает, сценарий включает», чтобы публичный стенд мог запретить инъекции целиком.

2. **Протокол.** Показывается ровно то, что описано в `docs/ru/01-concepts.md` и `02-protocol-spec.md`; единственная дыра — П1 (`left`), и она решается выбором (а) без правки протокола.
3. **Противник.** Нет.
4. **Дешевле.** (а) Только `note` → UI без новых типов: не даёт появления участников, темпа и scripted-событий. (б) Офлайн-плейлист без живого рана (034 П5 — «Посмотреть пример»): закрывает первый экран, но не «потрогать»; 036 как раз делает живой источник для «Попробовать самому». (в) Текущие инъекции + ручная подгонка `time`: нет текста и темпа. Выбранный вариант — расширить существующий формат и раннер, не строить второй движок.
5. **Цена, числом (оценка исследования, уточняется `T3601`):** схема ≈30–50 строк; раннер — scripted `payment`/`clearing` через пути Interact ≈80–150, новые инъекции ≈4×60; темп и пауза ≈20–40; REST `episodes` ≈60 + OpenAPI ≈40; фикстура ≈300–400 строк JSON; тесты ≈400–600. Итого ≈500–800 строк продукта. Новых запросов к БД на тик — ноль сверх существующих путей.
6. **Крайние случаи.** Берутся: пауза по событию и `resume`; отказ scripted-платежа (это сюжетный эпизод); `restart` рана на середине сюжета (эпизоды с начала); инъекция при выключенном флаге процесса (явный `note`, не тихий пропуск). Не берутся: несколько одновременных туров на одном бэкенде (один ран на владельца — существующее ограничение), темп быстрее 0.25 с/тик.
