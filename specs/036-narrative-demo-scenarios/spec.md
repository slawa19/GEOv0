## Problem

Симулятор умеет проигрывать нагрузку (автоплатежи по интенсивности, `stress`-множители, клиринг каждые 25 тиков) и показывать её анимацией, но **рассказать историю** не умеет: событие сценария не несёт текста, который дошёл бы до зрителя, темп зашит в секунду на тик, участники появляются и замораживаются только при глобальном флаге, а события «платёж» и «клиринг» в сценарии существуют в схеме и молча игнорируются раннером. Повествовательной фикстуры нет: два сценария — нагрузка на 50–100 участников, один — статичная заготовка для ручного клиринга (`clearing-demo-10`), два — двухузловые технические (`minimal`, `trust-drift-decay-minimal`).

Наблюдаемый вред — продуктовый (цель владельца): посетитель не может за короткое время увидеть жизнь сообщества с пояснениями. Это та же ось, что `F-034-D*` в 034 («не показано» по всем пяти целям), но со стороны **источника событий**, а не экрана.

## Целевое поведение

**Сценарий как рассказ.** Сценарий — это сообщество из 8–15 участников и **эпизоды**: датированные события с подписью для зрителя. Один эпизод — одно наблюдаемое изменение на графе и одна-две фразы, почему оно произошло и что это значит для сообщества. Зритель видит эпизоды подряд, медленно, с паузой перед следующим, если сценарий так велит. Пример сюжета (предложение, не решение): знакомство (10 участников, несколько линий доверия) → первая покупка напрямую → покупка через посредника → долги накапливаются, цвета меняются → появляется новый участник и ему открывают доверие → долги замыкаются в цикл → клиринг: «общий долг до → после, чистые позиции не изменились» → участник замораживается, его долги остаются видны → отказ платежа без доверия → финал с итогом.

**Формат (схема, `Contract: yes` для REST).**

- У события — `caption: {ru, en}` (тексты сценария живут в сценарии на обоих языках, чтобы UI не заводил второй словарь под чужой контент — запрос S9 2026-10-08; то же для `description` сценария), `pause_after: true|false` (ран сам становится на паузу после события — через существующий pause), `label` остаётся служебным.
- **Куда смотреть:** `focus: {pids: [...], edges: [{from, to}]}` на эпизод — камера и подсветка в UI; пустой `focus` = общий план.
- **Якорь к событию, не только ко времени:** `anchor: {event: "tx.updated"|"tx.failed"|"clearing.done"|"topology.changed", from?, to?}` плюс `time_ms` как фолбэк. Причина — честность: если платёж эпизода отклонён или сдвинулся на тик, подпись по одному `sim_time_ms` отрисовалась бы над чужим событием; UI показывает эпизод при совпадении якоря с реально пришедшим событием и только при отсутствии якоря — по времени. **Точное сопоставление (`T3600`, уточнено `T3600.1`):** для `tx.updated` якорь несёт `from`, `to`, `amount`, `equivalent`; для `tx.failed` — только `from`, `to`, `equivalent` (у события отказа нет `amount`: `schemas/simulator.py:192-202`, эмиттер `sse_broadcast.py:536-567`, нормализатор `normalizeSimulatorEvent.ts:403-425`; поле **не добавляется** — П7), поэтому эпизод-отказ в последовательной истории единственный на пару в своём окне; совпадением считается **первое ещё не потреблённое** событие с этими полями, пришедшее после `time_ms` эпизода; одно событие потребляется одним эпизодом. Чтобы якоря не путались, первая история исполняется **последовательно**: один scripted-эпизод за раз, следующий — после паузы/подтверждения; автоплатежи в сюжетном сценарии выключены (`intensity_percent: 0`). Подпись о действии **никогда** не показывается по времени «по умолчанию»: нет события — нет подписи (есть отдельная подпись отказа по `tx.failed`).
- **Для эпизодов клиринга:** `expected_cycle: [pid, ...]` с правилом честности: UI рисует объявленный цикл только если все его рёбра ⊆ рёбер пришедшего `clearing.done`; иначе — общий пульс без подписи цикла. `T3600` сверил: `clearing.done.cycle_edges` есть (`schemas/simulator.py:220`, `sse_broadcast.py:674`, нормализатор `normalizeSimulatorEvent.ts:437`), но это **объединение** рёбер всех исполненных циклов (Interact — `simulator.py:184`; тик — `tick.py:803,873`, с фильтром и лимитом для FX). Поэтому включение `expected_cycle ⊆ cycle_edges` доказывает только, что рёбра затронуты, **не** что объявленный цикл исполнен отдельным циклом, и **не** даёт права приписать ему `cleared_amount` всей пачки. Правило честности: подпись цикла — «эти рёбра участвовали в зачёте»; сумма зачёта — только общая по событию; точный состав циклов — из REST-ответа scripted-клиринга (`cycles[]`, как у `clearing-real`), который раннер сохраняет в прогресс эпизода (REST, см. ниже), либо нейтральная подпись.
- **Единый «формат истории».** `episodes[]` не привязан к REST-ответу: та же структура переиспользуется статической офлайн-фикстурой S9 — `episodes[]` плюс запись событий рана этого сценария в форме SSE (рантайм уже пишет `events.ndjson` в артефакты, `artifacts.py`; плейлисты `demo-tx.json`/`demo-clearing.json` 2026-02 — ровно такая запись). Офлайн-тур тогда не рукописный, а снятый с настоящего рана 036 и проверяемый гардом «фикстура актуальна» (образец — 029 S4). Снятие записи — задача 036 (`T3631`), плеер и оверлей — S9. Контракт передачи `T3631 → S9`: исходный снимок, упорядоченные события в форме SSE, `episodes[]`, маркер окончания; файл кладётся в `simulator-ui/v2/public/simulator-fixtures/<id>/`. **Всё, что 036 правит в UI-дереве, перечислено явно:** эта папка записи и функции чтения `ScenarioSummary` в `simulatorContracts.ts`/`simulatorTypes.ts` (выше); ничего другого в `simulator-ui/v2/src` 036 не трогает. **Гард актуальности называется честно:** существующий гард 029 S4 проверяет форму и не сравнивает запись с источником (`test_p029_s4_...py:14`); новый гард 036 проверяет, что `episodes` записи равны `episodes` сценария и что каждое scripted-действие имеет своё событие в записи, — это проверка соответствия, не байтовая свежесть (запись живого рана недетерминирована по id и времени).
- `settings.playback`: `tick_seconds` (реальная длительность тика, диапазон, например, 0.25–5 с; дефолт 1.0 — текущее поведение), `intensity_percent` по умолчанию для рана (чтобы `clearing-demo-10` не просил README), `inject_enabled: true|false` на сценарий (П2-техн.).
- `time` — только целое число мс; строковые токены **удаляются из схемы** (F-036-1), фикстуры со строками не существуют (проверить grep'ом).
- `payment`: `{from, to, amount, equivalent}` — исполняется тем же путём, что Interact `payment-real` (ядро, идемпотентность по ключу сценария); `clearing`: `{equivalent}` — тем же путём, что `clearing-real`; оба публикуют обычные `tx.updated`/`clearing.done`. Отказ scripted-платежа — обычный `tx.failed` плюс `caption` эпизода объясняет отказ (это и есть «один объясняющий отказ» тура).
